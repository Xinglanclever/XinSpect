## Confirmed paths and arithmetic

The GUI scalar binds an LHM package sensor (`SensorService.cs:181–185`) and reads its value through the generic plausibility filter (`:550`). It does not use `KernelBackendHost` to obtain that sensor. `BuildCache` invokes `BuildCpu` for every CPU hardware object (`:146–148`); each invocation replaces the scalar package-sensor reference. Thus on multiple LHM CPU objects the scalar represents the last selected package, without retaining that identity in its public value. It must not be described as total-system CPU power. This multi-package limitation does not establish a defect on the reported single-package processor.

The inspected LHM 0.9.6 Intel implementation uses PawnIO, not WinRing0, for these MSRs (`IntelCpu.cs:41`); model 0x55 maps to its Skylake branch (`:145`). Its package-energy counter is 0x611 and energy multiplier is taken from 0x606. The ordinary exponent path applies to this branch; no evidence justifies a compensating scale factor for this CPU. Reading 0x606 successfully proves neither energy-counter accuracy nor package identity.

The CLI direct path is separate (`XinSpectCli/Program.cs:1491–1511`), uses the chosen backend, and is enabled for wattage only after the cached RAPL verdict is Trusted. It uses a monotonic Stopwatch and `CeilingDecoder.Delta32`. `CeilingDecoder.cs:93–101` correctly extracts the current conventional unit fields; `:345` performs modulo-2^32 subtraction. A single wrap is handled. Reset, multiple wraps, wrong source identity, and counter accuracy are not established by this subtraction. No defect in that pure wrap decoder was found, and no new decoder test was added merely to repeat it.

## Source-confirmed reliability defects and limits

1. **LHM uses a wall clock as the power denominator.** Pinned `IntelCpu.cs:690–696` subtracts `DateTime.UtcNow` values. A forward clock correction can produce an artificially low positive result; a backward correction/short interval takes the continue branch and retains the old reading. This conflicts with this repository's monotonic-time measurement requirement. A synthetic 100 J increment over one physical second divided by an elapsed wall-clock value of 100 seconds yields 1 W. That example establishes failure mechanics, not evidence that a clock correction happened in the screenshot. Narrow upstream/fork fix: monotonic timestamps for counter intervals, with failure/reset/overlong-window invalidation; preserve UTC separately as a label.

2. **LHM read failure retains a previously successful wattage.** `IntelCpu.cs:687` skips the update when the energy read fails; there is no matching invalidation of the power sensor. Last timestamps/counts update only at `:697–698` after success. A caller reading Value cannot distinguish a fresh sample from a retained one. `SensorService` presently provides the plausible value, not a proven source-updated timestamp. Narrow fix in an upstream/fork adapter: clear the current reading on read failure and invalidate the next delta baseline when interval continuity is lost. Do not infer stale merely because consecutive legitimate values are equal.

3. **Package identity is not enforced by the energy read call.** LHM energy reads at initialization `:484` and update `:687` use the non-affinity overload. The pinned IntelMsr transport exposes a separate affinity overload, but these calls do not use it. The local CLI reads at `Program.cs:1503–1508` likewise do not pin or record a package. Different packages can therefore supply the two endpoints if scheduling migrates the sampling thread. Pin both endpoints and the unit read to one known package representative; refuse on pin failure or missing identity. A processor group is not a package. This is a source-confirmed identity gap, with hardware occurrence untested here; it does not explain a known single-package capture by itself.

4. **Trust is process-global, not bound to the sampled source/package.** `RaplEnergyGate.cs:21–32` stores one verdict and applies it to any supplied reportedPower; the result has no backend, package, CPUID, unit, or session identity. A successful response check is also not an independent power-meter calibration. Bind any future verified state to the exact source/package/session and invalidate it on source change. Current production consumers should continue distinguishing unverified sensor reports from analytical input. This investigation did not invoke the diagnostic or change that contract.

5. **A backend status read can initialize hardware.** `KernelBackendHost.Snapshot():79–85` calls Ensure. Ensure creates the PawnIO candidate (`:95`), whose acceptance path reads PLATFORM_INFO (`PawnIoBackend.cs:52`); allowed universal mode can create WinRing0 (`KernelBackendHost.cs:110`). Therefore Snapshot/Route/RouteUse cannot serve as a passive, metadata-only inventory primitive. This matters when designing the proposed capture: merely formatting a status panel must not accidentally open a new hardware path.

The local PawnIO backend checks one nonzero PLATFORM_INFO ratio and only exposes a small MSR whitelist (`PawnIoBackend.cs:11,52,65–72,155`). This detects a class of unusable transport, not package-energy scale/counter calibration. It and LHM may share the same module/counter, so agreement is not independent verification. The WinRing0 adapter delegates to the embedded 0.9.4 bridge; host mode policy is local to that host, not a global ban on every direct bridge caller.

## Safe passive diagnostic producer proposal

Implement separately from the load diagnostic. Its constructor receives an already-open, authorized read session plus a lease that prevents disposal during a read; it must not receive a backend factory. Add a non-initializing cached-status/TryAcquireExisting interface to the owning host if necessary. No implicit call to Snapshot, Route, RouteUse, Computer.Open, WinRing0Bridge.Create, repair, service install/start, module load, or settings mutation is allowed. If no authorized session already exists, return the actual unavailable state and reason.

Require an explicit passive-capture request and the applicable existing diagnostics/read-policy gates. Check current gate and cancellation before and after each synchronous read. Revocation stops further reads. No operation enables either risk switch. No fallback changes backend when a read fails. Never invoke RaplEnergyGate.EnsureStarted/RunOnce/RunOnceAsync or any benchmark/load worker. No hidden retry.

Use one dedicated, ordinary-priority sampling thread solely for a bounded sequence of reads and waits. Establish a known package representative `(Group, LP)` from real topology/identity; do not equate groups with packages or guess from thread count. Pin for the entire capture and verify Pin.Ok before reading. If support/identity is unresolved, produce Unknown/NotSupported with the reason instead of a wattage. Keep a single-package-only implementation explicit until package topology is implemented.

Suggested small fixed budget: eight samples at 500 ms, one fixed whitelist of 0x606 and 0x611, at most one in-flight read, no repeated failure loop. Capture UTC for report labeling plus QPC timestamps immediately before/after every call. Preserve full raw values, low-32 energy count, exact backend/module/assembly version/hash, CPU family/model/stepping, package identity, pin result, per-call status, configured gate state, sensor identifier/name and captured LHM Value. Source-update time must remain explicitly unknown if the provider does not expose it. Use the QPC read midpoints for the nominal interval and preserve durations to show uncertainty.

The producer can derive energy units and modulo-32 delta only after two successful same-source/same-package endpoints. Failures, unit changes, identity/session changes, nonmonotonic timestamps and overly long gaps invalidate the baseline; the next good point re-primes it. An apparent backwards counter is not enough to distinguish reset from wrap; retain that ambiguity and never silently grant Trusted. A bounded interval reduces multi-wrap exposure but cannot prove no reset/multiple wraps without further evidence.

Emit per-sample raw evidence and a derived estimate marked unverified/Unknown, with explicit interval and limitations. Never choose a floor, substitute TDP, tune a multiplier to an expected wattage, auto-load the CPU, or promote the existing process-global verdict. LHM-versus-direct comparisons are same-counter consistency checks, not independent measurement.

## Implementation follow-up — 2026-11-28

The parent authorized implementation after the initial investigation. New CpuPackagePowerDiagnosticService, OS/CPUID runtime, result models, an explicit-start CpuPackagePowerDiagnosticWindow, and injected regression tests were added. The actual host changed is Services/KernelBackends/KernelBackendHost.cs. Root owns CPU-page navigation and subsequent serialized build/test execution. This section supersedes the initial proposal-only status; no hardware capture or build/test result is claimed by this author.

The new host lease never invokes Ensure/factories. It retains the already-open selector's in-flight lifetime reference, whitelists only 0x606/0x611, and refuses subsequent reads after policy or mode changes. Native I/O does not hold the host lock, so mode retirement remains responsive; if disposal is requested while a read is in flight, the lifetime reference is released only after that read actually returns. A blocking synchronous read is not falsely reported as cancelled. The diagnostic checks gate/cancellation around every read and at most every 50 ms while waiting. Post-revocation raw evidence is marked failed and never becomes a power endpoint. A partial sequence is retained for explicit export.

The default runtime requires Windows x64, exactly one actual Windows package record, successful group/LP pinning, a matching current processor, GenuineIntel family6/model0x55, no declared hypervisor, and a usable CPUID.0BH package identity. Unknown or multiple packages and unsupported CPUs refuse before MSR acquisition. Eight points at 500 ms use QPC read brackets and midpoints; UTC only labels the evidence. No load, implicit driver initialization, fallback, repair, settings mutation, or RaplEnergyGate entry is present. A read failure stops and never reuses a stale estimate. Unit changes/long or reversed intervals invalidate that interval; subsequent points can re-prime. A modulo wrap increment is retained, but a descending counter's wrap/reset ambiguity suppresses wattage. Counter-stall does not become a zero-watt claim. Quantization resolution is explicitly not accuracy.

This addresses wall-clock, affinity, and stale-value failures **inside the new capture path only**. It does not patch LHM 0.9.6's existing implementation or identify the original 1.3 W cause. The window displays provenance, raw hex, QPC brackets, derived-unit/interval details, and limitations; JSON is written only after an explicit Save dialog. Construction/opening does not capture.
