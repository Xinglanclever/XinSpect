# XinSpect 工程憲法與接手行為規範

生效日期：2026-11-16。依使用者本輪明確要求整理，適用於維護者、AI 代理及受委派的工程工作。

**航太與企業級工程紀律、極客所需的深度、真實、安全、來源可追溯、定義精確，是共同要求。**
這是工程與驗收要求；任何認證、平台支援及精度宣稱，另須有對應證據。

本文件整理共同約束，不取代現有規格與歷史證據。舊文件與使用者最新指示衝突時，以使用者最新指示為準，記錄衝突、適用日期及待修正文案；不得默默挑選較寬鬆的條款。
文件中的版本、測試數、實機耗時與完成狀態，須回查程式、原始輸出和當前交接，不能沿用歷史數字充當現況。

## 2. 深度與企業可靠性

- 新功能須回答具體硬體或營運問題，包含讀取、解碼、定義、限制、診斷與驗證流程；不得用同義鍵、治理清單或空殼按鈕增加完成數。
- 保留既有內建能力；合併重複邏輯時先確認語意、消費端與相容性，避免遺失不同來源的證據。
- 桌面與 CLI 使用同一份領域邏輯、風險閘門與結果定義；某一入口尚未接線時明列缺口。
- X58／X79／X99／X299、C602／C612／C621／C422、EPYC、Xeon W，以及 MSDT／HEDT／MODT 必須按實際拓撲識別。MSDT 指主流桌機，HEDT 指高階桌機，MODT 指桌機改裝行動 CPU；平台名稱本身不構成支援證據。
- 對多插槽、NUMA、處理器群組、異質核心、DIMM／通道／rank、ECC 及 BMC 的假設必須成文。遇到無法辨識的拓撲或廠商欄位，保留原始證據並拒絕臆測。
- 每條讀取路徑明定時間、記憶體、併發、重試及覆蓋範圍預算；慢啟動、卡住、部分結果與取消均屬正式失敗情境。
- 航太工程紀律落實為需求可追溯、失效分析、邊界驗證與可重現證據；企業紀律落實為穩定介面、可稽核輸出、資料主權及平台相容性。不可僅加上名稱便宣稱達標。

## 3. 真實、來源與精確定義

- 每項數值須能追到裝置與範圍、原始欄位、位元位置、單位、轉換、有效範圍、來源版本、取得時間和已知限制。規格引用依既有 `SpecRef` 機制。
- CPU／DRAM 來源順序：**已支援且安全的核心／驅動直接讀取優先，其次 WMI，最後 CPU-Z 等外部來源**。優先序不等於絕對正確；失敗、停用及降級原因須可見，不得為取得高優先來源繞過風險閘門。
- 優先使用原廠文件、正式規格、官方 SDK／作業系統文件及上游原始碼，記錄修訂版、章節或 commit。第三方讀數與 AI 意見作為待核線索，不能自充驗證來源。
- 沿用六態：`Present`、`Unknown`、`NotApplicable`、`NotSupported`、`InsufficientPrivilege`、`ReadError`。讀不到、有值未確認、沒有硬體及本版不支援須分清；不得以 0、典型值、舊值或猜測冒充成功。
- 信任等級與可用狀態分別保留。`Reported` 是來源自述、`Derived` 是推導、`Measured` 只代表依所述方法取得；任何一種都不是精度認證。推測依既有 `Speculative` 隔離規則。
- 嚴分 CPU package／core／socket、設定值／實際值、標稱／量測、ECC 能力／啟用／錯誤事件，以及 Embedded Controller／ECC。數字的小數位數不代表準確度。
- 跨來源比較須確認同一實體、同一量、索引語意、單位與時間；同型號不保證同裝置，同名核心不保證同核心。來源共用感測器或 provider 時不得稱為獨立驗證。
- 分別標示來源更新時間與本程式讀取時間，未知者明列未知。量經過時間使用單調鐘；牆鐘供時間標記，不得混用。
- 多來源矛盾須列出雙方與限制；缺證據時維持未知／無法驗證，不以來源數量或表面一致推定正確。

## 4. 預設安全與資料主權

- 兩級風險開關均預設關閉；先開第一級，才能開更危險的第二級，關閉第一級時第二級不得繼續生效。高風險項目紅字顯示後果，必要的逐項確認在執行邊界生效，桌面與 CLI 一致。
- 硬體寫入、EC 原始存取、MSR／PCI／SMBus 寫入、高負載測試及威脅模擬須依各項風險門檻執行。開啟開關不等於所有平台、位址及操作都已獲驗證。
- 「讀取」也須檢查副作用：read-to-clear、EC 命令交易、共享匯流排與韌體仲介不可僅因名稱唯讀便視為無風險。尊重所有權、白名單、鎖與斷路器，不搶占硬體交易。
- 呼叫端逾時不等於核心 I/O 已取消。資源只能在操作確實結束後釋放；不得對仍卡住的裝置無限重試、換路徑重發或提前回收緩衝區。
- 未實作、未編譯、未封裝、未載入、未接線與實際執行的驅動／後端分別標示。第三方元件保留來源、授權與實際能力邊界。
- 預設本機處理；網路、AI 與擴充功能遵守既有逐項選擇及資料遮蔽。金鑰、序號、UUID、個人路徑與未遮蔽快照不得寫入公開文件、測試輸出或發送給外部模型。

安全與量測細節另見 [SECURITY.md](../SECURITY.md)、[EC 風險歷史評估](EC-RISK-ASSESSMENT.md)、[量測方法學](MEASUREMENT-METHODOLOGY.md)及[企業離線基準](ENTERPRISE-BASELINE-PACKAGES.md)。歷史 EC 裁定須按最新授權與實際通路重新核對，不能據此抹除風險或假稱已安全實作。

## 5. 驗證與完成判準

| 證據 | 可以支持的結論 | 仍缺少的證據 |
|---|---|---|
| 編譯成功 | 該組態可編譯 | 實際行為、硬體相容性 |
| 純函式／注入回歸 | 指定輸入下的邏輯 | 真實介面、實機時序 |
| 生產入口整合 | 已測入口確有接線 | 未測入口與硬體矩陣 |
| 實機紀錄 | 該硬體、系統、設定下的結果 | 其他平台、長時間及故障情境 |
| 全套測試通過 | 當次程式與環境下既有斷言通過 | 零缺陷、全平台支援或認證 |

- 高風險變更驗證格式邊界、畸形輸入、權限、逾時、取消、併發、部分結果與資源生命週期。測試須能捕獲實際缺陷，不寫只重複實作的湊數測試。
- 測試失敗先保留證據、定位原因再修；不得降低斷言、略過測試、靜默重試到綠或把環境失敗列成通過。
- 測試數、鍵數、來源數、覆蓋率、突變分數與功能完成率分別計數、註明範圍。測試數以實際完整結果對帳，不以推算替代。
- 新增資料或解碼器須確認生產消費端；更新同一來源生成的文件、三語硬事實及守門。尚缺實機、來源時間或獨立性證據的候選維持未完成。
