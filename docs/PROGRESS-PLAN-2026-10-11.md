# XinSpect 600 項推進計畫（2026-10-11）

## 0. 推進規則（使用者定調）

- **50 項＝一版**：版本號、changelog 條目、README 徽章／連結／沿革、測試基線都在**累計 50 項完成時**才動。
- **每 10 項跑一次檢測**：每組 10 項做完就跑一次套件（前景），紅的當場修，不把紅的帶進下一組。
- **每版（累計 50 項）發一次 GitHub Release**：push＋tag＋三資產＋`verify-release.ps1`＋README 位元組數 docs commit（順序不可顛倒）。
- **先簡後難**：優先挑「純讀取、有現成接縫、可合成 fixture 單元測試、不碰硬體風險」的項（表解碼、既有服務補事實鍵），把需要硬體／AML 解譯／UI 算繪／大工程的項往後排。
- 誠實紅線不變：**讀不到一律三態**（Present／NotApplicable／NotSupported／InsufficientPrivilege／Unknown／ReadError），**沒對準出處就不出值**，**不造假值**。

## 6. 計數紀律與查重結果（2026-10-12 使用者指出「有些功能已經做過了」之後补）

**規則（往後每輪第一條）**：一項只有在下列兩種情形才算一項——
①**新增能力**（原本讀不到的東西現在讀得到）；②**收口**（能力早就在，但規格要求的輸出鍵／陳述沒落地，本輪把鍵落地並加測試）。
以下三種<b>一律不計</b>：重複做既有服務（換個鍵名再講一次）、只做一半（有鍵但規格的實質動作沒做）、純聲明（只說「本版不做」）。
查重方法：先 grep 目錄 ID 與來源關鍵字（`wu.history`／`virt.*`／`acpi.table.*`／`setuptl`／`powercfg` 等），
再看 `Services/` 有沒有人做過同一件事；<b>有＝收口或不計，沒有才算新增</b>。

### 缺陷修復：NVMe 紀錄頁卡死（2026-10-14，同批）

**症狀**：全套測試跑到一半整個行程凍住，連測試結果都印不出來；`taskkill /F` 也殺不掉。

**根因**（`work/hangdiag*.ps1`、`work/p*.dmp` 的 `dotnet-dump` 傾印）：數十條執行緒全停在
`StorageSmartService.ReadNvmeLogCore` 的 `DeviceIoControl`。本機那顆狀態為<b>裝置故障</b>的
NVMe 對日誌頁查詢卡在驅動的逾時佇列（`SRB_STATUS_SELECTION_TIMEOUT`），兩種逾時機制都攔不住：

1. `DiskIo` 的「逾時就不等它」只讓<b>呼叫端</b>繼續，卡住的執行緒<b>永遠不回來也不釋放</b>——

2. `TryReadNvmeLog` 又套了 `GuardedRead` ＋ 外層 `Task.Wait(6s)`，同一次查詢被兩種逾時各記一次帳。

**修復**：NVMe 紀錄頁改走<b>可取消的 overlapped I/O</b>（`FILE_FLAG_OVERLAPPED` ＋
`WaitForSingleObject(3s)` ＋ 逾時 `CancelIoEx`），結果直接回報 `StorageProbeBreaker.Report`
（新增）；`DiskIo` 的文件補上「這不是萬靈丹」與「能取消的用 overlapped，只有取消不了的
同步 IOCTL 才用洩執行緒法」的規則。斷路器成為「不再製造新的卡死執行緒」的唯一防線。

**測試汙染一併修**：`FactKeyRuntimeReconcileTests`、`StorageReliabilityFactsTests`、
`UiSmokeTests` 走共用組裝點時會碰真碟。新增 `StorageAndScenarioReconciliationFactsService.IReaders`
接縫（`UseReaders`，可疊回），讓只驗接線與鍵對帳的測試改走合成讀取器——
<b>測試綠不綠不該取決於哪顆碟插著。</b>真碟行為仍由儲存類別自己的測試負責。

**新增守門**：`Tests/NvmeOverlappedIoTests.cs`（不存在裝置快速回 null、冷卻期間直接跳過、

### 推進紀錄：第 531–532 項（2026-10-14，CPPC 能力與滑鼠輪詢率）

2 項全計（逐項查重後確認為缺口）：**AC-002 CPPC 處理器效能控制**（`ac.cpc.summary`）、
**GP-004 滑鼠輪詢率實測**（`gp.pollrate`）。

鍵 618→620、測試 +28（5163→5191 綠，exit 0）。**有效累計 532／600。**
紅線：
① AC-002 <b>刻意不解碼 AML</b>——_CPC 是 DSDT 裡的位元碼，要取值就得寫 AML 解譯器，
而「解不出來卻有值」正是本專案最怕的失敗模式；改走 OS 層看得到的三件事實
（CPUID 的 HWP 能力位／Kernel-Processor-Power 事件痕跡／EPP 設定可讀性），

完整實作並被 28 條測試釘住；<b>即時取樣器本版刻意不接</b>——讀 Raw Input 要在收集流程裡
掛訊息迴圈等 500 ms，而事實收集是同步的啟動路徑，為一個事實鍵改架構不值得。
所以 <code>ReadSample()</code> 回 null → 誠實標 ReadError 並說明；接上取樣器時只換這一個方法。

### 推進紀錄：第 533 項（2026-10-14，更新失敗重試鏈）

1 項：**UF-002 失敗重試鏈**（`uf.retry.summary`／`uf.retry.count`）。

鍵 620→622、測試 +22（5191→5213 綠，exit 0）。**有效累計 533／600。**
紅線：
① <b>重試不等於失敗</b>——Windows Update 本來就會重試，重試一次成功是正常流程，
所以卡住的門檻看的是<b>失敗次數</b>（達 3 次）不是嘗試次數；
② <b>匯總用 KB 編號不用標題</b>——標題常含產品名與語言，KB 才是穩定識別；

③ <b>不斷言原因</b>——重試鏈只證明「這件事沒做完」，不證明為什麼。

看不出「同一個 KB 失敗七次」與「七個 KB 各失敗一次」的差別——前者是卡住、
後者是一次性問題，處置方式完全不同。本項補的是<b>聚合視角</b>，
共用同一份 WUA 歷史（`FetchCom()` 讀一次、兩個服務各自彙整）。

**測試踩到的坑（記下來免得再犯）**：驗「失敗分布最多列五條」時我用
`value.Split("失敗 ")` 計數，結果是 6 不是 5——門檻說明裡的
「同一個識別失敗 3 次」也含「失敗 」。改用 regex 也只解決一半，
最後是<b>先把字串切到「失敗分布：」之後</b>再數才對。
