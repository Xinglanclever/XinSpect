# 第 322 輪（U10 第三圈 FS-0001＋FS-0002）：NTFS 開機磁區——磁碟自己寫的字，與驅動的說法對帳

> `fs.mft.stat` 從 Vol 2 批次 B 起就在回答「這個卷冊的 MFT 多大」。
> 但它讀的是 `FSCTL_GET_NTFS_VOLUME_DATA`——**那是 Windows 解析後的看法**。
> 這一輪去問磁碟本人：開機磁區的 BPB 怎麼說，而它說的跟驅動說的**是不是同一件事**。

## 一、為什麼要做

檔案系統面在這一輪之前只有兩把鍵：`fs.mft.stat`（卷冊統計）與 `fs.usn.state`（USN 日誌）。
兩把都來自同一條通路，所以它們回答的是**同一個來源的兩種切面**，不是兩個來源。

而 `fs.mft.stat` 的值裡有一個數字看起來很確定：MFT 有效長度、每筆記錄大小、叢數。
那些數字是對的——但「對」的意思是「驅動這樣算」。**磁碟上寫的 MFT 起點在哪一格，
那時候沒有人問過。**

這一輪把那個問題問出來，並且順便拿到第三圈真正想要的東西：**兩個來源**。
一個來源只能陳述，兩個來源才能對帳；而對帳才有「不一致」可以抓。

## 二、做成什麼

三件東西：

1. `XinSpect.Decoders/NtfsBootSector.cs`——NTFS 開機磁區（磁區 0）的 BPB 解碼器，
   每個公開成員都有 `[SpecRef]`（Microsoft「NTFS Volume Boot Record」的逐欄位移）。
2. `fs.ntfs.bpb`——BPB 逐欄：OEM ID、每扇區位元組、每叢扇區、媒體描述符、
   每磁軌扇區／磁頭（歷史欄位）、隱藏扇區、總扇區、每 MFT 記錄、每索引緩衝區、結尾標記。
3. `fs.ntfs.mft.layout`——MFT 起始 LCN 與 MFTMirr 起始 LCN，**逐項與驅動端對帳**：
   磁碟說 786,432、驅動說 786,432，那一格才寫「一致」；不一樣就指名哪一邊差在哪。

讀取面只有一條新的：`SystemBootSectorProbe` 唯讀開啟 `\\.\C:` 讀位移 0 的 512 位元組。
**它與 `SystemVolumeProbe` 是同一個裝置、同一種權限**（管理員），沒有多開任何東西。

## 三、這一輪最容易寫錯的一格：`-10` 不是 246

NTFS 的「每 MFT 記錄叢數」與「每索引緩衝區叢數」是**有號位元組**，規格約定是：

| 欄位值 | 意思 |
|---|---|
| 正值 *n* | 每筆記錄佔 *n* 個叢（乘以每叢位元組） |
| 負值 −*n* | 每筆記錄是 2^*n* 位元組 |
| 0 | 未宣告 |

本機 C: 的欄位值是 **−10**，也就是 **1024 位元組**——與 `fsutil fsinfo ntfsinfo` 印的
「每個檔案記錄區段的位元組數目: 1024」相符。

如果照位元組讀（`0x40` 是 `0xF6`＝246），值會變成「246 叢」＝1,007,616 位元組。
**那不會拋例外、不會紅燈，只會安靜地講錯話**——正是這個專案最在意的那類缺陷。
所以解碼器把它讀成 `sbyte`，並且對指數限定 9–16（512 B–64 KiB）：超出範圍就回 `null`，不硬算。

## 四、第二格：0x50 的「校驗和」——驗不出規則就不要編一條

規格把位移 `0x50` 的 4 位元組叫「Checksum」。這一輪先在本機五個 NTFS 卷上量了一輪：

| 卷 | 0x50 的值 | 前 0x50 位元組的 DWORD 和 |
|---|---:|---:|
| C: | 0x00000000 | 0x47EF4093 |
| D: | 0x00000000 | 0x74B565FE |
| E: | 0x00000000 | 0x0C7694A5 |
| H: | 0x00000000 | 0x9026FE30 |
| I: | 0x00000000 | 0x9F84C309 |

**五個都是 0，而任何一種候選算法都對不上。** 所以這一輪的處置是：
把欄位如實解出來，**但不在值裡宣稱它是哪一種校驗**，並把「本機各卷皆為 0」寫進界線。
編一條看起來合理的校驗規則，會讓讀者以為這個數字被驗過了——那比不寫更糟。

## 五、第三格：一致不代表正確

`fs.ntfs.mft.layout` 寫的是「磁碟說 A／驅動說 B（一致）」。這句話的**強度必須寫清楚**：

- 一致只證明**兩個來源對同一組起點有共識**。
- 它不證明 MFT 內容正確——內容要靠逐條解析（屬明示觸發，本版未做）。
- 它也不知道**備份開機磁區**說了什麼：備份在卷尾，本版**未讀**。
  所以本輪只能說「開機磁區這樣說」，不能說「兩個開機磁區一致」。

這三句都寫在 `Value` 裡，不是寫在這份文件裡就算。

## 六、兩個「沒有」要分開

非 Present 的情形這一輪分成三種，理由各自不同：

| 情形 | `Availability` | 為什麼不是另外兩種 |
|---|---|---|
| `CreateFileW` 失敗（錯誤 5） | `InsufficientPrivilege` | 管理員權限就能讀，不是卷冊不存在 |
| 短讀（要求 512、拿到更少，Win32 沒報錯） | `ReadError` | 「打不開」與「讀不滿」是兩件事；短讀要懷疑讀取路徑 |
| OEM ID 不是 `NTFS    ` | `NotApplicable` | 這兩把鍵只描述 NTFS 卷冊；系統碟不是 NTFS 時它們不適用 |

第三種特別值得寫下來：把「不是 NTFS」標成 `ReadError`，會讓讀者以為「權限不夠、再試一次」；
實際上是「這把鍵對這台機器沒有意義」。**不同的「沒有」要用不同的狀態說。**

## 七、沒有多讀一次 FSCTL

對帳的兩邊必須是**同一輪的同一份資料**。若 `NtfsVolumeFactsService` 與
`NtfsBootSectorFactsService` 各發一次 `FSCTL_GET_NTFS_VOLUME_DATA`，
兩次之間卷冊可能剛好被掛載／卸載，於是「不一致」可能只是兩次讀取之間世界變了——
**那是自己製造的假訊號**。

所以 `NtfsVolumeFactsService` 多了一個 `out NtfsVolumeData?` 的重載，
`EvidenceLabService.LoadFsForensics` 把同一份資料交給開機磁區那一側。
這與第 321 輪「一次列舉餵兩個消費者」是同一條規則。

## 十、怎麼複算

```bash
# 事實鍵數、fs 域鍵數
python - <<'PY'
import re,io
from collections import Counter
s=io.open('Services/FactKeyCatalog.cs',encoding='utf-8-sig').read()
i=s.index('public static IReadOnlyList<string> Keys'); j=s.index('public static int Count')
keys=re.findall(r'"([^"]+)"',s[i:j])
c=Counter(k.split('.')[0] for k in keys)
print(len(keys), c['fs'])
PY

# 開機磁區的 BPB（需管理員）
fsutil fsinfo ntfsinfo C:
```

`fsutil` 印的「Mft 開始 Lcn／Mft2 開始 Lcn／每個磁區的位元組數目／每個叢集的位元組數目」
就是本輪 `fs.ntfs.bpb` 與 `fs.ntfs.mft.layout` 的對照組；
兩邊對得上，代表解碼器讀的是同一個東西。
