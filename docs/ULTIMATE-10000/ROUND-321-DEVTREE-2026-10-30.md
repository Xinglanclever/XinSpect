# 第 321 輪（U10 第三圈 OS-0001）：裝置樹全圖——「讀不到」的裝置在哪一層

> 第 309 輪回答了「有幾台有問題」；這一輪回答「問題在哪一層」。
> 一台 USB 裝置讀不到，可能是它自己、它掛的集線器、或整條匯流排——
> **三個答案的處置完全不同**，而既有事實把三層壓成同一個「N 台有問題」。

## 一、為什麼要做

`os.dev.summary` 的形狀是計數：在場幾台、不在場幾台、有問題碼幾台、缺驅動幾台。
那個形狀回答不了「這台機器的裝置樹長什麼樣」——而**「讀不到」的第一個問題永遠是
「在哪一層讀不到」**：根匯流排上的裝置讀不到，換一條匯流排可能就好了；
葉節點讀不到，通常就是那個裝置本身。

樹**早就建好了**：`DeviceDiagnosticService.BuildReport` 從第 309 輪起就用
`Parent instance ID` 把扁平清單建成 `Roots`。只是沒有任何人把它投影成事實。

## 二、做成什麼

一把總覽 `os.devtree.summary` ＋ 一個逐根家族 `os.devtree.root.{序號}`。

總覽回答四件事：**幾個根、幾個節點、最深幾層、層級分布**（第 1 層幾台、第 2 層幾台…）。
逐根回答：這個根的子樹有幾台、在場／不在場、最深幾層、子樹內幾個問題碼、直接子節點是誰。

## 三、這一輪最重要的一格：「根」有兩種

`DeviceDiagnosticReport.Roots` 的建法是「父找不到就當根」。於是兩種完全不同的東西
在既有資料裡長得一樣：

| 情形 | 意義 | 這一輪怎麼寫 |
|---|---|---|
| `ParentInstanceId` 是 `Unknown` | Windows 說它真的沒有父節點 → **真正的頂層** | 「Windows 回報它沒有父節點（真正的頂層）」 |
| 有父，但那個父不在這份清單裡 | **樹在這裡斷了** | 「**它有父節點，但那個父不在這份清單裡**——樹在這裡斷了，不是「它是頂層」」 |

總覽另外計數「父節點不在這份清單的根 N 個」。把兩者都當成「頂層」，
會讓**一棵斷掉的樹看起來很健康**——這正是第三圈要抓的那種錯。

## 四、其他三條界線

**成環的節點不得無限遞迴。** 走訪用 `HashSet` 記錄已到過的 instance ID，
走不到任何根的節點在總覽裡如實申報（「成環而未連到任何根的節點 N 台」／
「沒有成環的節點」兩種都寫）。這不是假想的：`BuildReport` 的註解就提到
「因異常循環而未能成為 root 的節點」，它已經防禦過一次，這裡再防一次並**說出來**。

**值裡不放 instance ID。** 那串常含序號（與 `os.dev.*` 同一條界線）。
鍵用序號、值用「類別＋名稱」辨識；**代價是同一類同名的兩個根在文字上分不出來**——
這件事寫在總覽的界線裡，不假裝它分得出來。

**截斷要說出來。** 直接子節點超過 8 個、根超過 200 個，都在值裡寫「另有 N 個未列出」。

## 五、沒有新增讀取面

`DeviceTreeFactsService` 是純函式，輸入是第 309 輪那份 `DeviceDiagnosticReport`。
`LoadDeviceTruth` 現在一次列舉餵兩個消費者：

```
LoadDeviceTruth()
  ├─ new DeviceDiagnosticService().Scan()          ← 唯一的 SetupAPI 列舉
  ├─ DeviceTruthFactsService.Collect(report, at)   ← 第 309 輪（計數）
  └─ DeviceTreeFactsService.Collect(report, at)    ← 第 321 輪（階層）
```

列舉失敗時兩支都標 `ReadError`，理由同源。

## 十、如實申報的邊界

- **沒有在真機上看過這棵樹**：本輪的測試全部餵合成報告。真機上根的數量與層級分布
  可能與這裡的樣本差很多（PC 通常十幾個根、最深五到七層），但**數法與邊界不依賴那些數字**。
- **樹的形狀是 Windows 說的**：`Parent instance ID` 由 `CM_Get_Parent` 取得，
  本服務不推、不補、不修。它斷在哪裡就寫斷在哪裡。
- **不做健康判定**：只知道「這個子樹裡有 N 台有問題碼」，不評價「這個根重不重要」。
