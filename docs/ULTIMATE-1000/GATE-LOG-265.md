# 閘門紀錄：F 群六把——「需要一個產品決定」有時候只是還沒找到不需要它的形狀（第 265 輪）

> **前情**：第 264 輪（`GATE-LOG-264.md`）把計畫庫的稽核搬進測試、更正兩個誤診。
> 本輪做的是階段二剩下的主線：**F 群的六把風險陳述**（P2-099～P2-104，鍵 `fw.risk.facts.*`）。
> `STAGE-02-REMAINING-KEYS.md` 原本把這一群寫成「解鎖條件是**決定**，不是能力——
> 分數由哪些事實組成、門檻怎麼定，由使用者圈定（本輪不動）」。

---

## 一、這一群為什麼一直沒動

不是難，是**沒有可以照抄的規則**。要輸出一個「韌體風險分數」，就得先有：

1. 一份「分數由哪些事實組成」的清單；
2. 一份權重或門檻表。

這兩樣在計畫裡都沒有出處。而**沒有出處的權重表就是一套沒有出處的常數**——
本專案在 `UNSOURCED-CONSTANTS.md` 記過四次同型的病（看起來很認真、就是沒有依據）。
所以前三輪都把它留在待辦，GATE-LOG-261 也明寫「可以算，但不能由我發明規則」。

---

## 二、這一輪的轉折：那個「決定」是可以避開的

實作時發現：**兩樣東西都已經在版控裡了，只是沒有人把它們接起來。**

| 計畫要的東西 | 已經存在的來源 |
|---|---|
| 「分數由哪些事實組成」 | `FactRelationRules.All`——**29 條對帳規則**，每一條自己就宣告了它用哪些鍵、以及為什麼可以這樣比（`Explanation` 就是出處理由）。規則集就是那份清單，**不需要再宣告第二份**（兩份清單遲早會不一樣，本專案吃過這個虧） |
| 「門檻怎麼定」 | 不需要門檻：等級只用**「有沒有」**判定——矛盾 ≥1 就是「有矛盾項」、缺口 ≥1 就不是「全部一致」、全部都無法驗證就是「無法評估」。**沒有加權、沒有分數、沒有可調門檻**，所以也沒有「門檻該定多少」這個問題 |

**這一群真正的教訓：**「需要一個產品決定」有時候不是沒有選擇，而是**還沒找到不需要那個選擇的形狀**。
代價是把「風險高低」換成「證據可陳述程度」——這一點寫在事實的文字裡，不藏在註解裡。

## 三、六把各自做了什麼

| 鍵 | 內容 | 界線（寫進事實，不是註解） |
|---|---|---|
| `fw.risk.facts.parts` | 構成：規則集 N 條、一致／矛盾／無法驗證各幾條、逐條 `規則 id＝關係`、參與鍵幾把、來源欄指名規則集 | 「構成由規則集決定，不由本服務另立一份清單」 |
| `fw.risk.facts.level` | 等級：`無法評估`／`有矛盾項`／`部分未定`／`全部一致` 四值之一 | 「它描述的是這批證據能陳述到什麼程度，不是機器的安全狀態，也不下安全／不安全判決」；政策版本寫在事實裡 |
| `fw.risk.facts.gap` | 缺口：逐條列未取得的規則與原因（取自對帳引擎的三態） | 「不被當成 0 或『沒問題』——缺的是『不知道』，不是『沒有』」；`NumericValue` 是缺口條數，0 缺口時也是一句話而不是「沒問題」 |
| `fw.risk.facts.baseline` | 基線：canonical JSON（規則依 id、鍵依鍵名排序）＋內容雜湊 `sha256:` | **不含時間、機器識別與路徑**——否則雜湊每次都變，離線比對就沒有意義 |
| `fw.risk.facts.delta` | 差異：由「時間膠囊比較」產生，只比對參與風險陳述的鍵 | 跨機器直接 `NotApplicable`（拒比）；「差異本身不是故障，也不建因果」；沒有差異時說「不等於沒有變更」 |
| `fw.risk.facts.report` | 報告：沿用既有的 `HtmlReportService`（自足單檔、尾端嵌可重算 SHA-256） | 報告不下「好／壞」總結；審計鏈狀態取不到時如實標「未取得」 |

守門（`Tests/FirmwareRiskFactsTests.cs`，22 條）：四個等級分支逐一釘住；
缺口的「0 缺口 ≠ 沒問題」；基線對同一份輸入穩定、格式是 64 位小寫十六進位、
不含時間與機器識別、規則與鍵都排序；差異的變更／無差異／跨機器三種結果；
報告可離線核驗；**以及一條靜態守門「風險陳述不得自己新增任何讀取路徑」**
（掃 `DllImport`／`ManagementObject`／`System.IO`／`Process`…——多一個 P/Invoke 不會有任何症狀，
所以只能掃原始碼）。

## 四、順手照出來的另一個缺口（不是本輪的範圍，但要記）

P2-104 依賴 **P1-072（`ev.chain.verify`：審計鏈與 manifest 互驗）**。查證發現：

> **`ev.chain.verify` 的產生端（`WriteGateReport.ToChainVerifyFact`）目前只有測試在呼叫它——
> 正式流程沒有任何地方生產這把鍵。**

所以 P2-104 的報告目前只能如實報「審計鏈狀態：未取得」，並且**不得把它寫成「沒有問題」**
（這一條也進了測試）。這是階段一的缺口（P1-072 自己的接線），
`FACT-KEY` 目錄有這把鍵、但執行期沒有值——與第 261 輪處理過的「目錄有、執行期沒有」同一型。
**留給階段一，不在這裡補**：補它要決定「誰在什麼時機算互驗」，那是產品問題。

## 七、這一輪沒有做、與不該被讀成「已解決」的事

- **「風險高低」仍然沒有被輸出，而且這是刻意的。** 本輪輸出的是「證據可陳述程度」。
  若真的要一個風險分數（例如給採購或稽核排序用），那仍然需要權重與門檻——那時候才需要產品決定，
  而且必須先有出處。**不要因為現在有一個「等級」欄位就以為風險已經被量化了。**
- **P1-072（`ev.chain.verify`）沒有生產端**，見第四節。
- **卡死的 testhost 與 headless 探針仍在樹上**（核心不可中斷等待，重開機才會消失）；
  這一輪的閘門同樣用 `-p:BaseOutputPath=` 繞開被鎖的 `obj/_rel_*`。
- `work/` 的暫存物仍未清。
