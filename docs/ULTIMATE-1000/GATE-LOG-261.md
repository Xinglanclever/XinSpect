## 一、先確認問題是真的：三種出口，第三種等於沒有

使用者的說法是「是不是很多功能做了但沒有顯示出來」。這一題不能用印象回答，所以先量：

| 量什麼 | 怎麼量 | 結果 |
|---|---|---|
| 導覽頁有沒有孤兒 | `Views/*.xaml` 與 `PageRegistry.Factory` 對帳 | 78 個檢視裡 11 個**不是孤兒**（host 在主頁分頁裡：主機板 4 個、處理器 1、記憶體 1、顯示卡 1、儲存 2、效能 1）；7 個是獨立視窗或卡片 |
| 事實鍵有沒有畫面 | 用目錄 1034 把鍵去比對 `Views/`＋`ViewModels/` 的字面引用 | **只有 1 把**（鍵名幾乎不出現在 UI 層——UI 走服務的屬性，不走路徑字串） |
| 服務有沒有被 UI 用到 | 352 支 `*Service` 對比 UI 層引用 | **223 支沒有直接被 UI 引用**（多半經由彙總服務進 `AllFacts`，只在匯出檔與證據實驗室看得到） |

**結論是誠實的中間版本：**不是「一堆功能沒有畫面」——每個服務的事實都進了 `AllFacts`、
進了報告與快照；問題是**第三種出口（只有匯出檔看得到）在使用者眼中等於不存在**：
功能確實做了（有 Collect、有金標測試），但他找不到它，於是「做了」與「沒做」長得一樣。

`Views/TroubleshootView.xaml` 是這個問題的現成例子：整頁故障排查嚮導寫完了，
但它不在 `PageRegistry` 裡，**沒有任何路徑到得了**。

## 二、這一輪的正面解：事實總表（`atlas`）

新增一頁 **「事實總表」**（`Views/FactAtlasView.xaml`＋`Services/FactAtlasService.cs`），
把本版實作的**每一把事實鍵**攤成一張可搜尋的表：

- **分母是編譯期目錄**（`FactKeyCatalog`，本輪 1037 把），不是「這一輪掃到什麼」。
  這一條是這一頁的靈魂：若分母改成收集結果，它就會退化成「這次掃到什麼列什麼」——
  而那正好是它要修的問題，並且畫面上看起來完全正常（一張整齊的表）。
- 每一列有：鍵、狀態（讀到／平台不支援／權限不足／讀取失敗／本機不適用／未確認／**本次未收集**）、
  值（非 `Present` 一律留白成「—」）、來源。讀不到的原因寫在名稱欄後面。
- 逐域摘要（`ac.dmar.summary` 的域是 `ac`）：目錄鍵數／本輪收到／其中量到／讀不到四欄分開，
  因為「收到」與「量到」是兩個不同的數字。
- 動態家族（27 個）另列，並寫明它們**不計入目錄總數**——成員由機器決定，編譯期列不完。

**「本次未收集」是這一頁最重要的字串。**它與「沒有實作」不同：最常見的成因是需要驅動、
需要提權、或要使用者自己按下量測。這一頁**不猜是哪一種**——猜一個原因比留白更糟。

守門（`Tests/FactAtlasTests.cs`，15 條）：目錄一把不少、不重複、逐域加總等於總數、
缺席一律標「本次未收集」而不是 0、非 `Present` 不得帶值與數字、搜尋不分大小寫、
域篩選與下拉選項、動態家族不冒充目錄鍵、五種三態都有中文說法。
UI 面另有 `UiSmokeTests` 的一條：**空資料與有資料各渲染一次**（這一頁最常出現的狀態是「空」）。

## 三、C 群三把鍵收口：說清楚一條路不存在，也是完成

`STAGE-02-REMAINING-KEYS.md` 的第 3 條建議是「把 C 群從 todo 改成明文『平台不提供』」。
本輪把它做完（`Services/FirmwareVariableSurfaceFactsService.cs`）：

| 鍵 | 規格項 | 收口後的陳述 |
|---|---|---|
| `ev.var.count` | P2-082 | Windows 只有**按名字**讀寫 EFI 變數的公開 API，沒有列舉 API；本專案不使用未公開的 `NtEnumerateSystemEnvironmentValuesEx` |
| `fw.capsule.history` | P2-089 | `Capsule####` 的編號本身要靠變數清單才找得到——沒有列舉就不知道有幾顆膠囊、叫什麼名字 |
| `ev.nvram.usage` | P2-090 | 用量需要逐變數大小再相加；上限同樣要靠列舉才數得出來 |

三件事一起寫清楚：

1. **兩個「沒有」分得開**：Legacy BIOS 開機時是 `NotApplicable`（這台機器沒有 EFI 變數），
   UEFI 開機時才是 `NotSupported`（有介面、沒有列舉路徑）。壓成同一個會讓讀的人以為換一台機器就能看到值。
2. **根因與第二個前提分開寫**：列舉 API 不存在是一件事；即使按名字讀也需要啟用
   `SeSystemEnvironmentPrivilege` 是另一件事（第 260 輪實測 elevated 讀 `BootOrder` 得到
   1314 `ERROR_PRIVILEGE_NOT_HELD` 的那個觀察，屬於後者）。
3. **與 P2-083（`ev.var.attrs`，已實作）的界線寫進程式註解**：那一把是按名字讀到的**那一個**變數的屬性，
   不需要列舉；常被混為一談，於是「讀得到某個變數」被誤讀成「盤點得了」。

矩陣與常數同步：`ok 65→68`、`todo 25→22`（`FirmwareDocReconcileFactsService`），
由 `FirmwareDocReconcileTests` 逐列重算矩陣釘住。事實鍵目錄 **1034 → 1037 把**。

## 五、把孤兒接上去：故障排查頁，以及「症狀→方向」的單一來源

第一節量到的孤兒（`Views/TroubleshootView.xaml`）在本輪收尾時接上了（`Nav/PageRegistry.cs` 的
`troubleshoot` 頁，掛在「總覽」群、**不標 Advanced**——收進簡易模式看不見的地方，等於把剛接上的路又切斷一次）。

**但接上去不等於把兩個入口疊在一起。** 菜鳥儀表板原本有六顆症狀鈕，各自在自己身上寫了一張
「症狀→要跳哪一頁」的對照表（`Troubleshoot_Click` 裡那個 `switch`），而嚮導裡六個場景
**每一個都已經有**可能原因／檢查步驟／建議動作／深入頁面。兩份對照表講同一件事，遲早會不一樣——
所以這一輪把對照表收成一份：

- 症狀鈕現在只做一件事：`TroubleshootView.Open(main, scenarioId)`——打開嚮導並指定症狀，
  **不再自己決定要跳哪一頁**。
- 嚮導頁在掛上視覺樹（`Loaded`）時把那張卡帶進可視範圍。用「待處理場景名」而不是直接選取，
  是因為按下症狀鈕時這一頁可能還沒被實體化（延遲載入），選取的對象還不存在；
  容器還沒產生就照常停在頁首，**不猜、不報錯**。
- 「症狀→方向」因此只有一個地方回答。要改哪一個症狀該看哪一頁，改 `TroubleshootService` 一次。

說明條目也跟著搬家：`beginner/故障排查嚮導` 改掛在 `troubleshoot/故障排查嚮導` 下。
**留著舊前綴會變成孤兒條目**——`HelpCatalogTests.說明表沒有孤兒條目` 就是為這種事存在的
（一條沒有人指的說明，會慢慢跟本事實講得不一樣）。

### 機械化：以後不會再靠「剛好有人去量」

這一類缺陷（**整頁做完、沒人指得到**）先前是靠人工盤點才照出來的，所以這一輪把它變成守門：

- `Tests/ViewEntryGateTests.cs`：`Views/` 裡的每一個檢視，都要被**別的**檔案指到
  （分頁註冊、被 host 的元素寫法、或獨立視窗）。自己的 `X.xaml` 與 `X.xaml.cs` 不算——
  一個只被自己提到的頁面就是這條網要抓的孤兒。
- **正對照不只是一個合成字串，而是一次真的假修補：**把 `troubleshoot` 的註冊與儀表板的呼叫
  同時拿掉，這條守門確實變紅並點名 `TroubleshootView`；改回來就綠。
  （第一次試的時候只拿掉註冊、守門是綠的——因為儀表板那行還在叫它。那不是誤報，
  而是這條網的定義就是「有人指得到」：**量錯了要修的是測試的預期，不是放寬守門**。）
- 守門清冊也補上了這一條（`GuardRegistry` 的「檢視入口守門」，含它守不住的那一半：
  「有引用、但引用路徑本身也到不了使用者面前」需要與命令面板／註冊表三方對帳）。

## 六、把 `ev.var.attrs` 接上（P2-083 的「輸入已經存在」真的用上了）

第二輪查證（`GATE-LOG-262`）修好了 UEFI 變數通路，並留下一件事等這一輪收口：
**`ev.var.attrs` 沒有被任何人收集**——它在目錄裡、有服務、有測試，但 `AllFacts` 裡不會出現，
所以在「事實總表」上永遠是「本次未收集」。那正是這一輪要修的病：功能做了，使用者看不到。

修法不是新開一條讀取路徑，而是**讓兩件事共用同一趟讀取**：

- `UefiSignatureFactsService.CollectWithReads` 在既有的那一趟（權限只啟用一次）之外，
  把 PK／KEK／db／dbx 四把的**富讀取結果**交出來。
- `EvidenceLabService` 把同一批讀取餵給 `EfiVariableFactsService.Collect`，收成 `EfiVariableFacts`，
  並接進 `AllFacts` 與匯出收集器。

**為什麼不是各自讀一次：**同一輪的兩份事實若各自去問韌體，就有兩個答案的可能，
而那種不一致在畫面上看起來像硬體在變。現在 `ev.var.attrs` 的內容是「`PK` 屬性 0x…／886 bytes」這種
與 `uefi.pk` **同一次讀取**得到的數字。屬性位元仍然不命名（`EFI_VARIABLE_*` 那張表還沒有可引用的原文），
原始值如實列出——這一條界線沒有因為接線而放寬。

## 七、帳面上那兩個對不上的數字（第 260 輪留下的）

第 262 輪的報告點出兩處**守門抓不到**的帳，本輪修掉：

   而同一支的常數 `AliasKeys = 24`。**一句話裡兩個數字，而 `FirmwareDocReconcileTests` 逐列重算的是矩陣**
   ——它守得住常數、守不住散文。註解改成 24，並在常數的說明裡把這件事寫下來：
   **會被人讀到的數字跟常數一樣要對。**

這種帳不會讓測試變紅，只會讓下一個讀文件的人算不出來——所以修法是把它寫成算式，不是再解釋一遍。

## 八、收尾時抓到：守門自己會當掉，而且只在「真的有東西要抓」時當掉

跑收尾測試時，`ServiceOrphanGateTests.每個服務要嘛被生產引用要嘛在登记表有顯式判定`
不是紅燈，而是**把測試主機弄當掉**（`測試主機處理序當機`，沒有失敗訊息、沒有堆疊）。
這種症狀很容易被當成環境問題——它發生在 `Starting:` 之後兩秒，什麼都沒印。

原因在守門自己身上：`ReferencedOutsideItsOwnDeclaration` 每次呼叫都 `new Regex(..., Compiled)`，
而呼叫點是「每支服務 × 每個生產檔」的雙層迴圈。這棵樹現在有 **392** 支公開服務、**916** 個生產檔；
即使孤兒數是 0，光是「每支服務找到第一個引用之前的那些檔案」就現編了近八萬個動態方法。

**最惡毒的地方是它與結果成反比：**孤兒越多，要掃的檔案越多，越容易在印出清單之前先當掉。
也就是說這條網**在最需要它的時候最可能沉默**，而沉默長得像「測試環境不穩」。

修法是把兩個樣式按服務名快取（`ConcurrentDictionary`，一個名字一對），去掉 `Compiled`：
392 個樣式一次建好、全程重用，24 秒跑完 4 條。**守門的效能也是守門的一部分**——
一條跑不動或當掉的守門，等於不存在，而且比不存在更糟（它會讓人以為已經守住了）。
