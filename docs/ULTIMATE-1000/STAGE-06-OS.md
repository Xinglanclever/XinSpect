# 極致計畫・階段六｜作業系統、驅動、服務與更新

> **規格庫，不是開工指令**：圈了 ID 才開工；接縫不到 API 級不許開工。
> **計數紀律**：只有「新增能力」或「收口」才算一項。
> **本階段 105 項（P6-001–P6-105）**，域碼 8 個。前置：階段一、二、四。

---

## 一、階段定位

階段六處理的是**作業系統這一層對硬體的敘述**：系統裝了什麼、驅動是誰、哪些服務在跑、角色與功能有哪些、更新到哪一版、端點政策是什麼狀態、效能觀測看到什麼。

這一層的特殊性在於：**它是最容易被誤認為「硬體事實」的一層，但其實是「軟體觀點」。**同一顆硬碟，SMBIOS 說它是哪一款、驅動說它能做什麼、服務說它被誰在用，三者可以完全不同。因此本階段的每一項輸出都必須標明它來自哪一層，並在跨層時並列而非取代。

階段六也承接兩個由專案自己確認的真實缺口：**驅動 IOCTL 的純靜態分析**（不載入驅動、不呼叫 IOCTL，因此與白名單最小化相容）與 **`.etl` 內容的讀回**（檔案已能寫、能驗、能管，獨缺讀回）。這兩項在本階段是錨點。

---

## 二、完美判準（Gate）

1. **靜態分析不動目標**：驅動 IOCTL 分析不載入驅動、不呼叫 IOCTL、不解析在地化字串（P6-017、P6-018）。
2. **`.etl` 讀回可對帳**：能讀 provider／事件數／CPU 取樣摘要，且**不可解的事件如實歸類，不以 0 補**（P6-092）。
3. **三層並列**：系統層、驅動層、硬體層的陳述並列，衝突具名（P6-001、P6-013）。
4. **服務與監聽對照**：服務清單可供監聽面三方對照使用（P6-030、P6-058）。
5. **角色與攻擊面分離**：角色存在性是事實，攻擊面是並列的對應關係，不合成單一分數（P6-033）。
6. **更新可對 CVE**：更新歷史可對知識包的已知問題清單（P6-051）。
7. **效能預算有守門**：效能退化由測試發現而非人工審查（P6-103）。
8. **端點政策只陳述狀態**：MDM、加密、應用程式控制等只陳述狀態，不判定合規與否（P6-069）。

## 四、完整規格（九欄）

### ★ P6-017｜驅動 IOCTL 與裝置介面的純靜態分析

**目標**：對一顆 `.sys` 回答「它提供哪些 IOCTL、開哪些裝置介面」，**完全不載入驅動、不呼叫任何 IOCTL**——因此與白名單最小化原則相容，且不需要任何權限。

**接縫**：PE 解析（匯入表、`.rdata` 中的裝置路徑字串）＋ 既有的 BYOVD 封鎖清單。輸入為磁碟上的驅動檔（唯讀開啟，僅讀取位元組）。

**方法**：解析 PE 標頭與分派表指標欄位（`MajorFunction` 表位址可自 `.data` 的 DriverObject 模板推得者才處理）→ 掃描字串池中的 `\Device\`／`\DosDevices\`／`\\?\` 樣式 → 彙整裝置名與可推得的分派旗標（`METHOD_*`／`FILE_*`）→ 與封鎖清單交叉引用。

**輸出鍵**：`drvinsp.{n}.devices`、`drvinsp.{n}.ioctl.methods`、`drvinsp.{n}.symbolic_links`、`drvinsp.summary`、`drvinsp.byovd.match`。

**三態行為**：檔案不可讀或非 PE → `ReadError` 附原因；PE 可解析但無可比對的分派表（如純核心庫）→ `NotApplicable`；字串池為空 → `Present` 且清單為空；**任何位址無法推得欄位時標 `Unknown` 並保留該欄位名，不以 0 補**。

**誠實界線**：本項**不判定驅動是否惡意**，也不反編譯函式內容；它只列出可靜態取得的介面事實並與封鎖清單比對。裝置字串可能是動態組出的，因此「未列出」不等於「沒有」，此限制寫入輸出。

**守門**：金標（模式：解碼器）——以真實驅動檔的解析結果為 golden；另以「載入／呼叫 IOCTL 的假實作」驗證掃描守門會紅燈（**這條守門同時保護白名單原則**）。

**依賴**：P6-016（驅動清單）、P1-008（唯讀保證守門）。

**驗收**：對已知驅動的裝置名與方法旗標與人工檢視一致；掃描守門有牙；未推得欄位在輸出中為 `Unknown` 而非 0。

### ★ P6-092｜`.etl` 內容讀回

**目標**：補上「寫得出、認得出、讀不回來」的最後一步——把專案自己產出的標準事件追蹤檔案讀回成可使用的事件摘要。

**接縫**：事件追蹤檔讀取 API（已在相依中）＋ 既有產出端（檔案模式工作階段）與檔頭驗證器。

**方法**：開啟 `.etl` → 逐事件列舉（provider、事件 ID、時間戳、CPU、負載摘要）→ 彙總為 provider 清單、事件計數、CPU 取樣分布 → **對無法解碼的事件（未知 provider 或格式）計入未解類別並列出其 provider 與事件 ID**。不嘗試以預設值填充未解事件。

**輸出鍵**：`etw.file.providers`、`etw.file.events.count`、`etw.file.cpu.spread`、`etw.file.range`、`etw.file.unsolved.count`、`etw.file.unsolved.list`。

**三態行為**：檔案不存在或非 `.etl` → `NotApplicable`／`ReadError`（依既有檔頭驗證結果區分）；檔案有效但無事件 → `Present` 且計數為 0；需外部解碼資訊而不可得 → `Unknown` 並列於 `unsolved`。

**誠實界線**：本項讀的是**已存在的檔案內容**，不進行即時訂閱（即時訂閱屬另一組既有服務）；不提供效能結論，只提供事件層級的摘要。未解事件的比例會被輸出，使讀者可自行判斷摘要的完整度。

**守門**：金標（模式：解碼器）——以本機既有 `.etl` 系統檔案切片作 golden；另以「截斷檔案」與「偽造檔頭」驗證不崩潰且不誤判為 0 事件。

**依賴**：P6-091（ETW 工作階段盤點）、P1-009（離線輸入接縫）。

**驗收**：本機系統 `.etl` 的 provider 與事件數與系統工具抽出的一致；截斷檔案不崩潰；未解事件比例輸出且有清單。

## 六、誠實界線與明文不做

**不做**：

| 不做 | 理由 | 解除條件 |
|---|---|---|
| 載入驅動、呼叫 IOCTL、動態測試驅動 | 會改變系統狀態；且與白名單最小化衝突 | 無 |
| 符號歸因（需符號伺服器） | 需網路，與零上傳衝突 | 由使用者在能上網的機器自行執行 |
| 修改服務、排程、政策、註冊表 | 寫入且影響系統行為 | 無 |
| 安裝、移除、更新任何軟體 | 寫入且不可控 | 無 |
| 端點合規評分 | 合規是機構定義，工具只陳述狀態 | 由機構提供可機器判定的政策檔 |

**本階段沒有證明的事**：階段六證明「作業系統這一層對硬體與自身狀態的敘述」，**不證明「系統是乾淨的」**。驅動分析（P6-017）列出的是可靜態取得的介面；服務與角色清單（P6-057、P6-031）列出的是現況，不是「應該如此」。這些事實的價值在於可與其他階段並列對照，而非單獨作為結論。
