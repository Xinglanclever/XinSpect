## 二、真正的缺陷①：規定的閘門在版控裡，卻沒有任何東西會跑它——而它已經跑不動了

> **更正（2026-10-18，本輪同日）：這一節的第一版寫「工具住在未入版控的暫存區」——那是錯的，
> 我沒有查就寫了。** 事實：`work/` **是入版控的**（`git ls-files work/` = 241 個檔案），
> `work/UltimateAudit/` 從 `c3af9fe`（2026-10-16 03:01「把對帳工具換成會自我檢查的那一支」）就在裡面。
> 缺陷不在「沒入版控」，而在**「沒有任何東西會自動跑它」**：沒有 CI、沒有腳本、測試也不引用它，
> 「每 25 項跑一次」只存在於這份文件的規定裡，靠人記得。
>
> 這正是本輪在修的那種病，而我當場又踩了一次：**把兩件不同的事混成一句好聽的結論**
> （§3.1 的「引擎壞掉」、§4.2 的「+31 vs 18」是同型）。
> `commit 4042b80` 的提交訊息沿用了同一個錯字；依「不改寫已發佈的歷史」的慣例，
> **留在原地、在這裡更正**——錯的訊息被更正過，比被抹掉更值钱。

`README` §六自己規定「每 25 項跑一次 `work/UltimateAudit` 與專案的守門測試」。
工具在版控裡，**但「跑」這個動作只存在於規定裡**。後果在這一輪具體發生：本目錄長出第 11 份檔案
（`STAGE-02-REMAINING-KEYS.md`）之後，它**連跑都跑不動**，而且三個缺陷疊在一起：

| # | 缺陷 | 症狀 |
|---|---|---|
| 1 | 自我檢查寫死「底下有 **10** 份階段檔」 | 數到 11 份 → 自我檢查失敗 → **直接結束、不產出結論** |
| 2 | 階段檔用 `STAGE-{nn}-*.md` ＋ `.Single()` | 階段二的 glob 命中兩個檔 → `Sequence contains more than one element` 拋例外 |
| 3 | `IsItemId` 寫死長度 6 | `P10-001`（7 字元）永遠不是 ID——自我檢查只測 6 字元的例子，所以看不出來 |

**這三個缺陷沒有一個會讓任何測試變紅**，因為這支工具不在任何會自動跑的地方。
這就是「靠守門不靠記性」這條原則的漏洞：**守門自己也要有人守**。

**修法＝搬進測試**（會自動跑的地方）：新增 `Tests/PlanLibraryTests.cs`（55 條），把檢查變成會被跑的東西：

1. 十階段各 105 列、ID 互異、編號連續；
2. 檔頭宣稱（「**本階段 105 項（…）**」）＝矩陣列數；
3. 域碼表宣告項數＝矩陣列數；
4. **逐域比對「這一塊的輸出鍵前綴屬於該域」**——這一條原本沒有，抓的是「合計相同但錯位」（P1-① 那型）；
5. 依賴欄只寫 ID、指得到、跨階段引用必須明示「參照」；
6. 輸出鍵前綴必須在該階段域碼表宣告內；
7. **稽核工具的自我檢查**（見第三節）。

`work/UltimateAudit` 留著當離線的細部探針（它有逐項清單輸出），但**閘門的憑據以測試為準**；
`README` 那一節改成指向 `Tests/PlanLibraryTests.cs`。

## 三、真正的缺陷②：一個被寫進永久紀錄的誤診

`README`（計畫庫）與 `FIX-REPORT` 都寫著同一句話：

> 「**這台機器上兩個不同的正則引擎都對這種樣式給出錯誤答案**」——`[A-Z]+\d?` 對 `"F10"` 回 `false`。

**那是誤診，而且比原本的樣式錯更貴。** `\d?` 只允許**一位**數字，而 `F10` 有兩位——
回 `false` 正是它該做的事。兩個引擎實測（2026-10-18）：

```
Python 3.11.9：  re.fullmatch(r'[A-Z]+\d?', 'F10')                → None   ← 正確
.NET 10：        Regex.IsMatch("F10", "^[A-Z]+\\d?$")              → False  ← 一致且正確
同一個樣式換成：  re.fullmatch(r'[A-Z]+\d*', 'F10')                → 命中   ← 域碼真正的形狀
```

所以病是「用猜的樣式去認實際有兩位數字的域碼」（以及那個把預期寫成 `true` 的探針），
不是引擎。**接受「引擎壞掉」這個更好聽的解釋的代價是：這台機器上明明能用的工具被寫成不可信。**
誤診的代價不是這一次數錯，是下一次有人不敢再相信一個會動的守門。

修法三處：`README` 那一段改寫（附上面那組實測）、`FIX-REPORT` §3.1 加第二次更正、
**並在計畫庫的自我檢查裡釘住**：

```csharp
Assert.False(Regex.IsMatch("F10", @"^[A-Z]+\d?$"),
    "F10 有兩位數字，而 \\d? 只允許一位——這裡的 false 是對的；會壞的是那個樣式，不是引擎");
```

## 四、真正的缺陷③：畫面上被覆寫，所以沒有人發現它舊了的字面值

`MainWindow.xaml` 與 `Views/AboutView.xaml` 各寫死一次 `"XinSpect v2.5 Olympus"`，
而程式在執行期會用 `AppInfo` 覆寫它們。於是：

- 使用者看不到舊字串 → **沒有任何回饋**；
- 編譯器不管字串內容；
- 既有的守門驗的是「版號的六處來源」，不包含 XAML 的屬性值。

結果是那兩個字面值一路落後三十幾個版本。修法：XAML 不寫版號（理由移到 code-behind
與守門的註解裡），並新增 `ChangelogTests.檢視的XAML不得留下舊版號`——
**允許寫、但寫了必須是當前版號**（只掃屬性值，不掃註解：註解裡的 `v2.60` 是「這個功能是哪一版做的」，
那是歷史，不是現在式）。

## 五、順手修掉：第 263 輪自己引進的警告

第 263 輪的行為面測試用 `Task.Run(...).Wait(9000)` 包逾時（用意是「實作若壞掉，紅燈會說話而不是卡死」），
但那讓測試專案多一條 `xUnit1031`（不要在測試方法裡阻塞等待）。改成
`await Task.Run(...).WaitAsync(9000ms)` ＋ `catch (TimeoutException)`：**語意相同、不再是阻塞等待**
——而「阻塞等一個不回來的呼叫」正是那一組守門要防的形狀，所以分析器這次說得對。
