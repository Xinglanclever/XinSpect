# 極致計畫・階段一｜地基與契約

> **規格庫，不是開工指令**：圈了 ID 才開工；接縫不到 API 級不許開工。
> **計數紀律**：只有「新增能力」或「收口」才算一項；重複、只做一半、純聲明不計。
> **本階段 105 項（P1-001–P1-105）**，域碼 10 個。前置：無（本階段的 Gate 是全計畫的第一前提）。
> 五原則與三態誠實不變；完整九欄只給 ★ 錨點，其餘為矩陣列，圈選後補九欄才可開工。

---

## 一、階段定位

階段一不產生任何新的事實。它產生的是**其他九個階段用來不彼此漂移的那組契約**：一個掃描骨架、一套可用性狀態、一條出處鏈、一個知識包格式、一層匿名化、五種守門、一條審計鏈、一份鍵目錄、一套錯誤處理、一條發布線。

之所以把它排在第一，是因為專案已經用一次代價換到這個結論：**沒有契約時，每個域都會各自長出一套狀態定義、一套識別方式與一份自己的「關於其他元件的說明」，而這些東西只會漂移，不會報錯。**同一件事四套命名空間的教訓（白皮書第六十二章）不是設計失誤，是缺這一階段的必然結果。

本階段的另一個性質是：**它無法被「先做一半」**。狀態型別收斂、鍵目錄全集、審計鏈頭尾、守門五模式，任一項只做一半，後面的階段都會長出替代品。因此階段一的 Gate 比其他階段嚴格。

## 二、完美判準（Gate）

本階段完成，若且唯若下列條款**逐條可機器驗收**成立：

1. **單一可用性型別**：全專案不得再有第二套列舉或字串常數集表達事實可用性；由原始碼掃描守門（P1-013）。
2. **狀態判定時序**：任何來源實作皆「先讀取、後判可用性」；反序即紅燈，並有正對照證明該守門會紅（P1-019、P1-061）。
3. **出處強制**：每個公開解碼方法具備規格出處註記，且位移級出處不得只寫到規格層級；未對準出處時輸出狀態而非值（P1-023、P1-025、P1-029）。
4. **鍵目錄雙向相等**：目錄 ≡ 原始碼掃描，且殭屍前綴（登記無生產）為零（P1-078、P1-080）。
5. **覆蓋申報分母成文**：分母的定義與豁免門檻寫在文件內，並有測試斷言其與實作一致（P1-081、P1-082）。
6. **寫入單一入口**：全專案寫入僅經一個閘門，逐筆可查；審計鏈頭可脫離應用程式獨立驗證（P1-067、P1-070）。
7. **L3 禁項釘死**：機密類欄位在顯示與匯出兩條路徑皆被守門擋住，且該守門有正對照（P1-048）。
8. **守門模式宣告**：每個新增守門都宣告五模式之一與其防範的真實風險；無理由者不加（P1-055）。
9. **文件數字可重跑**：白皮書與文件中的統計數字由產生器產生，重跑可比對（P1-105）。
10. **發布可驗證**：單檔發佈、資產雜湊與驗證腳本、測試基線三者與程式碼同步（P1-096、P1-099、P1-100）。

## 四、完整規格（九欄）

### ★ P1-001｜唯讀掃描骨架統一介面

**目標**：讓所有來源以同一種順序被讀取（發現→讀取→解碼→三態→鍵），且任何暫態必定還原。

**接縫**：`interface IReadOnlyScanner { string BackendName { get; } FactSet Scan(); }`；新域服務一律實作本介面，既有服務逐一套用（P1-012）。

**方法**：`Scan()` 內部固定序；每步可宣告超時上界（P1-002）；所有暫態（含 SuperIO 進出序列）以 `finally` 還原（P1-003）；中斷時保留已得事實（P1-004）。

**輸出鍵**：介面本身不產鍵；骨架的觀測以 `scan.skeleton.adoption`（既有服務採納數）、`scan.partial.count`（中斷時保留的事實數）呈現。

**三態行為**：來源不可用 → `Refused`（骨架自帶的來源狀態，不冒充 `NotApplicable`）；步驟逾時 → `ReadError` 並附步驟名；來源可用但零筆 → `NotApplicable`。

**誠實界線**：骨架不負責判斷事實的**意義**，只負責順序與還原；骨架不允許寫入，寫入必經閘門（P1-067）。

**守門**：掃描守門（模式：介面契約）——所有實作 `IReadOnlyScanner` 的類別不得出現寫入 API；正對照：臨時加入一個呼叫寫入 API 的假掃描器，須紅燈。

**依賴**：無（本階段第一項）。

**驗收**：全部公開掃描器通過介面契約守門；`scan.skeleton.adoption` 與實際採納清單一致；未施測者以聲明列出。

### ★ P1-083｜執行期註冊對帳（目錄≡原始碼≡執行期）

**目標**：把「有生產、目錄沒登記」與「目錄有登記、執行期沒註冊」兩類靜默缺口同時變成紅燈。

**接縫**：事實產生的唯一入口（`EvidenceCollection.LoadUsermodeFacts` 一族）＋ `FactKeyCatalog` ＋ `CoverageService.ScanFactKeysFromSource`。

**方法**：以測試在行程內執行一次完整載入，收集執行期實際註冊的鍵集合；與目錄全集、原始碼掃描結果三方比對，逐鍵輸出三個集合的差集。

**輸出鍵**：`coverage.threeway.count`（三方一致鍵數）、`coverage.threeway.diff`（不一致項清單，含來源側）。

**三態行為**：三方一致 → `Present`；任一側集合為空（載入失敗）→ `ReadError`（不得當成「一致」）；目錄有而執行期無 → 差異項，非錯誤。

**誠實界線**：本項只證明「鍵有被註冊」，不證明「鍵會被使用者看到」；後者需要呈現層的另一組對帳，屬階段九。

**守門**：完整性網（模式：接線／孤兒／對帳）；等級宣告：擋得住「未註冊」，擋不住「註冊了但沒有呈現路徑」。

**依賴**：P1-077（鍵目錄編譯期全集）、P1-078（雙向守門）。

**驗收**：三方差集為零或與豁免清單逐項對應；刻意移除一條載入呼叫時，測試須紅燈並指名該鍵。

## 六、誠實界線與明文不做

**不做**：階段一不做任何硬體讀取。它沒有辦法用「圖上有東西」來證明自己，只能靠守門與對帳——這是它的弱點，也是它必須排第一的原因。

**明文不做（附理由與解除條件）**：

| 不做 | 理由 | 解除條件 |
|---|---|---|
| 通用外掛框架 | 外掛＝第二份真相的入口，與整合優先衝突 | 若出現第三方需獨立擴充且無法合併進主線的需求，重新評估 |
| 執行期可改寫的鍵目錄 | 目錄必須編譯期固定，否則發佈版掃描失敗會被讀為全覆蓋 | 若發佈形態改為含原始碼（例如以指令碼發佈） |
| 自動上傳匿名統計 | 與零上傳原則衝突 | 無（屬產品立場，非技術選擇） |
| 覆蓋率門檻 | 強制全覆蓋會逼出湊數規則 | 無 |
| 分散式／雲端版本 | 與免安裝、零常駐衝突 | 無 |

**本階段沒有證明的事**：Gate 條款證明的是「契約成立」，不是「功能可用」。契約成立而功能為零，是本階段唯一允許的完成狀態。

## 七、階段出口

通過 Gate 後，階段一交付三件可對帳的東西：**一份介面契約（骨架、狀態、出處、知識包、匿名化）**、**一套守門（五模式、正對照、等級宣告）**、**一條發布線（單檔、雜湊、基線、認證）**。階段二至十的每一項，開工的第一步都是引用這三件。
