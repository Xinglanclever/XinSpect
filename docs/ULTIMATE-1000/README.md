## 一、這份計畫的性質

本計畫是 `docs/INDUSTRIAL-CATALOG-2026-10-10.md`（VOL1，300 項）與 `docs/INDUSTRIAL-CATALOG-VOL2-2026-10-11.md`（VOL2，300 項）之後的**第三組：極致組（ULTIMATE-1000）**，共 **1,050 項**，分為十個階段，每階段一份檔案。

三條承襲自專案既有文化的規則，先講在最前面：

**第一，這是規格庫，不是開工指令。**圈了 ID 才開工；沒圈的只是候選。每一項開工前必須把「接縫」欄補到 API 級，補不到的（檢索級／推測級）如實標註，不出半成品。

**第二，計數紀律不變。**一項只有在兩種情形才算一項：**新增能力**（原本讀不到的東西現在讀得到）或**收口**（能力早就在，但規格要求的輸出鍵或陳述沒落地，本輪把鍵落地並加測試）。重複做既有服務、只做一半、純聲明，三者一律不計。查重方法：先搜尋既有 ID 與來源關鍵字，再看 `Services/` 有沒有人做過同一件事。

**第三，五原則與三態誠實不變。**唯讀優先、零上傳、白名單最小化、免安裝、零常駐；讀不到一律標六態（`Present`／`NotApplicable`／`NotSupported`／`InsufficientPrivilege`／`Unknown`／`ReadError`），不以 0 或典型值填補。

## 二、「完美」在本計畫的定義（十條判準）

「無敵」不是無所不能。一份宣稱無所不能的清單，只要第一項站不住，整份就失去價值。本計畫對「盡善盡美」採用一個可被指令檢驗的定義：

> **完美＝沒有可被指出的空話。**任何一句「已支援」都能被重跑驗證；任何一句「不支援」都附理由與解除條件。

十條判準，每一條都在既有專案裡有對應的機制：

| # | 判準 | 既有機制 |
|---|---|---|
| 1 | **可讀必讀** | 範圍內沒有「還沒做」的藉口；「前提不存在」與「能力缺口」必須分開陳述（調度准入三條件） |
| 2 | **讀不到必說** | 六態可用性契約與狀態格；一次失敗不得被講成「不適用」 |
| 3 | **說了必有出處** | 每個解碼方法帶規格出處註記，未對準出處就不出值 |
| 4 | **錯了必紅燈** | 守門五模式；突變測試、正對照實驗；靜默失效視為缺陷 |
| 5 | **做了必可對帳** | 鍵目錄與原始碼逐鍵相等；覆蓋申報；目錄／執行期註冊／申報三方對帳 |
| 6 | **寫入必經閘門** | 讀取自由、寫入必經寫入閘門；一切寫入記帳並進審計鏈 |
| 7 | **敏感必分級** | L0–L3 逐欄標註；L3 禁項由測試機器釘死，任何功能不得輸出 |
| 8 | **不懂必留白** | 未施測聲明；檢索級／推測級如實標註；不以推測的位移硬做 |
| 9 | **重複必消滅** | 整合優先、調度最後；單一真相；登記表只能是整合的副產物 |
| 10 | **界線必成文** | 明文不做清單，附理由與解除條件；被否決的路徑必須被記錄 |

每一階段檔的「完美判準（Gate）」一節，就是把這十條在該階段**具體化為可驗收的條款**。Gate 未過，該階段不視為完成，也不進入下一階段。

## 三點五、對帳（2026-10-16，兩輪稽核的合併結論）

### 第一輪的結論：兩個計數指控，只有一個是真的

第一輪以 30 個 agent 稽核本計畫，得出兩條 P0：

| 指控 | 複核結果 |
|---|---|
| 「階段 2 只數到 102、階段 3 與 7 只數到 103，所以 **1,050 是錯的**」 | **不成立**。十階段各 105 列、合計 1,050 個互異 ID、編號連續、跨階段引用全部可解析。 |
| 「大膽區『不計入承諾』卻被算進 105」 | **成立**，但報告給的數字（「扣掉就變 99」）也是錯的；實情見下。 |

誤報的來源後來查清楚了，而且比「正則寫錯」更值得記：稽核腳本用
`[A-Z]+\d?` 這種「**字元類別 ＋ 量詞**」的樣式認域碼（`F10`、`SEC`、`TPM`），
而**這台機器上兩個不同的正則引擎都對這種樣式給出錯誤答案**：

```
Python 3.11.9：  re.fullmatch(r'[A-Z]+', 'A1')      → False（應為 False，但 'F10' 也變 False）
.NET 10：        Regex.IsMatch("F10", "^[A-Z]+\\d?$") → False（應為 True）
兩者一致：        Regex.IsMatch("P10-001", "^P\\d{1,2}-\\d{3}$") → True
```

也就是說：**認 ID 的樣式是好的，認域碼的樣式是壞的**——於是階段一的 F10 一整列
認不出來（宣告變成 95 而非 105），而矩陣列數一直數對。工具壞掉被讀成文件壞掉。

### 第二輪：真的缺陷與它的修法

任一項不符即以離開碼 2 結束、不產出結論。它找到並已修完的是：

| 缺陷 | 條數 | 修法 |
|---|---:|---|
| 階段一域碼表**少了 F10 那一列**（表上只剩 F1–F9、合計仍寫 105） | 1 | 補回該列；合計 12+10+10+12+10+12+10+10+9+10 = 105 |

| 依賴欄不是 ID 也不是佔位字（`L3 禁項`） | 5 | 改為 `P1-048（L3 禁項掃描守門）` |

## 四、每一階段檔的固定結構

每一份階段檔都由五節構成，順序固定，以便逐檔比對：

1. **階段定位**——這一階段解決什麼問題、以及它為什麼排在這個位置。
2. **完美判準（Gate）**——本階段可機器驗收的完成條件，逐條寫成可檢查的敘述。
3. **域碼與項數**——本階段的域碼表，含項數、主要輸出前綴、敏感度上限。
4. **完整規格（九欄）**——P0 錨點項目，九欄齊備（目標／接縫／方法／輸出鍵／三態行為／誠實界線／守門／依賴／驗收）。**只有錨點寫滿九欄**；矩陣列在圈選後補九欄才可開工，這是 VOL1／VOL2 的既有慣例。
5. **矩陣**——本階段全部項目的清單（ID／名稱／目標一句／輸出鍵／敏感度／成本／依賴）。
6. **誠實界線與明文不做**——本階段不做什麼、為什麼、以及解除條件。

## 五、推進節奏與成本單位

**成本**：S ≤ 0.5 輪｜M = 1 輪｜L = 2–3 輪｜XL ≥ 4 輪。一輪＝一次發佈迭代（現行 v2.x 節奏）。

**推進節奏**（2026-10-16 修訂，取代原本的「每 10 項跑套件、累計 50 項動版本」）：

| 節點 | 動作 | 為什麼是這個密度 |
|---|---|---|
| 每 **10 項** | 跑一次套件（前景，紅的當場修） | 一個 `[Fact]` 平均 10 行，10 項約 100 行；這是「一次看得完的 diff」的上限 |
| 每 **25 項** | 一次**閘門檢查**：跑 `work/UltimateAudit` 與專案的守門測試，產出一份可貼進帳本的紀錄 | 25 項＝矩陣的四分之一個域群；足以看出「這一區的命名與依賴有沒有漂」，又不必等到整階段 |
| 每 **100 項** | **發一次版本**：動版本號、變更記錄、測試基線與三份 README 徽章 | 版本是對外的承諾單位；1,050 項若每 25 項都發版會產生 42 個版本，把沿革撐爆且失去意義 |

**閘門紀錄格式**（每個 25 項節點產出一份，貼進 `docs/PROGRESS-PLAN-2026-10-11.md` 的推進紀錄）：
改了哪些檔、跑了什麼、離開碼多少、以及**這一輪新增的未修項計數**。格式由
`work/UltimateAudit` 自動產生（`work/ULTIMATE-GATE-RECORD.md`），不手寫。

**為什麼不手寫**：本計畫吃過一次虧——帳本裡「測試 +31」與實跑「+29」對不上，
而那個數字是**推算**出來的。紀錄要能對帳，就得由會跑的東西產生。

**階段 Gate**：階段內全部 P0 與 P1 項通過其守門，且該階段的 Gate 條款逐條成立，才視為完成。Gate 是階段之間的唯一通行證。

**敏感度**：L0 硬體／版本（預設輸出）；L1 本機元數據（匯出遮蔽）；L2 安全相關（匯出預設遮蔽、可選解除）；L3 禁項（任何功能不得輸出，測試釘死）。矩陣的「敏感度」欄記的是**該項輸出鍵的最高等級**。

## 六、與既有 VOL1／VOL2 的關係

本計畫與既有 600 項**不是相加的兩份清單**，而是同一條推進線上的兩段：

- **不重複**：凡 VOL1／VOL2 已列的能力，本計畫不另立一項；若本計畫的規格比既有條目更完整（例如既有只有一句目標，本計畫補上輸出鍵與三態），則該項在計數上算**收口**，並在矩陣的「依賴」欄註明既有 ID。
- **合併分母**：對外陳述推進進度時，分母為 600 + 1,050 = **1,650 候選項**；但有效累計一律以「新增或收口」為準，不以名目相加（見推進計畫 §六的計數紀律）。
- **前置關係**：既有 600 項中已完成的 40 項，是本計畫階段一至階段三的直接前置；「部分覆蓋」的 123 項，是本計畫優先收口的獵物。

## 七、十階段的為什麼是這十個

階段劃分不是按功能領域切，而是按**能力成熟的順序**切：先有契約（否則每個域都會各自長出一套狀態定義），再有可讀的硬體（否則上面全是空殼），再能保證資料可信（儲存與完整性），再擴到網路與作業系統（把機器放回環境裡），再處理安全與取證（需要前五階段的事實當證據），再做量測科學（量測需要穩定的平台與可重現的環境），再做平台化（把事實交到使用者手上），最後才談企業級與研究級（它們需要前面九階段全部成立）。

次序的意義在於：**任何一階段跳過，後面的階段都會長出重複的、彼此漂移的替代品。**這正是本專案已經吃過一次的虧（同一件事四套命名空間，見白皮書第六十二章）。

## 八、給不同讀者的入口

- **評估可行性**：讀階段一的 Gate、階段三與階段四的矩陣、階段十的明文不做。
- **找單一功能**：用全庫搜尋 ID（`P3-042`）或搜尋輸出鍵前綴（`st.nvme.`）。
- **接手實作**：讀階段一的完整規格九欄，再看目標階段的第一節與 Gate。
- **質疑本計畫**：讀每個階段的第六節（誠實界線與明文不做）與階段十的關係矩陣——這份計畫最需要被攻擊的地方都寫在那裡。
