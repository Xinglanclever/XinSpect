# WP-A45 ・ 規則引擎（**最優先**）

> **理由：它決定「別人能不能擴充你的法」。優先於其餘三項。**

## 現況

- `Services/FactRelationEngine.cs`（317 行）＋ **25 條規則寫死**
- 有 `ConsistencyRule` 抽象，但**沒有外部載入機制**

## 目標

把 25 條規則**外部化**，並提供可分享的規則格式。

## 範圍

| 產出 | 內容 |
|---|---|
| `Models/RuleDefinition.cs` | 規則的資料模型（id／severity／來源／目標／條件／訊息） |
| `Services/RuleLoader.cs` | 從 YAML／JSON 載入規則 |
| `Services/RuleValidator.cs` | **載入時驗證**：每條規則必須有 `SpecRef`、必須宣告誤報條件 |
| `Services/RuleExplainer.cs` | **規則要能解釋自己**（顯示：為什麼觸發、依據哪個規格、什麼情況會誤報） |
| `Rules/builtin.yaml` | **現有 25 條全部轉成 YAML**（不得遺漏一條） |
| `Tests/RuleEngineTests.cs` | 載入／驗證／解釋／衝突處理 |

## 硬性要求

1. **YAML 與現有 25 條行為必須完全等價** —— 寫一個測試對照兩者輸出，**逐條比對**。
2. **每條規則必須宣告「什麼情況下會誤報」** —— 答不出來的規則視為不合格。
3. **規則必須可解釋**：`RuleExplainer` 能輸出「為什麼這條被觸發」＋「依據的規格」。
4. **衝突處理要明確定義**：兩條規則對同一事實給出不同判決時，行為必須有定義且可測。
5. **不做規則市集**（那是後續，需要簽章與網路；本輪只做本機載入與驗證）。

## 明確不做

- ❌ 不下載遠端規則（需要簽章、網路、信任模型 —— 另立 WP）
- ❌ 不改動現有 25 條的**判決邏輯**（只搬位置）
- ❌ 不碰 `FactRelationEngine` 的公開介面（只加載入層）

## 驗收（V7 第 18.2 節六項）

1. 純解碼器／純邏輯 ＋ 完整單測（紅→綠）
2. 讀不到有對應三態 ＋ 原因
3. **`SpecRef` 齊全**
4. **有非自造的驗證來源**（＝用現有 25 條規則的實際輸出當黃金答案，逐條比對）
5. **Property test ＋ Mutation score 達標**
6. 全套測試綠 ＋ Release build 綠

## 範圍

| 產出 | 內容 |
|---|---|
| `Services/FactQuery.cs` | 查詢的資料模型 |
| `Services/QueryParser.cs` | 解析（**語法要簡單到五頁能講完**） |
| `Services/QueryExecutor.cs` | 對 `FactStore`／快照執行 |
| `Tests/QueryTests.cs` | 解析／執行／錯誤處理 |

## 能力（依 V7 A44）

1. **事實查詢** —— 依類別／來源／可用性篩選
2. **可組合管線** —— 上一個查詢的結果餵給下一個
3. **跨機器查詢** —— 對多台機器的快照同時查
4. **時間軸查詢** —— 依時間範圍查（接 `HistoryStore`）

## 硬性要求

1. **語法必須簡單** —— 目標：**一個不懂程式的使用者能在 5 分鐘內寫出第一個查詢**。
2. **查不到 ≠ 沒有** —— 要區分「沒有這個事實」與「事實存在但讀不到」（接三態）。
3. **絕不猜** —— 查詢不得回傳推估值。

## 明確不做

- ❌ 不做 SQL（太複雜，違反「五頁能講完」）
- ❌ 不做跨機器**寫入**
- ❌ 不碰 `FactAvailability` 的定義

# WP-A18 ・ 帶外管理（**受限：只能做純解碼器**）

## 現實

```
這台機器：無 BMC、無 IPMI 裝置
```

> **所以本 WP 只做「不需要硬體的部分」——純解碼器 ＋ 明確的未施測聲明。**

## 可做（純解碼器，可用合成資料驗證）

| 產出 | 內容 | SpecRef |
|---|---|---|
| `Models/IpmiMessage.cs` | IPMI 2.0 訊息結構 | IPMI 2.0 spec |
| `Services/IpmiDecoder.cs` | **SEL 事件解碼**、**FRU 解碼**、**SDR 解碼** | IPMI 2.0 §31／§38 |
| `Services/RedfishSchemaDecoder.cs` | Redfish 回應的**結構解碼** | Redfish Schema |
| `Tests/IpmiDecoderTests.cs` | **合成向量**（依 spec 手算的黃金答案） | — |

## 不可做（誠實界線）

| ❌ | 為什麼 |
|---|---|
| **不做 KCS 埠存取**（`0xCA2`/`0xCA3`） | 沒有 BMC，**無法驗證** |
| **不做 SSIF／SMBus BMC 通訊** | 同上 |
| **不做 NCSI** | 同上 |
| **不宣稱「支援 IPMI」** | 只能宣稱「支援 IPMI 訊息解碼」 |

## 硬性要求

1. **UI 必須明確聲明「本機無 BMC，未施測」** —— 比照 Rowhammer 那條誠實聲明。
2. **解碼器只吃位元組緩衝，不碰匯流排** —— 這樣才能在沒有 BMC 的機器上被驗證。
3. **合成向量必須依 spec 手算** —— 不得用「我自己算的」當黃金答案。
4. **`FactAvailability = NotApplicable`**（無 BMC）與 `NotSupported`（有 BMC 但功能未實作）**必須分開**。

## 驗收

- 純解碼器單測齊全 ✅
- SpecRef 齊全 ✅
- 合成向量有獨立依據 ✅
- **UI 有「未施測」聲明 ✅** ← 這一項是重點
