# 二手驗機・矛盾稽核 ・ 設計（2026-09-04）

## 一、這是什麼，以及刻意不是什麼

**是**：把曦覽已經讀到的硬體事實**互相對帳**，把彼此矛盾的地方擺出來並附證據。

**不是**：不給分數、不給「✅ 正品」、不下「這台是翻新機」的結論。工具負責把矛盾指出來，
判斷留給人——賣家可能有正當理由，而一個綠勾會讓使用者停止思考。

判定只有三種，沿用全站共用的 `Severity`：

| 判定 | Severity | 意義 |
|---|---|---|
| 相符 | `Good` | 兩邊事實一致 |
| 矛盾 | `Warning` / `Critical` | 兩邊對不上，附證據對照 |
| 讀不到 | `Neutral` | 缺其中一邊的事實，**不猜** |

「讀不到」必須跟「相符」一樣顯眼。二手驗機的情境裡，「這台機器讀不到 SMART」本身
就是資訊——不能靜靜地當作通過。

## 二、架構

沿用專案既有的三層分工（`PlatformTrustDecoder`／`CeilingDecoder`／`PcieLinkDecoder` 那族）：

```
VerifyFactsCollector   取值：把每個事實連同它的血統一起收集（不含 ViewModel 參照）
        │  VerifyFacts：Dictionary<FactId, VerifyFact>，可序列化
        ▼
VerifyRules            判斷：規則宣告它依賴哪些 FactId；引擎先查依賴是否齊全
        │  VerifyFinding[]（編號／標題／判定／Severity／證據鏈）
        ▼
VerifyService          呈現：依部件分組成 ObservableCollection
        ▼
VerifyView             UI：每筆矛盾把對帳的各邊並排，逐邊可展開看讀取方法
```

**規則不自己處理「讀不到」。** 每條規則宣告 `RequiredFacts`，引擎在跑規則前先檢查，
缺哪一個就直接產出「無法判定：缺 〈事實名〉（需要 〈權限〉）」。這樣「讀不到」永遠說得出
缺的是哪一邊、以及要怎樣才讀得到，而規則本體只剩下純粹的比對邏輯——好寫也好測。

`VerifyFacts` 從第一天就是純資料（無 ViewModel 參照、可序列化），C（變更稽核）接手時
只要加存檔與差異比對，不必回頭改資料模型。但**本輪不寫持久化、不定 schema 版本**。

## 三、資料模型

事實帶完整血統。這是整份設計的核心決定：**畫面上每一個數字都必須說得出自己是怎麼來的**。

```csharp
public enum VerifyVerdict { Match, Conflict, Unread }

public enum FactSource { Cpuid, Msr, Smbios, AtaIdentify, SmartAttr, NvmeLog, Edid, PciConfig, Wmi, Derived }
public enum FactTrust  { Native, FirmwareReported, Derived }
//   Native            = 直接問矽晶片／控制器（CPUID、MSR、IOCTL 原始回傳）
//   FirmwareReported  = 經韌體或驅動轉譯（SMBIOS、WMI）——韌體可以說謊，這點必須標出來
//   Derived           = 由其他事實推導

public sealed record VerifyFact(
    FactId Id,
    string Label,
    string Value,            // 已格式化，給人看
    double? Numeric,         // 給規則做算術；無數值意義時為 null
    string Unit,
    FactSource Source,
    string Method,           // "CPUID leaf 0x16 EAX" / "MSR 0xCE bits 15:8" / "SMBIOS Type 17 +0x15"
    bool NeedsAdmin,
    FactTrust Trust,
    DateTime ReadAt);

public sealed record VerifyFinding(
    string Id, string Part, string Title,
    VerifyVerdict Verdict, Severity Severity,
    string Explanation,          // 為什麼這是矛盾
    string? BenignCause,         // 可能的正當成因——沒有這一欄就是在誘導使用者殺價
    VerifyFact[] Evidence);
```

`Numeric` 與 `Value` 分家，是因為規則要做算術而人要看格式化字串；把格式化過的字串再
解析回數字是這類程式最常見的爛法，也違背「值只讀一次、來源只有一個」的原則。


規則表的形狀與 `DeviceIcons` 的徽章表一致：一條規則一列、由上而下逐條跑（規則之間互不
遮蔽，全部都跑），新增規則＝加一列＋加一個測試樣本。

## 四、規則表（第一版）

「資料現況」欄標明這條規則今天能不能跑：**現成**＝服務已曝露所需數值；
**要曝露**＝服務內部已讀到但只給了顯示字串，需補型別化欄位（見第五節）。

### 處理器

| 編號 | 規則 | 對帳的兩邊 | 資料現況 |
|---|---|---|---|
| R-CPU-01 | 品牌字串宣稱的世代 vs CPUID family/model 對應的微架構 | 品牌字串 ／ CPUID 1.EAX | 要新增對照表 |
| R-CPU-02 | 工程樣品跡象：字串含 ES／QS／`Genuine Intel CPU 0000`，或微碼版本為 0 | 品牌字串 ／ 微碼版本 | 現成 |
| R-CPU-03 | 快取層級異常：L3 為 0；**非**混合架構時另檢查 L2 總量與核心數是否成整數倍 | CPUID 4／0x8000001D ／ 拓撲核心數 | 要曝露 |
| R-CPU-04 | Hypervisor 存在 → 標注「以下讀值在虛擬環境中不可信」 | CPUID 0x40000000 | 現成 |
| R-CPU-05 | **最大非睿頻倍頻 × BCLK 與品牌字串宣稱的基礎頻率不符** | MSR 0xCE bits 15:8 ／ 品牌字串 | 要新增（MSR） |
| R-CPU-06 | 逐核微碼版本不一致（正常機器全核同版） | MSR 0x8B 逐核 ／ 自身比對 | 要新增（MSR） |

R-CPU-05 是抓打磨改標最硬的一條：**改標改得了外殼與品牌字串，改不了矽晶片裡的倍頻上限**。
`PLATFORM_INFO` 的最大非睿頻倍頻是燒在晶片裡的，乘上實測 BCLK 就是這顆的真實基礎頻率；
與品牌字串宣稱的對不上，只有兩種可能：改標，或這是工程樣品。

| R-SSD-04 | NVMe 關鍵警告位元非零 | NVMe Log 0x02 bit 0–5 | 現成 |
| R-SSD-05 | 宣稱容量與實際可定址容量對不上（假容量碟嫌疑） | 型號字串 ／ ATA IDENTIFY word 100–103 或 NVMe NSZE | 要新增（IDENTIFY） |
| R-SSD-06 | 宣稱轉速與屬性集矛盾（貼牌：說 SSD 卻有機械屬性，或反之） | IDENTIFY word 217 旋轉速率 ／ SMART 屬性集 ／ ACS 版本 | 要新增（IDENTIFY） |

### 鏈路・電池・年齡

| 編號 | 規則 | 對帳的兩邊 | 資料現況 |
|---|---|---|---|
| R-LNK-01 | 現行 PCIe 鏈路寬度／速度低於裝置能力 | Link Status ／ Link Capability | 要曝露（已算出，未給列） |
| R-BAT-01 | 滿充容量相對設計容量的衰退 | DesignCapacity ／ FullCapacity | 現成 |
| R-AGE-01 | 各部件年齡互相矛盾（BIOS 日期／OS 安裝／磁碟通電小時／螢幕製造年） | 四邊互比 | 螢幕那邊要曝露 |

共 20 條。R-AGE-01 是唯一一條「多邊對帳」，也是最能抓到拼裝機的一條：主機板 BIOS
日期 2019、SSD 通電三小時、螢幕製造 2016 年——每一項單獨看都正常。

**混合架構的陷阱**：Alder Lake 之後 P 核與 E 核的 L2 容量不同，「L2 總量 ÷ 核心數」
在混合架構上必然不成整數倍。R-CPU-03 因此先判斷是否為混合架構（CPUID 0x1A），
是的話只檢查 L3 為 0 這一項。這條規則寫鬆一點會在正常機器上狂報矛盾。

**分兩批落地**（避免一個 PR 塞 20 條規則）：

- 第一批 11 條：記憶體 4 ＋ 儲存 6 ＋ 電池 1。價值最高（翻新碟與混批記憶體是二手市場
  最常見的兩件事），依賴第五節的第 1、2 項改動。
- 第二批 9 條：處理器 6 ＋ 鏈路 1 ＋ 年齡 1 ＋ 顯示器 1。依賴第 3–6 項改動，
  其中微架構對照表是純資料，可獨立先做。


## 五、要動的既有服務與新增的讀取器

採用**資料深度層級二**：純使用者態上限 ＋ 已驗證打通的 MSR。層級三（SMBus 直讀 SPD）與
層級四（VBIOS 校驗）延後獨立一輪，理由見第九節。

### 5-0. 硬性前提：所有磁碟 IOCTL 都必須有逾時看門狗

**這一條是實測換來的，不是預防性設計。** 2026-09-04 在本機傾印基準檔時，一支列舉
`PhysicalDrive 0–7` 的測試程式卡在某顆碟的 IOCTL 裡沒有回來；那個程序**連提權後的
`taskkill /F` 與 `Process.Kill()` 都殺不掉**（回「存取被拒」＝卡在核心模式的不可中斷 I/O），
並且一路握著測試組件的檔案鎖，直到重開機為止。

同一組同步 IOCTL 就是現有儲存頁與 `MachineAgeService` 在用的，所以那不是測試專屬的風險：
**在這台機器上，按一下儲存頁的「讀取」就有機會把 XinSpect 凍成殺不掉的程序**——不是崩潰、
不是錯誤訊息，是整個程式停住而工作管理員也結束不了。

因此本輪新增與改動的每一個磁碟讀取器都必須：

1. IOCTL 一律跑在背景執行緒（`Task.Run`），呼叫端以逾時等待（單顆碟 3 秒為上限）。
2. 逾時就回 `null`，並讓事實層產出「讀不到」，訊息要指出**是哪一顆碟沒回應**。
3. 逾時後**不重試、不換路徑**——卡住的那條 I/O 還在核心裡，再發一次只是多卡一條。
4. 逐碟獨立：一顆碟沒回應不得影響其餘碟的讀取結果。
5. 現有的 `StorageSmartService.ReadSelected`／`TryReadPowerOnHours` 與 `MachineAgeService`
   的逐碟掃描一併套用同一個看門狗——它們今天就有這個風險。

> 這條要求也改變了任務順序：**看門狗讀取器要先做，再用它去傾印真實基準檔**，
> 不能反過來。

### 5-1. 其餘改動

1. **`StorageSmartService`**：`SmartRow` 增加 `RawValue`（`ulong?`）；NVMe 健康記錄的已解析
   數值（通電小時、寫入單位、通電次數、不安全關機、已用壽命）以型別化屬性曝露。
   目前只有 `RawText` 顯示字串——規則要做算術，不該把格式化過的字串再解析回數字。
2. **新增 ATA IDENTIFY 讀取器**（`IOCTL_ATA_PASS_THROUGH`，256 words 全解）：真實 LBA 總數
   （word 100–103）、標稱旋轉速率（word 217）、ACS 版本、支援功能位元、韌體版本與序號。
   NVMe 走 `IOCTL_STORAGE_QUERY_PROPERTY` 的 Identify Controller／Namespace 取 NSZE／TNVMCAP。
   這是 R-SSD-05／06 的唯一可靠來源，也是「假容量碟」目前能做到的最強讀取層證據。
3. **新增 MSR 讀取**（走既有 `WinRing0Bridge`，路徑已驗證）：`0xCE PLATFORM_INFO`
   取最大非睿頻倍頻與 TDP 可調旗標；`0x8B` 逐核微碼版本（需綁核親和性逐核讀，
   `CpuAffinity` 已有）。**只讀不寫**，且失敗即回「讀不到」，不重試、不繞路。
4. **`EdidService`**：解 EDID 標頭 0x08–0x11（製造商 PNP ID、產品碼、序號、製造週／年），
   位元組已經在讀了（色域用），只是沒解這幾格。同時保留原始 128 bytes 供傾印。
5. **`CpuIdService`**：曝露型別化的快取容量（位元組）、family／model／stepping 數值、
   以及 CPUID 0x1A 的混合架構旗標。
6. **`PcieLinkService`**：把內部已算出的 `curSpeed/curWidth/maxSpeed/maxWidth` 以列的形式曝露。
7. **新增純資料對照表**：CPUID family/model → 微架構世代（給 R-CPU-01），可枚舉、可測試。

第 2、3 項是新增硬體存取，其餘五項都是「把已經讀到的東西誠實地曝露出來」。


## 六、介面

新增主頁面「驗機稽核」，經 `Nav/PageRegistry.cs` 宣告式註冊（自動被 `UiSmokeTests` 涵蓋）。

版面：頂部一句話狀態（例如「17 條規則：5 相符、3 矛盾、9 讀不到」——**數字不加總成分數**），
下面依部件分組的卡片。每一筆矛盾展開後是並排的兩欄證據，各自標來源：

```
⚠ 通電小時與總寫入量對不上                                    R-SSD-01
   通電 42 小時（SMART 0x09）｜ 已寫入 8.7 TB（NVMe Data Units Written）
   42 小時寫進 8.7 TB 等於平均 207 GB/小時，遠超消費級碟的持續寫入能力。
   常見成因：SMART 曾被歸零，或這顆碟先前在別的機器上長期使用。
```

「讀不到」的那幾條照樣列出，並寫明**缺哪一邊**（例如「需要管理員權限才能下 SMART 指令」），
不折疊、不淡化。匯出沿用既有 `ReportService`，輸出純文字，可直接貼給賣家。

## 七、測試

**基準用真實硬體的原始位元組（golden fixtures），不用合成資料驗正確性。**
這一條是針對 1.9.1-B1 的教訓：那次 NVMe 健康記錄的位移錯誤帶了三個發佈版沒被抓到，
正因為測試資料是照著錯誤的實作位移合成出來的——測試把 bug 鎖死了。所以：

- 每個新解碼器（ATA IDENTIFY、EDID 標頭、NVMe Identify、SMBIOS 既有路徑）都先從本機
  把原始位元組傾印成 `Tests/Fixtures/*.bin`，測試斷言「這串真實位元組應解出這些值」。
  傾印檔要註明機型與讀取日期；含序號的欄位在入庫前遮成固定樣式（`XXXX`），
  但**位移與長度保持原樣**，否則就失去了驗證位移的意義。
- 合成資料只用來造邊界情況（全 0、全 F、溢位、欄位缺失），不用來驗正確位移。
- 每條規則至少三個測試：相符、矛盾、缺一邊（→ 讀不到，且訊息要指出缺哪一個 FactId）。
- 整表不變式（照 `DeviceIconsTableTests` 的作法）：編號唯一、每條規則都有測試樣本、
  每條規則的 `RequiredFacts` 都存在於 `FactId` 列舉、每條規則在某組合成事實下確實會回
  「矛盾」（防止寫出一條永遠不觸發的死規則）。
- 門檻值全部寫成具名常數並在測試中引用，不允許魔術數字散在判斷式裡。


## 八、刻意不做（YAGNI）

- 不做分數、不做「正品／翻新」結論、不做綠勾。
- 不做使用者可編輯的規則。
- 不做雲端比對（送機器指紋去伺服器比對群體資料）——那與本專案的隱私立場衝突。
- 不做快照持久化（那是 C 的工作，只保證資料模型不擋路）。

## 九、延後一輪的深度（不是做不到，是要單獨的安全設計）

| 項目 | 能換到什麼 | 為什麼延後 |
|---|---|---|
| SMBus 直讀 SPD（層級三） | 記憶體生產週、完整 512 bytes SPD、真實 XMP／EXPO profile——二手記憶體的混批／翻新／貼牌全靠這個 | SMBus 是共享匯流排。讀取時若與 CPU-Z、AIDA64、廠商燈光軟體搶匯流排，可能造成短暫停頓甚至需重開機。要先做匯流排讓與、逾時、失敗即放棄，並在介面上要求使用者關閉其他監控軟體。DDR5 走 SPD5 hub，協定與 DDR4 不同要另寫 |
| VBIOS 傾印與校驗（層級四） | 比對 ROM 內的裝置 ID／子系統 ID 與實際回報是否一致 → 抓刷過 BIOS 的顯卡 | 工作量最大，且「礦卡」沒有單一可靠判準，只能給線索不能給結論 |

## 十、現階段真的做不到，因此在頁面上明列為「未檢查」

| 想做的 | 為什麼不做 |
|---|---|
| 假容量碟的確證 | 唯一的鐵證是寫滿再讀回校驗（h2testw 那套），那是破壞性操作。讀取層只能給「宣稱容量與可定址容量不符」這種嫌疑 |
| 面板實際使用時數 | EDID 沒有這一欄；只有廠商 OSD 或專用協定才有 |
| CPU 型號 → 應有核心數／快取 的完整規格對照 | 需要一份型號規格資料庫，維護成本高於價值。R-CPU-05 用矽晶片裡的倍頻上限取代了它的大部分用途 |

這幾項在頁面上以「本工具未檢查的項目」明列——使用者要知道**沒被檢查的是什麼**，
否則「沒有矛盾」會被誤讀成「全部檢查過都沒問題」。


## 十一、風險

1. **誤判的代價不對稱**：一條寫太鬆的規則會讓正常機器出現「矛盾」，使用者可能因此殺掉一筆
   正當交易。故所有門檻取保守值，寧可漏判也不誤判，並在說明裡寫出「常見的正當成因」
   （`VerifyFinding.BenignCause` 是必填而非選填，就是為了逼自己每條都想過這件事）。
2. **權限落差**：SMART、NVMe 記錄、ATA IDENTIFY 與 MSR 都需要管理員權限。無管理員時整組
   儲存與處理器規則會變成「讀不到」，頁面必須說清楚缺的是哪一項權限與取得方式，
   不能只顯示一片「—」。
3. **ATA pass-through 的相容性**：部分 USB 外接盒與 RAID 控制器不轉送 ATA 指令，會回失敗或
   回一整片 0。全 0 的 IDENTIFY 必須判為「讀不到」，**絕不可解讀成「旋轉速率 0＝SSD」**——
   那正是這類程式最容易產生假結論的地方。
4. **磁碟 IOCTL 會卡死整個程序**：見 5-0 節的實測記錄。這是本輪最高等級的風險，
   因為它的表現不是錯誤而是凍結，使用者只會覺得「這程式壞了」。所有讀取一律走看門狗。
4. **MSR 逐核讀取要綁核**：`0x8B` 必須在目標核心上執行才有意義，需經 `CpuAffinity` 綁核並
   在結束後還原；綁核失敗就整條規則回「讀不到」，不要退而讀當前核心冒充逐核結果。
5. **虛擬機**：R-CPU-04 命中時，MSR 與 CPUID 的讀值可能是 hypervisor 合成的，其餘規則的
   可信度整體下降，頁面頂部要有一條橫幅說明，而非逐條加註。
6. **矛盾不等於造假**：整個功能的說明文字都不得暗示賣家有惡意。混批記憶體可能是使用者自己
   後來加的，通電小時低而寫入量高可能是原主換過主機板。工具的職責到「指出對不上」為止。
