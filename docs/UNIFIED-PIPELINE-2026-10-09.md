# 統一管線重寫：整合為正，調度為最後手段

> 2026-10-09。對象＝主藍圖 §1.2「事實 → 規則 → 判決 → 行動 統一管線」（P0 地基）。
> 本文＝研究結果 ＋ 重寫後的設計；**尚未動任何程式碼**。
> 基準：`main` @ `f5e6d32`，專案測試 3527 綠。

---

## 一、研究結果：四套的真實狀態

藍圖寫「事實層、對帳、政策、機隊是四套」。實際讀程式碼之後，實情比這句話更具體——**問題不只是四個子系統，而是同一件事有四套命名空間**。

| # | 層 | 代表型別／檔案 | ID 命名空間 | 實例 | 與其他層的關係 |
|---|---|---|---|---|---|
| 1 | 事實層 | `HardwareFact`（`Services/*.cs`，56 個生產者） | `key`（字串） | `spi.frap`、`board.serial` | 管線的貨幣 |
| 2 | 驗機對帳 | `FactId` enum ＋ `VerifyRules`／`CpuIdVerifyFacts`／`PcieVerifyFacts` | `FactId.*`（enum） | `FactId.DimmCount`、`FactId.CpuBrandString` | **與 #1 無對應關係** |
| 3 | 政策／評分 | `SecurityFinding.Id`（`Services/BlueSquadron/`） | 字串（另一套語法） | `kernel.hvci-off`、`dma.iommu` | **`BlueSquadron/*.cs` 對 `HardwareFact` 的引用數＝0** |
| 4 | 機隊 | —— | —— | —— | **未實作**（`Services/` 內 `fleet`／`機隊` 命中數＝0，屬 P1 路線圖） |

另外三處實測到的分歧：

1. **組裝有三條路徑、兩套鍵名。** `FirmwareSecurityRows`（27 組，`42108ed` 起已由 `AllFacts` 派生）、`LoadPlatformFacts`、以及 `Collect(vm)` 那條（用的是 `system.*`／`board.*`／`gpu.*` 命名，與 `spi.frap` 系併存）。`42108ed` 收掉的是其中一組重複，不是這三條的收斂。
2. **對帳有兩份實作。** 內建 `FactRelationRules.All`（26 條，生產路徑）與 `Rules/builtin.json`（26 條，未出貨），兩者行為等價由測試保證——亦即**同一套規則要改兩次，而其中一份使用者拿不到**。
3. **政策散在三個服務。** `BlueSquadron/PolicyEngine`、`AuditPolicyService`、`PowerPolicyService` 各自讀自己的來源，沒有一個共同介面把它們接進事實層。

**這解釋了為什麼 v2.36 那個缺陷會發生、而且只有發佈版才看得出來**：覆蓋申報要回答「哪些事實被規則碰到了」，但「事實」在 #1 是字串鍵、在 #2 是 enum、在 #3 是另一套字串——申報只能靠掃原始碼去猜，猜不到就說謊。**這不是單一 bug，是沒有統一管線的症狀。**

## 二、原則：為什麼整合優先、調度是最後手段

**調度的意思是**：四個子系統保持各自獨立，在中間加一層協調者，把東西路由過去（登記表、轉接器、中介層都算）。
**整合的意思是**：讓它們不再是四套——一份事實型別、一個產生入口、一條管線。

選整合的理由不是潔癖，是**風險的形狀**：

- **調度把漂移制度化。** 只要你保留兩份實作、中間靠一層東西對齊，那層東西就必須「知道兩邊長什麼樣」——於是它成為第三份需要維護的真相。本專案已經吃過這個虧：v2.36 的申報之所以說謊，正是因為它得從外部推斷事實層的內容；`42108ed` 收掉的 27 個複製 `Concat` 是同一個病的另一個器官。
- **調度的失效方式是靜默的。** 兩份實作漂移時，沒有任何一處會報錯；整合的失效方式是編譯錯誤。這個專案對「靜默失效」的容忍度是零（三態原則、誠實界線、突變測試都是為了這一點）。
- **整合讓新增功能自動變強**，這正是藍圖 §1.2 期待的效益；調度只讓新增功能自動變**複雜**。

**什麼情況才算「整合真的不可行」**（三個條件要**同時**成立，才准退到調度）：

1. 那份真相**不屬於本專案**（例如外部工具輸出、第三方格式），本專案無法擁有它；
2. 而且它**沒有公開規格**可以照著重寫（有規格就該寫成純解碼器，那不是不可行）；
3. 而且它**必須在執行期取得**（不能離線轉成事實）。

三者缺一，就該走整合。這條判準要寫進 Help／文件，否則「不可行」會變成每個人都能自己定義的藉口。

## 三、重寫後的設計

### 3.1 一句話

**事實只有一個型別、一個產生入口；對帳、驗機、政策、機隊都是這條管線上的消費者，不是平行系統。**

### 3.2 具體到本專案的程式碼

| 現在 | 重寫後 |
|---|---|
| `HardwareFact`／`FactId`／`SecurityFinding.Id` 三套命名 | **一個鍵命名空間**：`HardwareFact.key` 為唯一識別；其他層若需要枚舉，由鍵**推導**（而不是各寫一份 enum） |
| 三個組裝路徑（兩種鍵名） | **一份事實組裝宣告**：所有生產者回傳的事實直接進同一條管線 |
| 對帳 26 條 × 2 份實作 | **一份規則來源**；外部形式若保留，必須是同一份的**產物**（生成，而非手抄） |
| 驗機用 `FactId` 列舉所需事實 | 驗機規則改為**宣告它需要哪些鍵**，缺鍵即三態（不另立一套 ID） |
| 政策三個服務各自讀 | 政策是**事實的消費者**：吃同一批事實、吐判決，接進判決層 |
| 機隊不存在 | 機隊是**同一批事實的離線差分**——不需要新模型，只需要事實的序列化 |

### 3.3 關於「登記表」：它與整合其實不必二選一

先前的討論把它們當成兩條路（登記表 vs 四套合一）。讀完程式碼後我的判斷是：**只要登記的動作發生在唯一的事實產生函式裡面，它就不是調度，而是整合的一部分。**

差別在於誰擁有那份清單：

- **調度式的登記表**：事實由 56 個服務各自產生，另外有一份「誰產生哪些鍵」的表在中間對齊 → 表會漂移，因為它是第二份真相。
- **整合式的登記**：事實只能經由**唯一入口**產生，鍵在那一刻由型別系統記下 → 沒有第二份真相可以漂移。

所以「執行期登記」這個方向可以保留，但**它必須是整合的副產物，不能是整合的替代品**。這是本文與先前討論最主要的差別，也是我建議的落點。

### 3.4 驗收標準（可機器驗證，符合本專案既有文化）

1. **新增一個事實生產者時，只改一處**：它自動出現在對帳、驗機、查詢、報告四處。
2. **不存在第二套 ID**：`Services/` 內不得再有列舉事實識別的 enum 或字串常數集；由測試掃描守門（比照 `FactKeyCatalogTests` 的既有作法）。
3. **規則只有一份真相**：外部形式若存在，必須由內建那份生成，並有測試斷言兩者逐條相同（而不是靠人工維護再比對）。
4. **管線入口只有一個**：測試斷言事實產生的唯一路徑；任何新服務若繞過它即紅燈。

## 四、調度（最低優先級）：什麼時候才用、怎麼防止它漂移

**只有在第二節那三個條件同時成立時**才准用，並且必須附上：

- **一份「為什麼整合不可行」的書面理由**（對照三個條件逐條說明）；
- **失效可見性**：調度層的任何對不上都必須產生**畫面上的訊息**，不得靜默（v2.36 的教訓）；
- **不得手抄**：能生成的對照一律生成。

本專案目前**沒有任何一項**符合這三個條件：機隊是自己要實作的、驗機與政策都是自己的、對帳規則有規格可依。所以按這條判準，**現在應該零調度**。

## 五、切片順序（每一片獨立可驗收）

| 片 | 內容 | 為什麼在這個位置 | 風險 |
|---|---|---|---|
| **S1** | 驗機的 `FactId` enum 改為引用 `HardwareFact.key` | 四套裡最獨立、觸及面最小；做完立刻少一套 ID | 低（有既有測試覆蓋驗機） |
| **S2** | 事實組裝收斂成一份宣告（三條路徑 → 一） | 管線的地基；`42108ed` 已證明可行且值得 | 中 |
| **S3** | 對帳規則單一真相（外部形式改為生成物） | 收掉「同一套規則改兩次」 | 低 |
| **S4** | 政策（`PolicyEngine`／稽核／電源）改吃事實、吐判決 | 接上判決層 | 中 |
| **S5** | 機隊＝事實的離線差分 | 最後一片，因為它需要 S1–S4 的穩定鍵 | 低（無既有包袱） |

**建議從 S1 開始**：它是唯一一片「做完之後，某一個 ID 命名空間就再也不存在」的切片，效果可量測，而且不必先動 56 個生產者。

## 六、界線

- 本文是**設計**，沒有動任何程式碼；測試仍是 3527 綠（與本文無關，只是基準）。
- 「四套」中**機隊尚未實作**，所以第四套不是「要整合的既有系統」，而是「照新模型長出來的新東西」——這一點與藍圖的措辭略有差異。
- 本文沒有評估工作量天數；切片順序是**依風險與可驗收性**排的，不是依工時。
