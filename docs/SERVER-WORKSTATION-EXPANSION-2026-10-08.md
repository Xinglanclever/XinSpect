## 第一梯 — v2.32：伺服器與工作站視角

### 1. 虛擬化平台三態（元件／服務／虛擬層）

**問題**：Windows 從不把「Hyper-V 到底在不在跑」放在一個地方。CPUID 說的是有沒有虛擬層、選用功能說的是元件裝了沒、服務狀態說的是管理服務起了沒——**這三件事可以任意組合**，而一般工具把它們壓成一句「Hyper-V：已啟用／停用」。

**本機正是最容易講錯的那個狀態**：裝了、服務開著、但虛擬層沒載入——不會有 VM 能跑、不佔記憶體與 CPU，但 vmms 服務、驅動與其攻擊面是開著的。

判讀分四種處境：全關（裸機，MSR／TSC 讀值原生）／裝了未載入／被 VBS 拉起／真正在跑 VM。並明說**虛擬層不是只有 Hyper-V 會拉起來**——VBS、WSL2、容器都會。

- 解碼器：`VirtualizationJudge.cs`
- 服務層：`VirtualizationFactsService.cs`
- 關鍵地雷：`Msvm_ComputerSystem` 的「主機自己那一筆」在**繁中系統上 Caption 是「主機電腦系統」**，只比對英文字串 "Hosting" 會把主機算成一台 VM

### 2. 網卡鏈路落差（PCIe 供給 vs 線路速率）

**問題**：一張 PCIe 網卡同時受兩個上限約束。只報一個「1 Gbps」等於什麼都沒說——看不出是插槽只給 x1、是接在 1G 交換器上、還是驅動被鎖住。

**本機有兩個獨立的落差**：PCIe 側 8 GT/s **x2** 而能力 x4（插槽走線）；線路側 **1 Gbps** 而驅動回報支援到 10 Gbps（線材或對端）。

- **頻寬換算扣掉線路編碼**：8b/10b 用於 2.5／5.0 GT/s、128b/130b 用於 8.0 GT/s 以上。漏扣會高估 25%（Gen1／Gen2）
- 供給不足時明說「**這條線路跑不滿**」——那是真實的效能上限，不是顯示問題
- 解碼器：`NicLinkGap.cs`；服務層：`NicLinkFactsService.cs`
- WMI 地雷：類別名是 `MSFT_NetAdapterHardwareInfoSettingData`（不是 `...HardwareInfo`），速度欄位是 `*SpeedEncoded`（已是速度代碼）

### 3. 顯示轉接器真偽（真實 vs 軟體 vs 基本顯示驅動）

Windows 把三種東西一起列在「顯示卡」底下：真實 GPU、模擬器／遠端桌面裝的虛擬轉接器、沒有廠商驅動時頂上的微軟基本顯示驅動。

判準以 **PnP 識別碼的匯流排來源**為主（`PCI VEN_` vs `ROOT`），驅動有沒有回報視訊處理器與廠商字串為輔。

**本機是「1 張真實顯示卡 ＋ 3 個軟體顯示轉接器」**——後者不是硬體，不應計入顯示卡張數。

- 解碼器：`DisplayAdapterJudge.cs`；服務層：`DisplayAdapterFactsService.cs`

### 4. 記憶體錯誤更正三層分離

「伺服器記憶體」在印象裡是一個整體，實際上是**三個獨立屬性**，在 SMBIOS 裡也是三組不同欄位：

| 層次 | 欄位 | 意義 |
|---|---|---|
| 模組匯流排寬度 | Type 17 位移 0x0C／0x0D | 總寬 72 vs 資料寬 64 ＝ 有沒有 ECC 位元 |
| 模組型態 | Type 17 位移 0x15 bits 1:0 | Registered（RDIMM）／Unbuffered（UDIMM） |
| 平台更正能力 | Type 16 位移 0x06 | 整個陣列的錯誤更正類型 |

**混著講就會出現「有 ECC 所以是伺服器記憶體」這種錯**——ECC UDIMM 的工作站與 RDIMM 的伺服器，在寬度那一欄看不出差別，在型態那一欄才分得開。

**本機實況：`TotalWidth=72`（模組帶 ECC 位元）但平台回報「無」——兩欄對不上**，判讀明說不一致而不是靜靜挑一個講。

- 解碼器：`DimmEccJudge.cs`

### 5. SMBIOS 表補完（Type 1／3／28／29）

三個容易讀錯的地方：

- **Type 1 UUID**：前三個欄位是**小端序**，照位元組順序印會得到看起來正確但其實錯的 UUID。全 0（未編程）與全 F（不支援）如實區分
- **Type 3 機箱類型**：直接回答「這是不是機架式／伺服器」——韌體自己宣告的，不必從外觀猜。本機是「桌上型（Desktop）」
- **Type 28／29 感測器**：值欄位的 **bit 15 是「值未知」**，當成數值會讀出 3276.8 °C 這種荒謬值或看起來正常但其實沒量到的 0.0 °C。本機那兩個溫度探針與三個冷卻裝置的 `CurrentReading` 都是空的，如實顯示「值未知，感測器未回報」

**韌體未填的預設字串**（「Default string」「To be filled by O.E.M.」）如實顯示原字串並加註——直接照登會讓人以為那是序號，靜默改掉又會隱藏「韌體沒填」這個事實。

## 第二梯 — v2.33：兩處「數一數就好」其實都會算錯

### 6. 記憶體通道配置

理論頻寬上限的計算前提是「每支模組各佔一個通道」，而**這個前提可以被插槽配置推翻，方向還不一樣**：

| 配置 | 上限值 | 實測 | 該怎麼看 |
|---|---|---|---|
| 每通道 1 支 | 基準 | 基準 | 多通道平台最理想的插法 |
| **同通道掛 2 支** | **不變** | 通常偏低 | 容量優先的取捨，達成率偏低是**預期中**不是故障 |
| **全部擠同一個通道** | **不變** | 掉到接近單通道 | 這才是真的插錯，頻寬少一半 |

過去只寫一句「假設每支各佔一個通道」，卻沒有能力檢查它站不站得住。現在分三種陳述：假設成立／不成立（並說明偏低是預期的）／無法驗證。

**本機是四條各一支、四通道各一條 → 假設成立**；但兩種模組型號混插（`ZhuQue_8G_Y` 與 `ZJ-4000-C18-8G-RWMC`），判讀同時提醒型號不同會讓時序退到共同的最低標準。

- 解碼器：`MemoryChannelJudge.cs`；整合點：`DimmLayout.cs`、`MemBandwidthService.cs`

### 7. 螢幕組成

Windows 的顯示器清單混了三種東西，設定畫面全都顯示成「一台螢幕」：

- **接了線的真實螢幕** —— EDID 帶製造商代碼、產品名稱、製造年週
- **軟體虛擬螢幕** —— 虛擬顯示驅動／模擬器／遠端桌面合成的最小 EDID
- **作業系統的預設監視器物件** —— 後面沒有實體裝置

**本機是 1 台真實螢幕（`MTT` / `VDD by MTT` / 2024 年）＋ 3 個預設監視器物件（`DesktopMonitor1／2／4`，沒有 PNPDeviceID）**。

**本判讀不指名是哪一套虛擬顯示軟體**——只陳述欄位證據。猜錯的代價比不猜高，軟體名稱留給「顯示轉接器」那一區對照。

- 解碼器：`MonitorJudge.cs`；服務層：`MonitorFactsService.cs`
- WMI 地雷：`WmiMonitorID` 的 EDID 字串是 **`ushort[]`**，直接轉字串得到 `"System.UInt16[]"`

## 第三梯 — v2.34：佇列深度曲線與 NUMA 的誠實界線

### 8. IOCP 佇列深度（QD）曲線判讀

**問題**：同一顆 SSD 在 QD1 與 QD32 的 IOPS 可以差一個數量級，只報一個數字等於沒說。

判讀指出曲線屬於三種形狀中的哪一種：

| 形狀 | 意義 | 該做什麼 |
|---|---|---|
| 每級明顯上升 | 本次條件下還有餘裕 | 要找到實用上限需要更高的 QD |
| 某級之後不再上升 | **該點就是本次條件下的實用上限** | 再加深只會拉長延遲 |
| 加深反而下降 | SLC 快取用盡／過熱降速／驅動排程的形狀 | 值得查（看連續寫入曲線與溫度） |

**最重要的一句寫進證據欄**：延遲隨 QD 上升是排隊的必然結果（QD ＝ IOPS × 延遲），**不是故障**——該注意的是 IOPS 有沒有明顯趨緩。同時給出「QD1 對上最高 QD 差幾倍」，因為 **QD1 才接近日常體感**。

- 解碼器：`StorageQdJudge.cs`；整合點：`StorageIocpEngineService.cs`（判讀附在結果的 Limitations）

### 9. NUMA 跨節點：本機標「未驗證不代表可用」

**本機是單插槽，`GetNumaHighestNodeNumber` 回 0——跨節點延遲與頻寬無從量測。**

照使用者指示做成「**不適用**」而不是「正常」，並明說：

> **未驗證不代表可用——沒量到不等於沒有問題。**

把「沒量到」寫成「正常」會讓閱讀者以為已經驗過了，而這正是驗機報告最不該犯的錯。這張卡片對本機沒用，但對將來拿去驗雙路伺服器有用，而且它不會假裝驗過了。

## 第四梯 — v2.35：專業音訊、識別資產、角色攻擊面

### 10. 音訊端點緩衝區（延遲下限）

對每個輸出端點**實際配置一次**獨占模式與共用模式。那個值才是端點的延遲下限——只讀格式而不嘗試配置是問不出來的，因為 **Windows 沒有「這個端點能跑多小」的查詢 API**。

延遲等級依用途分四級（同一個數字在「看影片」與「邊聽邊彈」下意義完全不同）：

| 獨占模式緩衝區 | 等級 |
|---|---|
| < 10 ms | 可做即時監聽（邊聽邊演奏不干擾） |
| 10–20 ms | 低延遲（單向錄音可行） |
| 20–40 ms | 一般用途（即時監聽不適合） |
| > 40 ms | 只適合播放 |

兩個容易講錯的地方：

- **要求值被裝置夾住是常態**。要求 1 ms 常配到 21 ms 或 80 ms——那是裝置能提供的最小週期，**不是應用程式選的**
- **共用模式那個值由引擎決定、所有應用程式共享**，不能拿來當延遲指標

**本機實況**：Realtek 數位輸出與 VB-Audio／UUYC 虛擬端點都是 21.3 ms，Steam Streaming 的兩個端點是 80.0 ms，要求值全部是 1 ms。

- 解碼器：`AudioLatencyJudge.cs`；服務層：`AudioLatencyFactsService.cs`
- 安全性：只呼叫 `Initialize` 取得緩衝區大小後立刻 `Dispose`，**不呼叫 Start**——不送出任何音訊、不佔用裝置

### 11. 識別與資產

SMBIOS 識別欄位與機箱類型，並標出哪些是**韌體未填的預設字串**。

**把它們當序號登錄，資產清單上就會出現一堆一樣的值，序號欄位形同虛設。** 本區如實顯示原字串並加註，給出替代方案（磁碟序號、網卡 MAC、自訂編號）但**不代為選擇、也不補一個看起來合理的值**。

**本機實況**：系統序號「System Serial Number」、機箱序號與資產標籤都是「Default string」（全部未填），**只有主機板序號 `181242565700856` 有實際值**。

- 解碼器：`AssetJudge.cs`；服務層：`AssetFactsService.cs`

### 12. 已安裝角色與功能的攻擊面

裝了的角色佔三樣成本：磁碟空間、開機與維護時間，以及**可被利用的程式碼面積**。

判讀分開陳述：裝了什麼、哪些屬於伺服器角色類、服務跑著還是停著，並明說：

> **「服務沒在跑」不等於「不會跑」**——服務可由相依關係、RPC 呼叫或觸發條件被拉起來。

**不建議移除任何項目**：哪一個角色對這台機器有用只有使用者知道，一台檔案伺服器的 File Server 角色是它的用途，不是多餘。

- 解碼器：`RoleSurfaceJudge.cs`；服務層：`RoleSurfaceFactsService.cs`

### 13. IPMI／MegaRAID／Redfish 解碼器納入 SpecRef 覆蓋

三個既有的純解碼器（`IpmiDecoder` SEL／FRU／SDR、`MegaRaidDecoder` MFI 訊框、`RedfishSchemaDecoder` 信封）納入機器檢查的規格引用覆蓋。

**本機沒有對應硬體可驗證，維持「只支援訊息解碼、不宣稱支援通路」的既有界線**——這是誠實契約，不是缺漏。

### 14. 大頁與工作集

**這一項在提議時就已存在**（`LargePageService` 在記憶體頁），A／B 兩次指標追逐、只有頁面大小是變數，顯示大頁單位、鎖定記憶體權限、能否配置、兩種頁的每次存取延遲。**沒有重做**——重複實作已存在的功能是浪費，也違背「只寫真的做了的事」。

## 誠實界線總表（每一條都有測試釘住）

| 界線 | 內容 |
|---|---|
| 上游讀不到 | 標「未判定」，**不當成「上游沒有限制」** |
| 支援速率清單讀不到 | 不當成「已達最高」 |
| 感測器值未知 | 不當成 0，也不讀出 3276.8 °C |
| ECC 寬度讀不到 | 不當成 64，不講成「沒有 ECC」 |
| VBS 狀態讀不到 | 不當成關閉 |
| 虛擬介面 | 不套用 PCIe 結論 |
| 跨節點（單節點機） | 標「不適用」，並明說**未驗證不代表可用** |
| 服務沒在跑 | 明說**不等於不會跑** |
| 音訊配不出來 | 如實標示，不推測它的延遲 |
| 判讀不得寫入 | 每個判讀類別都有「公開介面不得出現 Set／Write／Enable」的測試 |
| 對外發佈 | 不代為選擇替代識別欄位、不建議移除角色、不改任何設定 |

## 未做與刻意不做

| 項目 | 原因 |
|---|---|
| **PCIe 主動重協商**（設 Target Link Speed ＋ Retrain） | 會動到正在運作的鏈路。全專案硬體存取以唯讀為原則，跨這條線是產品方向的決定。**v2.31 只做了唯讀的落差判讀** |
| **Redfish** | 要網路連線，與零網路 API 原則衝突 |
| **IPMI 通道（KCS 0xCA2／0xCA3）** | 本機沒有 BMC 可驗證，出了貨也只是「未施測」 |
| **RAID 帶外管理** | 理由同上 |
| **ECC 錯誤注入** | 要硬體支援，且會刻意製造錯誤，違反唯讀原則 |
| **大頁與工作集（重做）** | 已存在（`LargePageService`），重複實作是浪費 |
