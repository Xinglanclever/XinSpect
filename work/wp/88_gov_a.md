# 第八部　規格庫與治理文件

本文前七部說明的是**已實作**的系統。第八部處理另一類材料：專案在推進過程中累積的**判定文件**——功能目錄、能力域判定、管線決策、接線守門與計數帳本。這些文件不是設計說明，而是**決策的證據與其形狀**；它們在同一個專案裡承擔的作用，與程式碼中的測試相當：把「我們怎麼決定」變成可複核、可對帳、可追問的東西。

之所以值得專章說明，是因為本專案的一項實際教訓：**判定文件如果不被機器對帳，就會與程式碼分離，而分離之後它們不會報錯，只會安靜地變成錯的。**這一部記錄的就是防止這件事的幾種機制，以及它們實際擋住過什麼。

## 第五十九章　規格庫的工程契約

### 59.1 規格庫與開工指令的分離

專案在 2026-10-10 至 10-11 之間把候選功能收斂為兩份目錄：第一組（VOL1）300 項與第二組（VOL2）300 項，合計 600 項，全部以工業級規格撰寫，存放於 `docs/INDUSTRIAL-CATALOG-2026-10-10.md` 與 `docs/INDUSTRIAL-CATALOG-VOL2-2026-10-11.md`。

這兩份文件的第一條規則就是它們的性質宣告：**本文件是規格庫，不是開工指令；圈了 ID 才開工，沒圈的只是候選。**這條規則解決的是一個真實的組織問題——一份寫得夠細的候選清單，很容易被讀成一份承諾清單。分離這兩者之後，候選項目可以在規格上被反覆修改而不產生「已經說要做」的暗示，而已圈選的項目則必須在開工前把規格補到可實作的精度。

### 59.2 域碼與項數

VOL1 以域碼分組，共 300 項，其中包含 GP（遊戲呈現）4 項；域碼涵蓋韌體與開機鏈（FW，25）、CPU 與記憶體（CM，20）、儲存（ST，20）、網路與周邊（NW，22）、安全審計（SA，20）、可靠性考古（RC，16）、證據與工作流（EV，20）、UX 與工程品質（UX，18）、策略與工程（EG，30）等。VOL2 另立 **27 個新域**，同樣 300 項，包含 ACPI 與 AML 深化（AC，18）、SMBIOS 與 PCIe 表深化（SB，15）、GPU 深化（GX，14）、伺服器角色（SV，14）、檔案鑑識（FS，16）等。

VOL2 的域碼設計有一個值得指出的差異：FS（檔案鑑識）與 DL（開發者診斷）被**明文標記為 L2 鑑識域、預設 opt-in**。這不是普通的優先級標註，而是把「這個域的功能若預設執行，會踩到什麼線」寫進了目錄本身（見 24.2 的出網與敏感度政策）。目錄因此不只是功能清單，也是敏感度的登記處。

### 59.3 九欄契約

P0 與 P1 等級的項目必須具備完整九欄，缺一欄即不達開工精度：

1. **目標**——回答什麼問題（一句話）。
2. **接縫**——具體的 API、檔案或表。
3. **方法**——讀什麼、怎麼讀、重試與放棄條件。
4. **輸出鍵**——事實鍵命名與值的形狀（須進鍵目錄對帳）。
5. **三態行為**——六態各自的觸發條件。
6. **誠實界線**——不做什麼、為什麼。「是事實非判決」類的聲明逐條成文。
7. **守門**——測試級的防回歸機制（見 59.7 的守門五模式，至少一種）。
8. **依賴**——共用骨架、知識表、其他項目。
9. **驗收**——fixture 金標全綠加實機記錄，或未施測聲明。

九欄的精神與本文第三章的事實模型一致：**一個功能在被實作之前，就必須回答「它的輸出是什麼形狀、讀不到時怎麼說、以及誰來防止它退化」。**把這三件事延後到實作階段決定，正是專案過去產生缺陷的主要來源。

### 59.4 接縫必須到 API 級

第二欄「接縫」附帶一條硬性條件：**不到 API 級不許開工**。規格若只能寫到「讀取某個登錄機碼」而不確定是 `RegQueryValueEx` 還是 WMI 類別，或是只知道「應該有這個指標」而不知道確切位移與位寬，該項目就必須留在候選狀態，並如實標註其證據等級為檢索級或推測級。

這條規則有一則具體的先例：專案的 PCH 世代判定曾因「規格只寫到晶片組型號、寫不到可讀的暫存器」而被主動裁決不做，而不是以推測的位移硬做一個半成品。**寧缺勿錯**在此處的具體含義是：一個會輸出錯誤值的功能，比一個明文標示未實作的功能更糟，因為前者會進入使用者的判讀流程。

### 59.5 成本、敏感度與優先級

**成本**以「輪」為單位（S ≤ 0.5 輪、M 1 輪、L 2–3 輪、XL ≥ 4 輪），一輪即一次發佈迭代，對應專案現行的 v2.x 節奏。這是把工作量錨定在可觀測的交付單位上，而不是人日估算。

**敏感度**分四級，並且是匿名化層的直接輸入：

- **L0** 硬體與版本類——預設輸出。
- **L1** 本機元數據（路徑、行程名、埠）——匯出時遮蔽。
- **L2** 安全相關（帳戶、憑證存在性、審計、監聽面）——匯出預設遮蔽、可選擇解除。
- **L3** 禁項（密碼、金鑰、修復金鑰的**值**）——**任何功能不得輸出**，並由測試機器釘死。

L3 的處理方式是本文第二十四章所述資料主權政策的規格化版本：它不只規定「不要輸出」，而是規定「由機器確認沒有任何功能輸出」，因此禁項是掃描守門的對象而非撰寫者的自律。

### 59.6 Trace 模型與機器對帳

專案採用航空級的四級追溯模型：`REQ-{ID}`（目錄條目）→ `DESIGN`（服務或解碼器檔名）→ `TEST`（測試名）→ `VERIFIED`（實機記錄或未施測聲明）。

四級之中最重要的是第四級的可空缺性：**允許沒有實機記錄，但不允許「沒有說自己沒有」。**未施測必須是一條明文的聲明，而不是留白。

除此之外，目錄還被一條機器對帳規則釘住：**規格聲稱的每一個輸出鍵，都必須在鍵目錄中有帳。**這是既有 `DocumentationIntegrityTests` 模式的擴大應用，其意義在目錄中被直接寫成一句話——「**規格與程式說謊一樣會紅燈**」。本文第十章說明過靜態鍵全集必須編譯期固定，原因是發佈版掃不到原始碼；這條對帳規則補上了另一半：不僅程式碼不能有未登記的鍵，**規格也不能承諾不存在的鍵**。

### 59.7 橫切框架七件

目錄定義了七個橫切元件，所有新域都必須套用：

| 代號 | 元件 | 強制內容 |
|---|---|---|
| F1 | 唯讀掃描骨架 `IReadOnlyScanner` | 固定內部序（發現→讀取→解碼→三態→鍵）；`finally` 還原任何暫態；每步超時上界；中斷時保留已得事實 |
| F2 | 三態六態契約 | 復用 `FactAvailability` 六態與狀態格；取樣瞬間資料標 `Unknown` 不冒充 `Present`；外來匯入資料起步一律 `Unknown` |
| F3 | SpecRef 出處鏈 | 每個解碼器方法必須標註規格出處；**未對準出處就不出值** |
| F4 | 知識表框架 `knowledge-pack-vN` | 版本化離線快照包（OUI、PCI、微碼 CVE、dbx、PSU 型號、KB 已知問題、bugcheck 代碼）；宣告 SHA-256；明說沒有更新通道 |
| F5 | 匿名化層與出網許可 | L0–L3 逐欄標註；任何出網或寫入的新通路必須 opt-in、使用者主動觸發、清單成文、語意如實 |
| F6 | 守門五模式 | 新守門必須宣告模式與「防什麼真風險」，寫不出理由的不加 |
| F7 | 審計鏈與寫入閘門 | 一切寫入經寫入閘門記帳；狀態變更進審計鏈；證據包 manifest 雜湊與審計鏈互驗 |

其中 F1 的「**讀取自由、寫入必經寫入閘門**」與 F3 的「**未對準出處就不出值**」是既有的兩條立場（見 2.6、42.3）在規格層的重述；它們之所以被寫進橫切框架，是因為新增一個域時，最容易遺失的正是這兩條——它們不像輸出鍵那樣會在測試裡立刻反映出來。

F4 的設計誠實性值得一提：知識表是離線快照包，而專案有零網路原則，因此它**沒有更新通道**。目錄要求「沒有更新通道就明說」，而不是留一個看似可以更新的介面。這與附錄 D 中「明文不做」的記錄方式同源：**能力的有無必須是明示的，不能靠使用者推測。**

### 59.8 全域資料流

目錄為整份系統畫了一條單一資料流，作為所有域的定位依據：

```
來源層  WMI │ MSR/MMIO │ SMBus │ ECAM │ 登錄檔 │ 事件日誌 │ ETW │ 檔案系統 │ 韌體變數 │ 使用者供檔
   ↓   全部經 F1 掃描骨架（發現→讀取→解碼→finally 還原）
解碼層  XinSpect.Decoders（純函式＋出處註記＋金標／往返／模糊測試）
   ↓   F2 六態契約
事實層  鍵目錄 → 知識表交叉 → 規則引擎 → 能力矩陣
   ↓   F7 審計鏈與寫入閘門＋F5 匿名化
呈現層  WPF 頁面 → 逐值溯源卡 → 錯誤聚合頁 → 情境包精靈
輸出層  JSON／HTML／PDF │ 命令列 │ 本機 API │ 監控端點 │ 簽章封裝
```

這條流與本文第四章的架構總覽一致，差異在於它把「離線模式」並列為來源層的一種形態：掛載既有映像、事件日誌、傾印或裸碟之後，走的**是同一套解碼層、同一套六態、同一套守門**。離線鑑識因此不是另一個子系統，而是同一條管線的另一個輸入端——這正是 OF 域（離線鑑識，8 項）能在不新增架構的前提下成立的原因。

### 59.9 本章的意義

規格庫的價值不在於它列了 600 項，而在於它把「一項功能算不算完成」拆成九個可回答的問題、四級可追溯的鏈、以及七件必須套用的橫切元件。**這使得「我們做了多少」與「我們做得對不對」變成兩件可分別追問的事**——前者由下一章的計數紀律處理（見 65.5），後者由守門與對帳處理。一份沒有這兩層結構的候選清單，只會隨時間變成一份更長的願望清單。

## 第六十章　十二能力域的逐域判定

### 60.1 判定的性質

`docs/CAPABILITY-DOMAINS-2026-10-09.md` 記錄的是專案對一份外部能力清單的逐域判定。它有兩個方法論上的自我約束，值得在引用其結論之前先說明。

第一，**全文不替任何品牌背書**：清單中每一項工具的存在、功能與授權都沒有被逐一查證（文中如實說明「唯一的授權查詢沒有可用結果」），因此判定只談**能力**，不談產品。第二，**凡宣稱「已有」的，證據一律是本專案自己的檔案**——文中每一條「已整合」都附上檔名、型別名或引用檔數。

這兩條約束使判定成為可複核的：讀者不需要信任撰寫者對外部工具的認識，只需要檢查專案自己的程式碼是否真的做著那件事。

### 60.2 四種判定

判定只有四種，且第四種必須附理由：

| 判定 | 意思 |
|---|---|
| 已整合 | 這個能力已經在本專案裡，且做的是同一件事 |
| 本次整合 | 這一輪真的動了程式碼（有新增檔案、有測試） |
| 可整合未做 | 規格公開、唯讀、可機器驗收 → 列為缺口 |
| 不可整合 | 附理由，且理由必須是「硬體／授權／與已裁決原則衝突／屬另一類產品」之一 |

第四種的限制是這份判定的核心設計：**「不可整合」不是一個可以自由填寫的欄位，它的理由被限定在四個種類之內。**少了這條限制，「不可整合」會變成任何困難都能使用的出口，而判定文件的最終價值恰恰取決於這個出口有多窄。

### 60.3 「已整合」的形狀

第一域的判定顯示了本專案與外部清單最大的分歧點。這一域（底層硬體存取、總線與協議分析）的已整合部分是白名單唯讀驅動（`XsRegProbe*`，12 檔引用）加上 WinRing0 的反射載入（47 檔引用）；PCI／PCIe 設定空間、SMBIOS 與 SPD 皆已在讀。

而外部清單中相對應的一類工具是「全權可讀可寫的硬體視窗」。判定因此寫下了一句關鍵的話：這一域**不是「沒整合」，而是刻意整合成更窄的形狀**。這個區分是整份判定的縮影——「有這個能力」與「以同樣的權限形狀提供這個能力」是兩件不同的事。

同樣的結構出現在其他域：域 6（效能、ETW、延遲）的判定指出，該領域外部工具的核心資料源是 ETW，而 `.etl` 是可離線解析的檔案格式，因此屬於「自己讀」而非「調度」；域 7（GPU）則判定「這一域沒有值得動的缺口」，因為專案已用 MSR 直讀在做 GPU 降頻與功耗牆歸因，比讀第三方工具顯示的值更底層。

### 60.4 「不可整合」的理由形狀

四個理由種類各自對應一種不可克服的限制，實例分布如下：

| 理由種類 | 代表性的例子 | 限制的性質 |
|---|---|---|
| 需硬體 | PCIe 協議級分析儀、CAN 匯流排工具、廠商 RF 測試硬體 | 前提不存在 |
| 需核心驅動或注入 | DMA 記憶體存取工具、圖形 API 攔截器（RenderDoc／Nsight）、需自寫核心驅動的 ARK 家族 | 與白名單最小化或「不注入其他行程」衝突 |
| 需網路 | WinDbg 的符號歸因（需符號伺服器） | 與零上傳衝突 |
| 屬另一類產品 | 記憶體取證框架、DFIR 採集與編排、第三方掃描引擎 | 不是本產品的形態 |

值得注意的是第二類之中包含**攻擊性記憶體存取**（直接存取記憶體的工具）與**故障注入**（刻意製造當機或記憶體錯誤的工具）：它們被判不可整合，理由不是技術上做不到，而是與唯讀立場衝突。判定因此示範了一種立場的實際運用方式——**先有已裁決的原則，再用它去裁剪清單，而不是先看清單有什麼再決定原則。**

### 60.5 一行結論與其分佈

判定把整份清單壓縮成一句話：十二域之中，**2 域沒有缺口，5 域已經整合大半，3 域的核心屬於另一類產品或開發者工具鏈，剩下真正值得動的缺口共 4 個——全部是「純解碼器或唯讀讀取」，都不需要硬體、不需要新權限、不需要第三方引擎。**

這個分佈本身是一項結果：在 600 項規模的候選之外，真正可由本專案獨立完成的**新**能力，在該次判定中只有四項。其餘的價值不在新增，而在整合形狀的差異化。

### 60.6 四個真缺口

四項缺口與其契合理由如下：

| # | 缺口 | 為什麼契合 | 驗收重點 |
|---|---|---|---|
| 1 | UEFI 映像 FV／FFS／區段樹分解 | 規格公開（UEFI PI Spec），可寫成純解碼器；不需硬體、不需新權限、不需寫入 | 輸出可導覽結構；解不開的位元組如實標示；**以真實傾印當 fixture** |
| 2 | 驅動 IOCTL／符號連結純靜態分析 | 不載入驅動、不呼叫 IOCTL → 與白名單最小化相容；可與既有的 BYOVD 清單交叉引用 | 列出 IOCTL 分派與裝置名，標示 `METHOD_*`／`FILE_*` 旗標 |
| 3 | `setupapi.dev.log` 外設連接時間線 | 純文字日誌、離線、唯讀；專案已在用 SetupAPI | 逐筆事件；**不解析在地化欄位**，只取結構化段落 |
| 4 | `.etl` 內容解析（讀回） | 寫檔、檔頭驗證、清單管理都已存在，只差讀回內容 | 讀 provider／事件數／CPU 取樣摘要；不可解的事件如實歸類，**不以 0 補** |

第一項的驗收欄附了一條由經驗得出的要求：**以真實傾印當 fixture**，理由是「本專案在 NVMe 位移上吃過合成資料的虧」。合成資料只能證明解碼器對自己的假設自洽；要證明它對真實的輸入正確，fixture 必須來自真實裝置。這條要求把「測試通過」與「解碼正確」之間的差距明文寫進了驗收標準。

第三項的「不解析在地化欄位」則是第四十四章所述語言模式在規格層的落實：日誌中的欄位名稱會隨系統語言改變，若解析依賴文字標籤，則同一份日誌在中文與英文系統上會得到不同的結果——而這種差異是靜默的。

### 60.7 被推翻的假設

判定文件中最有價值的段落之一，是那些記錄了「原本的判斷是錯的」的地方。三例：

**其一，記憶體診斷結果通道不存在。**原本的計畫是「讀取 Windows 內建記憶體診斷的結果」，實測 `wevtutil gl MemoryDiagnostics-Results` 找不到該通道。判定寫下：這不是「我們還沒做」，是**那條通道不存在**；並留下記錄，免得下一輪又有人去試。這正是本文第五十五章所要求「被否決的路徑必須被記錄」的用意。

**其二，`powercfg /energy` 並未整合。**判定在此更正了自己前一份文件的錯誤——前一份把 `powercfg /energy` 寫成已有，實際使用的是 `/batteryreport`（且是產生報告檔的子命令）。同時補充了一項清單沒提的事實：`/sleepstudy`、`/systempowerreport`、`/batteryreport`、`/energy` 都是**會寫出報告檔**的子命令，與專案那五條唯讀查詢不同類，因此不應直接進唯讀區段。

**其三，`.etl` 寫得出、認得出、讀不回來。**專案已有工具能產出標準 `.etl`、驗證 `.etl` 檔頭、管理清單與修剪，但全專案沒有任何一處使用事件來源讀回內容（實測 `grep -rln` 為 0 命中）。這條記錄的價值在於它把一個看起來「已完成」的能力，精確定位到缺失的那一步。

三例的共同結構是：**判定不是在做規劃，而是在消除不確定。**它的產出除了缺口清單之外，還包括一份更新的「什麼不是問題」的清單——後者對後續工作的價值往往更大。

### 60.8 本章的意義

逐域判定的可複製之處，不在於它有 12 個域或 4 個判定，而在於它把三件事同時固定住：**每一條判定的證據來源（本專案的程式碼）、每一條否定的理由種類（四選一）、以及每一條自身修正的記錄。**一份具備這三者的判定文件，可以在半年後被重新檢驗；缺少任何一項，它就會退化成一份只能被相信、不能被檢查的意見。

## 第六十一章　白名單最小化與調度准入

### 61.1 分歧的焦點

如果把本專案與外部的底層工具清單並置，最清楚的差異不是功能多寡，而是**存取權限的形狀**。外部清單中的代表性工具提供「全權可讀可寫」的硬體視窗；本專案提供的是**白名單唯讀**：只開得出明確列舉過的那幾條讀取路徑。

這個差異的實際後果是：許多在外部清單中「可以做」的事，在本專案中是「刻意不做」。判定文件處理這個落差的方式不是逐一辯論，而是把它提升為一條判準（見 61.3），再讓所有項目依判準排隊。

### 61.2 判準：四級分類

對照清單時，先定級，再談優先順序。四級的分法以「資料是否可由本專案自行取得」為軸：

- **A 級：自己讀。**規格公開或格式可離線解析 → 寫成純解碼器，不調度任何外部程式。
- **B 級：原生接縫。**系統自帶可查詢的介面 → 照專案既有慣例包成唯讀來源。
- **C 級：需要調度。**只有在 A、B 皆不可行時才考慮。
- **D 級：不做。**與已裁決原則衝突，或屬另一類產品。

這四級之中，判準最關鍵的推論是：**「外部工具有相同資料」不構成調度的理由。**只要資料源本身是 A 級（公開規格或可離線解析的格式），正確的做法是自己讀，而外部工具充其量提供了一個已知的答案可以對照。判定中對 ETW 的處理就是這條推論的實例：外部效能工具的核心資料源是 ETW，而 `.etl` 可離線解析，因此整條路徑自讀即可。

### 61.3 調度准入三條件

為避免「不可行」被自由定義，判定訂出三個必須**同時**成立的條件：

1. 這項能力**沒有**穩定 API 或公開規格可自己讀；
2. 所需的外部元件（驅動或硬體）**已經在機器上**，不需使用者額外安裝；
3. 它的輸出是**結構化**的，或至少不需要解析在地化文字。

任一條件不成立，就應走整合。

第三條的存在是本文第四十四章的直接延伸：如果唯一的取得方式是解析一個會隨系統語言變動的文字輸出，那麼這個來源的可靠性不由本專案控制，而它失效的方式是靜默的（欄位名改變、輸出為空、或在不同語系上給出不同結果）。**把不可靠的解析包裝成事實鍵，等於把不確定性帶進事實層**——那正是六態與出處鏈要防止的事。

### 61.4 七條留在清單上的「請自行在對的環境跑」

嚴格套用三條件之後，整份清單剩下的調度需求只有七條，而它們的共同點是「整合的前提不存在」而非「判準放行」：

| 場景 | 唯一需要外部工具的地方 | 前提不存在的形式 |
|---|---|---|
| 開機前記憶體測試 | MemTest86 一類 | 需獨立開機環境；行程內做不了 |
| PCIe 協議級／眼圖 | 協議分析儀一類 | 需分析儀或重時序器硬體 |
| USB 協議級捕獲 | 捕獲驅動加封包分析器 | 需安裝核心級捕獲驅動 |
| CAN／現場總線 | 廠商匯流排工具 | 需硬體與廠商驅動 |
| 記憶體取證 | 取證框架加傾印工具 | 屬另一類產品；需傾印檔 |
| GPU 圖形 API 逐幀 | 圖形除錯器 | 需注入目標行程 |
| 藍屏符號歸因 | 符號除錯器加符號伺服器 | 需網路（與零上傳衝突） |

第七條的處理方式是整份判定的典型：符號歸因需要網路，因此不由本專案執行；但**不需符號的那一半**（傾印標頭、bugcheck 代碼、模組清單等）被做成事實，交由缺口 #1 與 #2 承接。也就是說，一個「不可整合」的判斷並不會讓這條路徑整體消失，而是把它切分為「本專案可以誠實完成的部分」與「需使用者在他處完成的部分」。

### 61.5 結論：零個自動調度

套用三條件檢查上表七項，結果是**七項全部不成立**——它們留在表上是因為前提不存在，不是因為判準放行。因此該清單的最小調度路徑，其誠實結論是：**零個自動調度、七個「請你自行在對的環境跑」。**

這個結論的形狀值得留意：它把「我們做不到」轉譯成「這件事需要一個本工具不具備的前提」。前者是能力的缺口，後者是**前提的錯配**，兩者對使用者的意義完全不同——後者告訴使用者該去哪裡做這件事，而不是讓使用者在工具裡反覆尋找一個不存在的按鈕。

### 61.6 界線

這份判定在文末如實列出它沒有做到的事：**沒有**逐一查證清單中每一項工具的存在、功能與授權（唯一的授權查詢沒有可用結果），因此所有判定只針對能力；也**沒有**評估導入的成本與時程。這兩項限制被寫在文件裡，而不是留給讀者推測。

這種自我界線的宣告方式，與本文第二十五章「已知限制」的撰寫原則相同：**限制若不被寫成文件，它就會變成使用者的一次失望；寫成文件，它才變成一次可預期的取捨。**
