# 第五部　工程

## 第二十二章　品質保證體系

### 22.1 測試的規模與結構

本版測試專案包含 433 個測試檔，`[Fact]` 與 `[Theory]` 標記合計 4568 處。測試的組織方式與程式碼結構對應：每個服務模組有對應的測試檔，每個解碼器有其金標向量測試，每條對帳規則有其逐情境行為測試。

測試的完整清單與規模見附錄 F。

### 22.2 三個層次的驗證

曦覽的品質保證動用三種互補的機制，各有其擅長發現的缺陷類型。

**單元測試——發現邏輯錯誤。** 單元測試驗證每個模組在給定輸入下的輸出。其優勢是快速、精確、可大規模執行；其局限是只能驗證被測到的輸入組合。

**金標向量測試——發現解碼錯誤。** 對暫存器與結構的解碼器，測試使用手算的位元組級金標向量。例如 SMBIOS 結構的解析以人工建構的位元組序列作為輸入，並比對每個欄位的解析結果。此類測試的價值在於它驗證的是**對規格的理解**，而非對程式碼的理解——若實作者誤解了位元配置，測試會失敗，因為金標向量來自規格而非來自實作。

**突變測試——發現測試的無效性。** 純函式解碼器獨立為 `XinSpect.Decoders` 類別庫並以 Stryker 進行突變測試。突變測試對原始碼進行微小的語意變更（例如將比較運算子的邊界改變、將位元遮罩的值改變），然後檢查測試是否失敗。若突變未被發現，代表測試對該處的實作不敏感。

`docs/MEASUREMENT-METHODOLOGY.md` 與 `docs/spec/METHODOLOGY.md` 記載方法論的完整內容。

### 22.3 突變測試發現的真實缺陷

突變測試的價值已在實際開發中證實。一個具體案例是擴展家族（extended family）的進位處理：該邏輯在文件與註解中記載，但實作中未處理進位情形。此缺陷在功能測試中不顯現，因為受影響的輸入組合在真實硬體上罕見；但突變測試將該處的邊界改動時，測試未失敗，因而暴露了測試對該處不敏感——順著這條線索找到了實作本身的缺失。

此案例說明了突變測試與覆蓋率的根本差異：覆蓋率會顯示該行被執行過（因為它就在正常路徑上），因此不會引起注意；突變測試則要求測試對該行的**語意**敏感。

### 22.4 守門測試

除了一般的功能測試，本專案使用一類「守門測試」（guard tests），其目的是防止特定類別的缺陷再次出現。守門測試的特徵是它驗證的不是功能，而是**一致性的不變式**。

已知的守門測試包括：

| 守門對象 | 檢查內容 |
|---|---|
| 事實鍵目錄 | 重新掃描 `Services/` 原始碼，與 `FactKeyCatalog` 逐鍵比對；新增事實而忘記更新目錄即失敗 |
| 執行期鍵對帳 | 執行期出現的鍵必須在目錄全鍵中、或命中某個已登記的動態家族前綴 |
| 殭屍前綴 | 已登記的動態家族前綴必須在原始碼中確實有生產者 |
| 豁免理由 | 不允許存在空理由的豁免條目 |
| 解碼器規格引用 | 解碼器必須攜帶 `SpecRef` 註記，由反映式檢查強制 |
| 探針接線死路 | 防止探針被接線後卻無路徑消費該結果的情形 |

最後一項的命名值得說明：「探針接線死路」指的是探針蒐集了資料、接了線，但沒有任何人消費它——資料被產生但從未被使用。這類缺陷不會導致測試失敗、不會產生錯誤輸出、也不會影響效能（或影響極小），因此極難被發現。把它機械化的唯一辦法是檢查接線圖本身。

### 22.5 測試作為設計約束

本專案的測試不只是驗證，也是設計約束。三個具體例子：

**純函式的隔離。** 要把解碼邏輯納入突變測試，它必須是純函式且不依賴作業系統。這個要求迫使解碼與 I/O 分離，因而改善了架構。

**目錄的編譯期固定。** 要在發佈版中保有正確的鍵全集，目錄必須在編譯期固定。這個要求來自一個真實缺陷（見 10.1），其成因是測試環境與發佈環境的差異。

**可用性的強制。** 要讓「讀不到」不可能被誤報為「值為零」，可用性欄位必須進入資料模型而非輸出層。這個要求改變了模型設計。

### 22.6 效能預算作為測試

載入時間設有預算，且預算由測試守門（`Tests/PerformanceBudgetTests.cs`）。其設計要點是：效能退化不以人工審查發現，而以測試失敗發現。此機制與 2.7 的突變測試同屬「把品質要求機械化」的做法。

## 第二十三章　效能工程

### 23.1 效能的量測方法

效能工作若無可比較的量測，其結論不可信。本專案對載入效能的量測方法為：

**同一行程、同一機器、暖機後。** 冷啟動與暖機後的量測差異顯著（前者包含 JIT、驅動載入與磁碟快取填充），因此兩者必須分開記錄，不可混用。

**逐項計時。** 每條載入方法各自計時，而非只量測總時間。逐項計時是必要的，因為最佳化目標的選擇取決於排序，而排序只有在逐項計時下才可見。

**輸出鍵集合逐字比對。** 任何效能變更之後，必須比對其產生的事實鍵集合是否與變更前完全相同。此要求針對的失效模式是：最佳化過程中改變了載入行為，導致部分事實不再被產生（或產生了不同的鍵），因而使效能看似改善。鍵集合的比對使這類「以功能換效能」的變更無法隱藏。

### 23.2 已完成的效能工作

本版之前已完成數項效能收口，其中兩項記錄於 `docs/ROUND-PERF-SIGCACHE-2026-10-12.md` 與 `docs/ROUND-PERF-DISK-BREAKER-2026-10-13.md`：

**簽章判定快取。** 簽章驗證是重複性高且昂貴的操作（同一檔案的簽章在多次掃描中被重複驗證）。加入判定快取後，重複驗證的成本顯著下降。此類快取的正確性要求是快取鍵必須涵蓋所有影響判定的輸入（檔案內容、憑證狀態、時間），否則會產生過期的判定。

**儲存探測斷路器。** 儲存裝置的探測在特定硬體上可能長時間阻塞。斷路器（`StorageProbeBreaker`）在偵測到失敗模式後停止再嘗試，使單一異常來源不再拖累整體載入。

**慢來源查詢守門。** 對已知昂貴的來源（例如列舉選用功能的 WMI 查詢）建立守門測試，確保該類來源在一次載入中只被查詢一次。此守門針對的失效模式是：多個模組各自查詢同一來源，其成本隨模組數線性成長而無人察覺。

### 23.3 載入路徑的現況量測

暖機後的完整載入路徑量測結果約 5.6 秒，前三名為：

| 載入方法 | 量測時間 | 性質 |
|---|---:|---|
| `LoadPlatformFacts` | 約 1,700 毫秒 | 平台識別與角色事實，包含數個 WMI 查詢 |
| `LoadSbom` | 約 974 毫秒 | 軟體物料清單，涉及檔案系統走訪 |
| `LoadAdvancedSupplement` | 約 700 毫秒 | 進階補充事實 |

此排序是後續最佳化工作的依據：最佳化的優先順序應由排序決定，而非由「哪個模組看起來複雜」決定。

### 23.4 並行化的量測與其未採用

載入路徑的聚合特性是 **I/O 密集且彼此獨立**，這使其成為並行化的自然候選。本專案對此進行了受控量測：把 42 條具 `Load` 前綴的方法置於同一行程、同一機器，比較循序與不同並行度的牆上時間。

| 執行方式 | 牆上時間 | 相對循序 |
|---|---:|---:|
| 循序（現行） | 6,384 毫秒 | — |
| 並行度 3 | 2,661 毫秒 | −58% |
| 並行度 6 | 2,200 毫秒 | −66% |
| 並行度 12 | 2,031 毫秒 | −68% |

三次量測產生的事實鍵集合逐字相同（560 個鍵，集合比較為相等），因此並行化並未改變輸出的內容。

**此項最佳化未被採用。** 未被採用的理由有三，且必須完整記錄，因為「量到了改善卻不做」需要比「做了」更充分的理由。

**理由一：存在一條真實的順序相依，且並行化會使其輸出依時序而變。** 如 5.2 所述，`LoadServerCompliance()` 需要 `RoleFacts` 作為輸入，而後者由較後段的方法產生。在循序載入下，合規性穩定地看到上一輪的值；並行化之後，它可能在角色事實填入之前或之後執行，因而產生時序相依的輸出——同一台機器在不同次執行中可能得到不同的 `role.compliance.*` 值。**以不穩定的輸出換取兩倍的載入速度，是不划算的交易。** 若要並行化，必須先把角色事實的載入前置於合規性判定之前；此為該缺陷的修正，屬獨立工作項。

**理由二：並行化等於對硬體探測加併發。** 45 條載入方法同時執行意味著同時進行多個 WMI 查詢與多個驅動 IOCTL。WMI 的併發行為、以及既有那些「一旦觸發即無法取消」的硬體存取操作的併發行為，皆未經充分驗證。量測到並行度 12 未拋出例外、且鍵集合未變，但單次量測不構成對競態的排除。

**理由三：協調成本。** 現行的 45 條載入方法是一長串 `try { … } catch { … }`，此形式使新增來源的邊際成本極低。改為清單式或並行編排會改變此手感。此因素在多個貢獻者同時在該方法中新增來源時尤其重要。

此項工作的記錄方式體現本專案的工程原則：**量測結果、未採用的理由、以及解除條件三者一併記錄**。未來的貢獻者可以在修正順序相依之後重新評估並行化，而不需重新發現上述理由。

### 23.5 效能的設計約束

效能工作在本專案受到以下約束，這些約束優先於效能目標本身：

- **不得以遺漏事實換取速度。** 任何減少載入時間的變更都必須通過鍵集合比對（見 23.1）。
- **不得以不穩定輸出換取速度。** 見 23.4 理由一。
- **不得以降低誠實度換取速度。** 例如以逾時後直接跳過某來源（而不標記為 `ReadError`）換取速度，屬違反 2.1 的行為。
- **快取必須有正確的鍵。** 見 23.2。

## 第二十四章　隱私與資料主權

### 24.1 不收集、不上傳

程式不收集、不上傳任何使用者資料。此陳述的具體內容是：

- 無遙測、無使用統計、無當機回報（`CrashLog` 與 `diag.log` 僅寫入本機，由使用者決定是否提供）。
- 事實集合的保存位置與保存期限由使用者控制。
- 網路流量的產生僅限於使用者主動呼叫的功能：AI 評價（第二十一章）與更新檢查。兩者的端點皆可設定。

### 24.2 敏感資訊的處理

部分事實具有敏感性，程式對其處理有明確約束：

**資產識別欄位。** 序號、SKU、資產標籤等屬於組織的資產資訊。這些欄位在報告中保留（因為它們是爭議情境中的關鍵證據），但其對帳豁免理由記載「可對帳的是『有沒有填』，那已寫在 asset.identify 的判讀裡，不是值的本身」——即工具不對這類值的內容進行推斷。

**服務名稱與服務清單。** 服務清單可反映組織的軟體部署。因此服務就緒時間線（PO-005）明文「不列服務名稱」。

**識別資料的分離。** 端點政策相關的事實（ZR-001、ZR-002）明文「只報狀態，不讀識別資料」。

**匿名機器識別。** 本機 API 的設計約束包含匿名機器識別（見 20.2）。

### 24.3 資料主權

`docs/DATA-SOVEREIGNTY.md` 記載資料主權的完整立場。其核心內容是：使用者對其資料的位置、形式與去向具有完全控制權。具體落實為三點：本機優先（事實與報告預設存於本機）、格式開放（時間膠囊的格式有公開規範，`docs/spec/snapshot.schema.v1.json`）、可攜（資料可以離開工具，且離開後仍可解讀）。

第三點的意義值得說明：若資料離開工具後即不可解讀（例如私有二進位格式），則使用者實際上並不擁有其資料——其使用受到工具本身的限制。公開的規範格式使資料的所有權與工具的使用權分離。

### 24.4 寫入操作的可稽核性

所有寫入操作經由集中閘門（`WriteGate`）並進入審計日誌。使用者可查閱「工具做過什麼」，且日誌可脫離應用程式驗證（見 20.4）。這是資料主權在「變更」面向的落實：不僅資料屬於使用者，對資料的變更紀錄也必須對使用者可見且可驗證。

## 第二十五章　已知限制

本章列出本版已知的限制與缺陷。列出的原則是：**發現即登記**。未列出的限制並非不存在，而是尚未被發現。

### 25.1 已知缺陷

**載入順序的語意相依（5.2）。** `LoadServerCompliance()` 在現行的循序載入順序下讀取上一輪的角色事實，導致同一份快照內部的自相矛盾。此缺陷穩定可重現（不隨機），其判讀影響限於角色變更的那一次載入。修正方向為前置角色事實的載入。此缺陷同時是 23.4 所述並行化未能採用的原因之一。

### 25.2 未經真機驗證的功能

**AMD 平台專屬事實。** SMU、PSP、SEV 系列相關事實已實作，但開發機為 Intel 平台，無法驗證。豁免條目明文記載「有真機時應補對帳規則，屆時本條豁免要移除」。

**CXL 相關事實。** 已實作，但無 CXL 硬體可驗證。豁免條目記載「本機無 CXL 硬體」。

**部分平台特定解碼。** 依賴特定晶片組或特定平台結構的功能，其驗證限於開發機所具備的硬體。

此類限制的處理方式是在豁免清單中逐條登記，而非以測試通過宣稱功能可用。此為本專案對「未驗證」與「已驗證」的區分原則。

### 25.3 覆蓋的不完整性

**未覆蓋的事實鍵。** 844 個靜態鍵中，並非全部被對帳規則考慮。未被考慮且未豁免的鍵構成一個已知數字（見 10.3）。這些鍵的事實不會被交叉檢查。

**豁免的事實鍵。** 562 條豁免涵蓋大量事實鍵，其不對帳的理由各有不同（見附錄 D）。豁免的門檻是「無法交叉」而非「難以交叉」，但門檻的維持依賴審查，不是機械保證。

**突變分數 82%。** 突變測試的目標分數為 82%，而非 100%。未達 100% 意味著部分程式碼的語意未被測試充分約束。

### 25.4 量測的固有限制

**虛擬層下的量測。** 在虛擬機器中，MSR、PCI 設定空間與感測器讀值由虛擬層提供，不必然對應實體硬體。規則 `R-CPU-04` 對此提出方法論警告，但警告本身不能改變量測的本質。

**溫度與功耗的時序相依。** 這類量測受熱慣性與電源狀態影響，跨量測的可比較性依賴條件記錄（見 13.2）。

**基準測試的模型依賴。** NPU 等單元的效能高度依賴模型與精度，跨場次的比較需要條件一致。

**單一來源事實的本質限制。** 部分事實只有一個來源（見 14.3 與附錄 D 的單一來源類豁免）。這類事實無法被交叉驗證，其可信度上限由來源本身的可靠度決定。

### 25.5 使用環境的限制

**平台。** 程式為 Windows x64 專用，不支援其他平台。

**權限。** 部分事實需要以系統管理員權限執行才能讀取（`FactCatalog` 逐項標示）。未以此權限執行時，這類事實的可用性為 `InsufficientPrivilege`，且工具會說明取得所需的條件。

**硬體相依。** 依賴 Ring-0 存取的功能需要可載入的驅動。在驅動無法載入的環境（例如部分受管制的端點、啟用特定記憶體完整性設定的系統）中，這類功能不可用。

**語言涵蓋。** 介面提供三種語言模式，但部分長篇文案（例如安裝精靈與特定說明頁）的翻譯涵蓋不完整。

### 25.6 刻意的不作為

第 1.4 節所列的不作為屬於設計選擇而非限制，但對使用者的影響類似，因此在此一併提示：不主動變更硬體狀態、不在未經請求時產生網路流量、不代替使用者診斷故障、不提供繞過防護的手段、不承諾特定平台的完整性。

## 第二十六章　版本沿革

### 26.1 沿革的記錄方式

版本的完整沿革記載於 `README.md` 的版本沿革章節，另有 `docs/ROUND-*.md` 形式的逐輪工作紀錄。本節不重複該清單，而是說明沿革的結構與其反映的開發模式。

### 26.2 開發模式

本專案的演進以「輪」為單位。每一輪處理一組相關的能力（例如某個子系統的深度、某個來源的分層、某類對帳的補齊），並產生一份 `docs/ROUND-*.md` 記錄，內容包含該輪的目標、實作範圍、量測結果與遺留事項。

此模式的特徵是**把調查本身也產出文件**。例如本白皮書所述的多項效能量測（例如並行化天花板）其價值不只在於結論，也在於其記錄了「量到什麼、為何不採用、解除條件為何」。這使後續的貢獻者不必重新發現已被否決的路徑。

### 26.3 版本號與事實鍵數

自 v2.70 起，版本沿革中的鍵數改採**可重現基準**——即由掃描原始碼得到的數字，而非人工統計。此改變的理由與 10.1 相同：人工統計的數字會與程式碼漂移，而可重現的數字可以隨時驗證。

本版（v2.84）的對應數字為：靜態鍵 844、動態家族 23、規則 18、豁免 562、服務模組 416、測試檔 433、測試標記 4568、文件 51。

### 26.4 本輪的對應關係

本白皮書所述的引擎版本為 `2.84.0.0`，對應的開發進度為第 547 項（檔案系統中介資料微延遲）。此數字代表專案以「項」為單位追蹤能力的累積，其編號與規格編號（如 NG-002、ZR-004）並行使用。

## 第二十七章　路線圖

### 27.1 待修正項

**載入順序的語意相依修正（5.2、25.1）。** 把角色事實的載入前置於合規性判定之前。此修正同時解除 23.4 所述並行化的第一個障礙。

**並行化的重新評估。** 在順序相依修正之後，重新評估載入路徑的並行化。評估的條件為：鍵集合不變、輸出穩定（同一機器多次執行結果一致）、以及硬體探測的併發行為經過驗證。

**AMD 與 CXL 真機驗證。** 取得對應硬體後，補齊相關的對帳規則並移除其豁免條目。

### 27.2 能力的擴充方向

**知識包的擴充。** 目前知識包的形式已支援裝置合規基線與 CVE 對照，其擴充方向為更多可外部維護的判定基準，使工具的判定能力可隨外部知識更新而不需改版。

**量測方法論的收斂。** 部分量測項目的方法論仍在演進（例如不可見停頓的歸因），其收斂會影響報告的可比較性。

**未覆蓋鍵的逐步處理。** 未覆蓋的事實鍵將被逐步處理：可交叉者補規則，不可交叉者補豁免理由。此工作的目標不是覆蓋率數字，而是**讓每一個未被檢查的事實鍵都有明確的狀態**。

### 27.3 不打算做的事

路線圖亦包含不打算做的事，其登記方式與豁免清單一致：

- **不提供 REST 範例集**（規格編號 XT-003，已明文決定不做）。
- **不建立背景服務、不註冊排程**（AG-005 的立場）。
- **不預設啟動 HTTP 監聽殼**（17.7）。
- **不提供攻擊性功能**（1.4）。

登記「不做」的理由與登記「要做」同等重要，因為它防止未來的貢獻者在不知情的狀況下重新引入已被否決的設計。

第三方元件的授權資訊見 `THIRD-PARTY-NOTICES.md`。

### 28.2 貢獻

貢獻的起點是 `docs/AGENT_CONTEXT.md` 與 `README.md` 的貢獻者章節。本專案對貢獻的具體要求有三：

**新增事實必須同步更新目錄。** 這是機械要求，由測試守門（見 22.4）。忘記更新會導致測試失敗。

**新增事實必須處理其覆蓋狀態。** 可交叉者補規則，不可交叉者補豁免理由。空理由的豁免不被接受。

**新增解碼器必須攜帶規格引用。** 由反映式檢查強制。

**新增來源必須處理讀不到的情形。** 以 `Diag.Swallow` 記錄並標示對使用者的後果，不得以預設值填補。

### 28.3 貢獻的設計立場

貢獻者的設計立場應與本文件所述的原則一致。最重要的三條是：

**讀不到不可偽裝為沒有。** 這是本專案所有設計原則中最核心的一條，其違反形式包括以 0 填補、以典型值填補、以快取值填補，以及把掃描失敗解讀為空集合。

**矛盾勝於結論。** 指出不一致比給出結論有價值，因為前者可被複核而後者只能被信任。

**不確定性必須與數值同時呈現。** 誤差範圍、樣本數、條件記錄與可用性欄位皆屬此類。

### 28.4 致謝

本專案整合了多個開源元件的成果，包括感測引擎 LibreHardwareMonitor、內嵌瀏覽器 WebView2，以及在其基礎上建立的硬體存取與列印路徑。完整的元件清單見 `THIRD-PARTY-NOTICES.md`。

同時，本專案的開發過程中大量依賴真機測試——許多設計決策的直接成因是特定硬體上觀察到的行為（SMBus 的併發存取、Super I/O 感測器的固定值、裝置 IOCTL 的不可取消性、韌體計數器的重設）。這些觀察無法從規格書推導，只能來自實際使用。
