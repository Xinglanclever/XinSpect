## 第五十五章　設計決策記錄

### 55.1 本章的用途

本文前述各章說明了設計的內容與理由，但理由散布於各處。本章把重要的設計決策收斂為一份清單，每條記錄四項：決策、理由、代價、以及解除條件。解除條件的欄位是本清單中最重要的部分，因為它說明「在什麼情形下這個決策應該被重新考慮」。

### 55.2 資料模型類決策

**D-01：全部事實收斂為單一型別。**
理由：消費端的一致性（見 3.1）。代價：模型包含部分項目用不到的欄位。解除條件：若出現一類事實無法以現有欄位表達（例如需要結構化的多值），則需擴充模型而非另立型別。

**D-02：可用性與值分離。**
理由：讀不到與零值必須可區分（見 2.1）。代價：每個事實多一個欄位，且所有消費端需處理四種不可用狀態。解除條件：無。

**D-03：可信層級分為四級。**
理由：推論鏈長度的陳述（見 3.3）。代價：分級需人工判定，且分級的邊界有模糊之處。解除條件：若出現大量難以歸類的事實，則需重新檢視分級的定義。

**D-04：`numericValue` 與 `value` 分離。**
理由：比較運算子需要數值，呈現需要格式化字串（見 3.1）。代價：兩者需保持同步。解除條件：無。

### 55.3 鍵空間類決策

**D-05：事實鍵全集的編譯期固定。**
理由：發佈版掃不到原始碼目錄，掃描失敗會被讀為「全部覆蓋」（見 10.1）。代價：新增事實需手動更新目錄。解除條件：若發佈形態改變為包含原始碼（例如以指令碼發佈），則可重新評估。

**D-06：動態家族需逐筆申報理由。**
理由：成員由機器決定的鍵無法列舉，但不得因此成為免死金牌（見 10.2）。代價：新增家族需撰寫理由，且需人工審查理由的品質。解除條件：無。

**D-07：鍵不更名，語意變更以新鍵表達。**
理由：歷史比較的有效性（見 54.4）。代價：鍵空間會隨時間累積。解除條件：無。

**D-08：彙總性的問題使用固定鍵。**
理由：彙總本身是固定的問題（見 54.3）。代價：需人工判斷哪些是彙總、哪些是成員。解除條件：無。

### 55.4 對帳類決策

**D-09：判定只有三種，且不輸出分數。**
理由：分數會使使用者停止思考（見 1.1、8.1）。代價：使用者需自行解讀矛盾清單。解除條件：無。

**D-10：缺值由引擎處理，規則不寫缺值分支。**
理由：缺值的處理需在全域一致（見 8.2）。代價：規則的輸入需完整宣告。解除條件：無。

**D-11：矛盾的輸出必須附證據。**
理由：判定需可被複核（見 8.4）。代價：輸出量增加。解除條件：無。

**D-12：儲存裝置規則逐碟執行。**
理由：儲存裝置的健康狀態本質上逐裝置（見 8.3）。代價：報告的組織需區分逐碟與整機。解除條件：無。

**D-13：不設覆蓋率門檻。**
理由：強制全覆蓋會逼出湊數的規則（見 2.5、10.4）。代價：一部分事實永遠不會被交叉檢查。解除條件：無。

**D-14：豁免需附理由，且理由的門檻是「無法交叉」。**
理由：區分「不能對帳」與「懶得對帳」（見 2.5）。代價：新增不支援對帳的事實需撰寫理由。解除條件：無。

### 55.5 取得與讀取類決策

**D-15：白名單唯讀驅動。**
理由：可存取範圍可列舉、可審閱（見 6.1）。代價：新增暫存器需修改驅動與清單。解除條件：無。

**D-16：讀取優先，寫入經由集中閘門。**
理由：把讀取與寫入缺陷的後果分開（見 2.6、46.3）。代價：寫入功能的實作成本較高。解除條件：無。

**D-17：高風險來源設逾時與斷路器。**
理由：不可取消的硬體存取可能造成長時間阻塞（見 43.4）。代價：斷路器只能在後續嘗試中停止，首次阻塞仍會發生。解除條件：若底層取得可取消性，則可重新評估。

**D-18：診斷紀錄分為已接住（`Diag`）與未接住（`CrashLog`）。**
理由：區分「工具的缺陷」與「環境的限制」（見 4.5）。代價：兩份紀錄的存在需使用者理解其分工。解除條件：無。

**D-19：`Diag` 自身不得拋例外。**
理由：診斷機制不得成為新的失敗來源（見 2.1）。代價：寫檔失敗時僅保留記憶體紀錄。解除條件：無。

### 55.6 輸出與介面類決策

**D-20：四種輸出消費同一模型。**
理由：介面與匯出的一致性由架構保證（見 20.5）。代價：模型的變更影響所有輸出。解除條件：無。

**D-21：本機 API 的 HTTP 監聽殼預設不啟動。**
理由：開啟監聽等於新增本機攻擊面，屬使用者的決定（見 17.7、20.2）。代價：需要 HTTP 存取的整合需自行開啟。解除條件：若提供安全的本機認證機制，可重新評估。

**D-22：查詢語言的語法錯誤回傳錯誤而非空結果。**
理由：把查錯偽裝成空結果屬於誠實違反（見 19.4）。代價：使用者需處理錯誤。解除條件：無。

**D-23：審計日誌可脫離應用程式驗證。**
理由：驗證不應依賴被驗證的對象（見 20.4、48.6）。代價：需維護獨立的驗證路徑。解除條件：無。

### 55.7 功能取捨類決策

**D-24：明文不做 REST 範例集。**
理由：發佈可用的範例等於提供連向未承諾端點的程式碼（見 1.4、附錄 D）。代價：整合者需自行依 CLI 輸出實作。解除條件：若端點規格正式納入承諾範圍，則可重新評估。

**D-25：不建立背景服務、不註冊排程。**
理由：「可以做」與「正在做」是兩件事（見 17.6）。代價：需要常駐執行的使用者需自行整合。解除條件：無。

**D-26：網路流量的產生限於使用者主動觸發。**
理由：資料邊界（見 21.2、33.4）。代價：無法提供自動的更新或監控。解除條件：無。

**D-27：AI 評價位於資料流的末端。**
理由：生成式功能不得影響事實層（見 21.3）。代價：其輸出需明確標示為生成內容。解除條件：無。

### 55.8 效能類決策

**D-28：載入路徑暫不並行化。**
理由：存在一條真實的順序相依，並行化會使輸出依時序而變（見 23.4）。代價：放棄約 66% 的載入時間改善。解除條件：修正 `LoadServerCompliance` 對角色事實的依賴（見 5.2）後可重新評估。

**D-29：效能變更後必須比對鍵集合。**
理由：防止以遺漏事實換取速度（見 23.1）。代價：每次效能變更都需比對。解除條件：無。

**D-30：效能預算由測試守門。**
理由：效能退化應由測試發現而非人工審查（見 22.6）。代價：預算的調整需修改測試。解除條件：無。

### 55.9 決策的整體性質

回顧以上三十條決策，其共同結構為：**多數決策的代價是「實作成本」或「功能便利性」，而換取的是「可複核性」或「輸出的穩定性」。**

少數決策沒有解除條件，其意義是它們屬於工具的基本立場而非技術選擇（例如 D-02、D-09、D-13）。這類決策若被改變，工具的性質隨之改變，因此其改變不應以技術評估的方式進行。

其餘決策皆有解除條件，且解除條件通常是**環境或實作條件的變化**（例如 D-05 的發佈形態、D-28 的順序相依修正）。這類決策應在條件變化時被主動重新檢視，而非維持現狀直到問題出現。
