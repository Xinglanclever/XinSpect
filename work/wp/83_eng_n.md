## 第五十四章　事實鍵的命名與演進規範

### 54.1 為什麼需要規範

事實鍵是程式的公開介面之一：時間膠囊的內容、查詢語言的比對對象、本機 API 的回應、以及報告的組織方式都以此為基礎。因此鍵的命名不是實作細節，而是介面設計。

規範的必要性來自三個實際問題：鍵的更名會使既有的快照與查詢失效；鍵的語意變更會使歷史比較產生錯誤的結論；鍵的無節制增生會使覆蓋申報失去意義（因為分母會持續擴大）。

### 54.2 命名的結構

事實鍵採點分階層，其一般形式為：

```
<領域>.<子領域 or 對象>.<屬性>
```

**第一段為領域前綴。** 本版有 107 個前綴（見附錄 A）。前綴的數量應保持節制：新增前綴意味著新增一個領域，其成本高於在既有前綴下新增子領域。

**中段為對象或子領域。** 例如 `role.installed.<功能名>` 中的 `installed` 為子領域，其後的段為具體對象。

**末段為屬性。** 例如 `pci.dev.` 家族中的裝置號、或 `ac.hpet.full.base` 中的 `base` 欄位。

### 54.3 三種鍵的形態

**固定鍵。** 成員在編譯期確定，登記於 `FactKeyCatalog`。適用於「有哪些項目取決於程式碼」的事實。

**動態家族。** 成員由機器決定，以字首登記於 `FactKeyDynamicCatalog`。適用於「有哪些項目取決於機器」的事實（見 10.2）。每個家族必須申報兩件事：為什麼成員是編譯期數不出來的，以及成員由什麼決定。

**動態家族中的固定鍵。** 部分家族同時有一個彙總鍵登記於固定目錄（例如 `monitor.summary`、`sa.lsp.count`、`role.surface`）。此設計的理由是：彙總本身是一個固定的問題（「有幾台顯示器」），因此它應該是一個固定的鍵，而非動態家族的成員。

此三種形態的區分標準是**成員的決定因素**：取決於程式碼者為固定鍵，取決於機器者為動態家族，而彙總性的問題為固定鍵。

### 54.4 演進規範

**規範一：已發佈的鍵不更名。** 更名會使既有的快照與查詢失效。若需要表達新的語意，應新增鍵而非修改既有的鍵。

**規範二：語意變更需以新鍵表達。** 若某個事實的計算方式或語意發生變化（例如原本由 A 來源取得，改為由 B 來源取得而語意不同），則應新增鍵。此規範的目的與 48.5 所述相同：使歷史比較中的「值改變」能區分為「事實改變」與「來源改變」。

**規範三：鍵的移除需同步更新目錄。** 未同步會導致測試失敗（見 22.4）。

**規範四：動態家族的前綴必須有生產者。** 登記了卻沒人生產的前綴為殭屍前綴，測試會判定為失敗。

**規範五：前綴的終止符規則。** 家族前綴一律以點結尾，除非其末段為埠號前綴（例如 `sio.0x`）。此規則的存在是為了容納「埠號是平台事實」的情形（見附錄 B 的登記理由）。

### 54.5 鍵空間的完整性

鍵空間的完整性由兩道檢查保證（見 10.2）：

**執行期對帳。** 任何執行期出現的鍵，要嘛在固定目錄中，要嘛命中某個已登記的動態家族前綴。否則為失敗。

**殭屍前綴檢查。** 已登記的前綴必須在原始碼中有生產者。

兩道檢查的合稱使鍵空間成為一個**封閉且可驗證的集合**：不會有未登記的鍵產生，也不會有登記而不生產的前綴。此封閉性有兩個用途：覆蓋申報的分母是正確的（因為鍵空間完整），以及報告的欄位集合是可預期的。

### 54.6 鍵的全部引用點

新增或修改鍵時，需注意鍵在程式碼中被引用的位置。由附錄 A 的「產生模組」欄可見，部分鍵被多個模組引用（例如讀取端與呈現端）。修改鍵的語意時，所有引用點都需檢視。

此多點引用的性質是將鍵集中於目錄的理由之一：目錄是鍵的唯一權威清單，因此可以機械檢查一致性（見 22.4）。

### 54.7 規範的成本

前述規範帶來實作成本：新增事實需更新目錄、新增不支援對帳的事實需撰寫豁免理由、動態家族需申報理由、以及鍵不得更名。這些成本是刻意的，其換取的是：

- 覆蓋申報的正確性（分母完整、狀態明確）。
- 歷史比較的有效性（鍵的穩定性使值的變化可解讀）。
- 報告欄位集合的可預期性。
- 鍵空間的封閉性（無未登記的鍵、無殭屍前綴）。
