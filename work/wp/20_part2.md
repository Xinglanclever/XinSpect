# 第二部　系統架構

## 第四章　架構總覽

### 4.1 技術選型

曦覽以 C# 撰寫，目標框架為 `.NET 10.0-windows`，使用者介面採 WPF 與 MVVM 模式。選用 WPF 而非較新的跨平台框架，理由是此工具的核心需求集中在三處，而這三處都需要 Windows 原生的深度存取：

- **Ring-0 存取**：MSR、PCI 設定空間、I/O 埠與 MMIO 的讀取需要核心模式驅動與裝置 IOCTL，這在 Windows 上透過自訂驅動與 `DeviceIoControl` 完成。
- **WMI 與系統 API**：大量事實來自 WMI 的 CIM 類別與 MSFT 進階類別，以及 Win32 API 的直接呼叫。
- **硬體感測**：整合 LibreHardwareMonitor 作為感測器引擎，另以 Intel XTU 橋接處理超頻相關功能、以 NVIDIA NVML／NVAPI 處理顯示卡控制。

同時，內嵌 WebView2 提供內建瀏覽器，用於檢視線上文件與規格，以及呈現部分 HTML 形式的報告。

### 4.2 分層與職責

程式碼目錄的劃分對應其職責：

| 目錄 | 職責 | 規模（本版） |
|---|---|---|
| `Services/` | 事實收集、解碼、對帳、輸出與基礎設施 | 416 個模組 |
| `Models/` | 資料模型與業務實體 | 24 個模組 |
| `ViewModels/` | 畫面狀態與命令，含啟動序列編排 | — |
| `Controls/` | 自繪控制項（儀表、歷史圖、示波器、環形圖等） | — |
| `Views/` | 畫面定義 | — |
| `XinSpect.Decoders/` | 純函式解碼器，獨立類別庫，供突變測試 | — |
| `XsRegProbe/` | 白名單唯讀核心模式驅動 | — |
| `Tests/` | 測試專案 | 433 個測試檔、4568 處標記 |

`Services/` 佔絕大多數模組數，反映本專案的重心：功能的主要複雜度不在介面，而在於**如何正確地從數十種來源取得事實、以及在讀不到時如何誠實地陳述**。

### 4.3 啟動序列

應用程式啟動時執行一條固定的載入序列，其順序具有語意而非僅為便利。序列由 `StartupSequence` 編排，逐步推進並在每一步更新介面上的進度狀態。順序的考量有三：

**其一，先建立可用的骨架。** 系統與平台識別事實（處理器、主機板、記憶體配置、作業系統版本）先載入，因為後續的判讀需要平台資訊作為前提。例如「此平台不支援某項功能」的判定需要先知道平台為何。

**其二，把可能阻塞的操作往後放。** 涉及裝置 IOCTL 或 WMI 的查詢可能因驅動異常或提供者無回應而延遲。這類查詢安排在序列後段，使介面在這些查詢完成前即可使用，並在逾時時顯示原因而非持續轉圈。

**其三，昂貴但非必要的部分可延後或省略。** 深測中心（第十一章）的各項測試、證據實驗室（第十九章）的深度蒐集，皆由使用者主動觸發，不屬於啟動序列。

### 4.4 事實收集的組織方式

事實收集集中於 `EvidenceCollection`，其中的載入方法以 `Load` 為前綴，每一條對應一組來源或一個子系統，例如 `LoadPlatformFacts`、`LoadSbom`、`LoadAdvancedSupplement`、`LoadOperationsInventory`、`LoadNetworkSystemInventory`。每條載入方法的形式一致：

```
try { …蒐集並產生 HardwareFact… }
catch (Exception ex) { Diag.Swallow(「位置標籤」, ex, 「對使用者的後果」); }
```

這個形式的意義是：**任何單一來源的失敗都不會阻止其餘事實的產生，但都會留下具名的紀錄**。`Diag.Swallow` 的三個參數分別是發生位置的短標籤、例外本體、以及對使用者的實際後果（例如「服務狀態未查，角色只報安裝狀態」）。第三個參數是刻意設計的：它強制實作者說明此次降級的影響範圍，而不只是記錄「有例外發生」。

### 4.5 失敗隔離的層次

本專案對失敗處理有三個層次，各有明確的分工：

**事實層的降級。** 單一來源失敗時，該組事實以 `ReadError` 或 `InsufficientPrivilege` 的可用性值呈現，其餘事實照常。這是數量最多的情形。

**子系統層的斷路器。** 對於已知可能造成長時間阻塞的來源，設定斷路器（`StorageProbeBreaker` 為其實例之一）。斷路器在偵測到重複失敗或逾時後，於本次執行中停止再嘗試該來源，並將狀態記為「已停用」，避免同一個失敗來源被反覆探測而拖垮整體載入時間。

**製程層的例外記錄。** 未接住的例外寫入 `CrashLog`，與 `diag.log` 同置一資料夾，供使用者回報問題時一併附上。

三個層次的區分標準是**影響範圍**：事實層處理單一讀值的失敗，斷路器層處理一個來源的持續性失敗，製程層處理程式本身的缺陷。任何新增的失敗處理都應歸入其中一層，而非新增第四種機制。

## 第五章　事實收集管線

### 5.1 管線的組成

事實從硬體到使用者介面之間經過以下階段：

```
來源讀取 → 解碼 → 事實產生 → 快照聚合 → 對帳 → 呈現／匯出
```

**來源讀取**是最具平台相依性的一段，涉及驅動 IOCTL、WMI 查詢、API 呼叫與檔案解析（如事件記錄、登錄檔、`setupapi.dev.log`）。此階段的原則是不進行解讀，只取得原始位元組或原始字串。

**解碼**是純函式階段，輸入原始資料、輸出結構化欄位。此階段被刻意隔離為 `XinSpect.Decoders` 類別庫，因為它是唯一可以完全脫離作業系統進行測試的部分，因而適用突變測試（2.7）。解碼器必須攜帶規格引用註記，說明其位元配置的依據。

**事實產生**把解碼結果轉為 `HardwareFact`，並賦予可信層級與可用性。此階段是「量測」與「自述」的分野所在：同一個數值若來自暫存器直讀則為 `Measured`，若來自 SMBIOS 欄位則為 `Reported`。

**快照聚合**把全部事實收斂為一次載入的完整集合，附帶量測時間。快照是時間膠囊與歷史比對的輸入單位。

**對帳**以規則為單位檢查跨來源的一致性（第三部）。

**呈現與匯出**包含介面、HTML 報告、CLI 的 JSON 輸出與本機 API。

### 5.2 載入順序的語意依賴

載入順序並非任意，其中至少存在一條真實的順序相依，且該相依本身構成一項已知的架構缺陷。

`EvidenceCollection` 中的 `LoadServerCompliance()` 需要 `RoleFacts` 作為輸入，而 `RoleFacts` 的唯一寫入者是排在序列**較後段**的 `LoadPlatformFacts()`。這意味著在現行的循序載入順序下，伺服器合規性所看到的是**上一輪載入**所產生的角色事實，而非本次載入剛產生的。其具體影響是：在角色狀態發生變化的那一次載入中，合規性判定的輸入與同一份快照中的角色事實可能不一致。

此問題在循序載入下是穩定且可重現的（每次都是上一輪的值），因此不構成隨機性缺陷；但它是**同一份快照內部的自相矛盾**，違背了 3.1 所述「消費端一致性」的原則。本白皮書將其列為已知缺陷，其修正方向為把角色事實的載入前置於合規性判定之前，或在合規性判定中改讀取本次載入的角色事實。列出的理由是本專案對缺陷的處理原則：**發現即登記，即使不在當輪修正範圍內**。

### 5.3 載入時間的預算

載入時間是使用者對工具的第一印象，也是最容易在功能累積中失控的指標。本版對使用者模式路徑的量測結果（同一機器、暖機後）顯示，完整的 45 條載入方法合計約 5.6 秒，其中前三名為 `LoadPlatformFacts`（約 1.7 秒）、`LoadSbom`（約 1.0 秒）與 `LoadAdvancedSupplement`（約 0.7 秒）。效能工程的具體措施與其量測方法見第二十三章。

## 第六章　讀取層

讀取層是曦覽與裸硬體之間的唯一通道，也是整個專案中風險最高的部分。本章說明其結構與設計約束。

### 6.1 驅動與橋接

硬體層的讀取需要核心模式權限。曦覽不依賴第三方驅動進行存取，而是自寫白名單唯讀驅動 `XsRegProbe`，並在其上建立 `WinRing0` 風格的事實讀取層。

`XsRegProbe` 的設計是**白名單**：驅動僅處理清單中登記的暫存器存取請求，請求的暫存器位址與操作類型在編譯期固定。其契約定義於 `XsRegProbeContract`，並由測試驗證。白名單設計的三個後果：

- **攻擊面可列舉**。可存取範圍是有限的、可審閱的清單，而非任意位址。
- **擴充有成本**。新增暫存器需修改驅動與清單。此成本是刻意的：它迫使每次擴充都被記錄與審查。
- **功能邊界明確**。使用者可以確知工具能碰觸哪些暫存器，這對受管制環境是必要條件。

橋接層（`WinRing0Bridge`）負責與驅動通訊並提供型別化的讀取介面。其上分為兩條路徑：MMIO 讀取（`MmioAccess`、`WinRing0MmioReader`、`DriverMmioReader`）與 I/O 埠讀取（`IoPortAccess`、`DriverMsrReader`）。MMIO 後端另由 `MmioBackendSelector` 選擇，因為不同平台的記憶體映射存取方式可能有差異。

### 6.2 SMBus 存取

記憶體模組的 SPD 與溫度感測器（TSOD）位於 SMBus 上。其存取由一組模組分工完成：`SmbusController` 與 `ImcSmbusController` 處理控制器層，`SmbusBusLock` 處理匯流排層的互斥，`SpdReader`／`SpdBus` 處理讀取，`SpdDecoder`／`SpdDetailDecoder` 處理解碼，`TsodSurveyor` 處理溫度感測器盤點，`ImcSmbusDiscovery` 處理控制器的發現。

匯流排互斥（`SmbusBusLock`）不是可選的最佳化，而是正確性要求：SMBus 是共享匯流排，同時存取會產生不可靠的讀值。此處的設計約束是，互斥必須在程序內有效，因為同一台機器上可能有其他監控軟體也在存取同一條匯流排——這是本專案在真機測試中遭遇過的實際情形。

### 6.3 逾時與不可回復性

讀取層最實際的風險不是讀到錯誤的值，而是**讀取操作本身卡住**。裝置 IOCTL 在驅動異常時可能長時間不返回，而部分硬體存取操作一旦觸發即無法取消。因此：

- 可能阻塞的讀取一律設有逾時，逾時後以 `ReadError` 呈現並記錄於 `Diag`。
- 已知高風險來源由斷路器保護（見 4.5），在重複失敗後停止嘗試。
- 載入序列把高風險查詢排在後段（見 4.3），使介面在先前的階段即可使用。

這些措施的目的是把「單一來源異常」的影響限制在該來源，而非擴散至整個應用程式的可用性。

### 6.4 唯讀性與寫入閘門

讀取層的預設立場是唯讀。需要寫入的功能（例如風扇策略套用）必須經由 `WriteGate`，並在介面上經由一致性的同意流程（`CeremonyService`）取得使用者授權。寫入操作在介面上必須明確標示其影響範圍與風險，這是 2.6 所述原則的實作。

## 第七章　來源分層與其判讀意涵

### 7.1 硬體層：直接量測

硬體層的事實具有最高可信層級 `Measured`，因為它們不經過任何中介的描述。其具體來源包括：

| 來源 | 讀取方式 | 典型事實 |
|---|---|---|
| MSR | 驅動讀取型號特定暫存器 | 微碼版本（逐核）、頻率與倍頻、電源狀態、溫度上限 |
| PCI／PCIe 設定空間 | 設定空間讀取 | 裝置識別、鏈路寬度與速度、能力暫存器、BAR 資源 |
| SMBus SPD | 匯流排讀取 | 記憶體模組的製造商、料號、序號、標稱與實際時序 |
| ATA SMART | 裝置命令 | 通電小時、累計寫入量、通電次數、屬性集的完整清單 |
| NVMe 健康紀錄 | 裝置命令 | 已用壽命百分比、累計寫入資料量、不安全關機次數、關鍵警告 |
| Super I/O | I/O 埠存取 | 風扇轉速、溫度、電壓、輸入電壓 |
| CMOS | I/O 埠存取 | 開機設定相關的少量持久值 |

硬體層的判讀意涵是：**這些值最難在不被察覺的情況下偽造**，因為它們位於裝置的持久性記錄或矽晶的行為中。快閃記憶體內容的雜湊、微碼版本的一致性、SMART 與 NVMe 的累計計數器，這三類證據構成驗機時最有價值的部分。

### 7.2 韌體層：平台的自我描述

韌體層的事實可信層級為 `Reported`。其來源包括：

- **ACPI 表**：機器的平台描述。本專案解碼的表包括 MCFG（PCIe 記憶體映射組態）、HEST（硬體錯誤來源）、BERT（開機錯誤記錄）、SLIT（系統局部性）、CEDT（CXL 早期發現）、HPET（高精度事件計時器）、FPDT（韌體效能資料）、FADT（固定 ACPI 描述表）等。ACPI 表的解碼包含逐表的檢查和驗證。
- **SMBIOS 結構**：機器的資產與組態描述，包括系統、主機板、機箱、處理器、記憶體裝置（Type 17）、記憶體陣列、以及帶外管理（Type 38）等條目。
- **UEFI 變數**：開機組態與安全狀態，包括 Secure Boot 相關變數、啟動選項、以及變數的屬性（唯讀、非揮發、開機時存取等）。

韌體層的判讀意涵是：**它描述的是「平台聲稱的機器」，而非必然是「實際的機器」**。更換過元件而未更新 SMBIOS、或是經過韌體修改的機器，其韌體層陳述會與硬體層量測不符。此落差本身即為可陳述的事實，也是對帳引擎的主要輸入來源之一。此外，`FADT` 與 `HPET` 的宣告值可與實際計時行為比對，`BERT` 的存在與內容可與開機錯誤時間軸對照。

### 7.3 作業系統層：最易取得亦最易改寫

作業系統層的事實可信層級為 `Reported`，其來源包括：

| 來源 | 內容 | 改寫難度 |
|---|---|---|
| WMI（CIM 與 MSFT 進階類別） | 系統、處理器、記憶體、儲存、網路、顯示、電源、安全等 | 中——提供者可替換 |
| 登錄檔 | 驅動設定、裝置列舉、政策、資產標記 | 低——可直接編輯 |
| 事件記錄 | 系統、應用程式與安全性事件 | 中——可清除且有稽核痕跡 |
| 效能計數器 | CPU、磁碟、網路、記憶體的即時與累計計數 | 中 |
| ETW 追蹤 | 核心與提供者的事件串流 | 中—需權限 |
| X509 憑證存放區 | 憑證與其屬性 | 中 |

作業系統層的判讀意涵是：**這一層最容易取得，也最需要交叉驗證**。一個經過改寫的系統可能在其登錄檔與 WMI 中一致地回報錯誤的資訊（因為兩者可能來自同一份被修改的資料）。因此曦覽對這一層的事實維持 `Reported` 標記，並在對帳規則中優先與硬體層或韌體層的事實交叉。當作業系統層與硬體層矛盾時，其診斷價值遠高於兩個作業系統層來源之間的矛盾。

### 7.4 三層交叉的實例

以記憶體為例說明三層的實際交叉方式：

- 硬體層可從 SPD 讀出每條模組的製造商、料號、序號、標稱速度與實際運行的速度（後者亦可由 MSR 或記憶體控制器暫存器驗證）。
- 韌體層的 SMBIOS Type 17 提供每條模組的裝置描述，Type 16 提供記憶體陣列的宣稱上限與插槽數，並可宣告錯誤更正型別。
- 作業系統層的 WMI 提供記憶體總量與部分組態資訊。

三層交叉可產生的事實包括：各條模組是否同批（硬體層比較製造商與料號）、序號欄位是否為空或全零（硬體層）、實際運行速度是否低於標稱（硬體層內部交叉）、模組的實體位元寬度是否大於資料寬度（用以驗證 ECC 的存在，硬體層）、以及韌體宣稱的 ECC 型別是否與模組實際一致（韌體層與硬體層交叉）。這些檢查分別對應規則 `R-MEM-01` 至 `R-MEM-05`，逐條說明見第九章。
