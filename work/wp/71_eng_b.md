## 第四十二章　解碼器與規格依據

### 42.1 解碼在管線中的位置

事實的產生分為三個階段：來源讀取、解碼、事實產生。解碼是其中唯一可完全脫離作業系統與硬體的部分，因此它是本專案中品質保證投入最集中的一段。

解碼的輸入是原始位元組或原始字串，輸出是結構化欄位。例如 ACPI 表的解碼輸入是表的位元組內容，輸出是各欄位的值與其語意；SMBIOS 結構的解碼輸入是結構的位元組序列，輸出是各欄位的值；SPD 的解碼輸入是模組 EEPROM 的內容，輸出是時序與識別資訊。

### 42.2 為何把解碼獨立為類別庫

解碼器獨立為 `XinSpect.Decoders` 類別庫的理由有三。

**其一，可突變測試。** 突變測試需要對程式碼進行反覆的微幅修改並重跑測試。若解碼器散落在依賴作業系統的模組中，每次突變都需要載入整個應用程式，成本使其不可行。獨立類別庫使突變測試可以只針對解碼邏輯進行。

**其二，可金標向量測試。** 解碼器的輸入輸出對應明確，因此可以用人工手算的位元組序列作為測試輸入。此測試不依賴任何環境條件，可在任何機器上執行。

**其三，邊界清晰。** 把解碼與 I/O 分離使兩者的職責明確：解碼器不得進行 I/O，I/O 模組不得進行解碼。此約束使「量測邏輯」與「資料取得」的測試策略可以不同，並使兩者的缺陷不會互相掩蓋。

### 42.3 解碼器的通則

本專案的解碼器遵循以下通則，這些通則來自實際遭遇的失效模式。

**通則一：先驗證結構特徵，再套用解析規則。** 以 SPD 為例，DDR3、DDR4 與 DDR5 的 SPD 結構不同。若以錯誤版本的規則解析，會產生看似合理但完全錯誤的值。因此解碼器必須先驗證結構特徵（例如 DDR4 的固定位元組簽章與 DDR5 的結構標記），驗證失敗即輸出無法判定，而非以預設版本強行解析。

此通則的一般形式是：**解碼器的第一步是判斷「這是不是我可以解的東西」。**

**通則二：缺失欄位必須有地方標示缺失。** SMBIOS 的解析是典型的例子：欄位集由規範定義，但實際的結構中可能缺少部分欄位。若缺失欄位不被產生為事實，該欄位在報告與覆蓋申報中會完全消失，使用者無法區分「此機器沒有這個欄位」與「工具沒有讀取這個欄位」。因此缺失欄位產生一筆標示缺失的事實（此設計對應動態家族 `asset.field.` 的登記理由）。

**通則三：攜帶規格引用。** 解碼器必須攜帶 `SpecRef` 註記，指向該欄位在規格書中的章節。此要求的理由見 2.2：一個不記錄依據的解碼器，其正確性無法被複核。此註記由反映式機器檢查強制。

**通則四：不做跨欄位的語意推斷。** 解碼器的職責是依規格把位元轉為欄位，而不是推斷欄位的意義。例如 NVMe 的關鍵警告欄位應被解碼為其位元組合，而非被解碼為「這顆碟有問題」——後者是判讀，屬於對帳層或呈現層的工作。

此通則的邊界需要說明：**格式層級的推斷是允許的**（例如「此位元組的存在與否決定欄位的解讀方式」），因為那是規格本身的一部分；**語意層級的推斷則不允許**。

**通則五：不吞掉無法解釋的位元。** 若解碼器在結構中遇到無法解釋的位元或區段，應保留其原始內容或明確標示未解析的部分，而非忽略。原因是：無法解釋的位元可能是有意義的（新的欄位、廠商自訂的擴充、或是內容被修改的痕跡）。

### 42.4 主要解碼器的規格依據

本專案的主要解碼器及其規格依據如下：

| 解碼器 | 輸入 | 規格依據 |
|---|---|---|
| `SpdDecoder`／`SpdDetailDecoder` | 記憶體模組的 EEPROM 內容 | JEDEC SPD 規範（DDR3／DDR4／DDR5 各自的版本） |
| `NvmeLogDecoder` | NVMe 控制器的日誌頁 | NVMe 基礎規格（SMART／健康資訊日誌、錯誤資訊日誌、韌體插槽資訊日誌） |
| `NvmePowerDecoder` | NVMe 的電源狀態描述 | NVMe 基礎規格（電源狀態描述元） |
| `AtaIdentify` | 裝置的 IDENTIFY 資料 | ATA／ATAPI 指令集（IDENTIFY DEVICE 的欄位定義） |
| `SmbiosFacts`／`SmbiosDeepFactsService` | 系統管理 BIOS 的結構 | SMBIOS／DMI 規範（各結構類型的欄位定義） |
| ACPI 表解碼器群 | 韌體提供的表 | ACPI 規範（各表的欄位定義，含 FPDT、PPTT、HEST、BERT、SLIT、CEDT、MCFG、HPET 等） |
| `PcieLinkDecoder` | PCIe 的鏈路能力與狀態暫存器 | PCI Express 基礎規格（鏈路能力與鏈路狀態暫存器） |
| `ResizableBarDecoder` | PCIe 的 BAR 大小暫存器 | PCI Express 基礎規格（可調整大小 BAR 能力結構） |
| `UsbLinkDecoder` | USB 埠的狀態暫存器 | USB 規範（埠狀態與協商速率） |
| `NetAdapterDecoder` | 網路介面的描述結構 | 作業系統提供的介面描述與其欄位語意 |
| `DriverAuditDecoder` | 驅動程式的檔案屬性與簽章資訊 | 作業系統的驅動程式簽章模型 |
| `BootBreakdownDecoder` | 韌體效能資料與開機記錄 | ACPI FPDT 與作業系統的開機記錄格式 |
| `CoreTimeDecoder` | 核心時間來源的暫存器 | 平台計時器規格（HPET、PM Timer） |
| `PowerPolicyDecoder` | 電源計畫的組態 | 作業系統的電源管理模型（電源計畫的設定結構） |
| `InvisibleStallDecoder` | 排程延遲的量測資料 | 本專案自訂的量測方法（非外部規格） |
| `CeilingDecoder` | 效能上限的量測資料 | 本專案自訂的量測方法（非外部規格） |
| `LicenseDecoder` | 授權狀態的資料 | 作業系統的授權模型 |
| `BiosMeDecoder` | 管理引擎的區段 | 平台廠商公開的區段描述 |
| `DisplayLinkDecoder` | 顯示連結的描述 | 顯示介面的規格與作業系統的描述結構 |
| `MachineAgeDecoder` | 機器年齡的推定輸入 | 本專案自訂的推定方法（非外部規格） |
| `LargePageDecoder` | 大頁組態 | 處理器與作業系統的分頁模型 |

此表中，部分解碼器的規格依據為本專案自訂的量測方法而非外部規格。此區分在 `SpecRef` 的註記中明確標示：註記為外部規格時指向規格章節，為自訂方法時指向本專案的方法論文件。此區分的重要性在於**可複核性的對象不同**：前者的正確性可由規格複核，後者只能由方法論與量測自驗複核。

### 42.5 解碼器的測試形態

解碼器的測試以三種形態組成：

**單一欄位的金標測試。** 以人工建構的位元組序列輸入，驗證單一欄位的解析。此類測試的輸入通常只包含該欄位附近的位元組，其餘以固定值填充。

**完整結構的金標測試。** 以完整的結構輸入，驗證所有欄位的解析。此類測試的輸入來自規格範例或真機擷取，並經人工核對。

**邊界與異常輸入測試。** 空輸入、截斷的輸入、結構特徵不符的輸入、以及欄位值為極端值的輸入。此類測試驗證的是通則一所述的結構驗證與通則二所述的缺失標示。
