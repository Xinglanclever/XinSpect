## 第五十章　疑難排解與常見誤判

### 50.1 排解的順序

遇到「某個欄位沒有值」的情形時，排解的順序應由外而內：先確認環境條件，再確認工具狀態，最後才懷疑硬體。此順序的理由是前兩者的機率遠高於第三者。

**第一層：環境條件。** 是否以足夠的權限執行？是否在虛擬機中執行（部分事實本就不可用）？殺毒或端點防護軟體是否阻擋了驅動的載入？

**第二層：工具狀態。** 是否有診斷紀錄？是否有未接住的例外紀錄？驅動是否已載入？

**第三層：硬體與平台。** 此項目是否在本平台上存在？裝置是否已連接？

此順序對應 43.2 與 43.3 所述的分類：多數的「沒有值」屬於第一級或第二級的失敗，其原因通常在環境或工具層。

### 50.2 常見現象與其成因

**現象：多個欄位同時沒有值，且可用性為權限不足。**
成因：未以系統管理員權限執行。此類事實集中於需要 Ring-0 存取的項目（微碼版本、PCI 設定空間、SPD、Super I/O）。

**現象：某個 WMI 來源的全部事實都沒有值。**
成因：WMI 提供者異常，或該命名空間在此系統上不可用。此時同一來源的多個事實會**整體**失敗（見 43.3）。

**現象：載入時間異常長。**
成因：某個來源的存取阻塞。此時應檢視診斷紀錄與斷路器的狀態（見 43.4）。若某來源已被斷路器停用，其事實會以讀取失敗呈現。

**現象：某個感測器的讀值長時間不變。**
成因：感測器未連接或未被驅動程式正確初始化。此為 `SensorSanity` 處理的情形（見 12.1）。使用者應注意此讀值可能不是真實的溫度。

**現象：記憶體插槽數為 0 或空白。**
成因：記憶體陣列的 SMBIOS 結構（Type 16）不存在於此系統，或讀取失敗。**此情形不應解讀為「沒有記憶體插槽」**（見 2.1）。可用性欄位會指出原因。

**現象：SMBIOS 的某些資產欄位為空白。**
成因：該欄位在結構中不存在。此情形由動態家族 `asset.field.` 的設計處理（見 16.5）：缺失欄位產生一筆標示缺失的事實，使「此機器沒有這個欄位」與「工具沒有讀取這個欄位」可區分。

**現象：PCIe 鏈路的寬度低於顯示卡的能力。**
成因包括：插槽的實體佈線限制（x16 插槽實際只有 x4 的佈線）、電源管理設定、訊號完整性問題、以及轉接卡或延長線的品質。規則 `R-LNK-01` 陳述落差，其成因需進一步查證（見 9.5）。

**現象：儲存裝置的已用壽命為 0%，但機器有使用痕跡。**
成因：控制器韌體重設了壽命計數器。規則 `R-SSD-02` 以累計寫入量對照此值（見 9.2）。

**現象：無法讀取 TPM 的狀態。**
成因：TPM 在韌體中未啟用、被作業系統停用、或管理權限不足。**「無法讀取 TPM 狀態」與「TPM 未啟用」是不同的結論**（見 1.3）。報告會區分兩者。

**現象：事件記錄顯示沒有錯誤。**
成因：事件記錄可能已被清除，或其保存範圍已被新事件覆寫。**「沒有錯誤」不等於「未曾發生錯誤」**（見 37.7）。

**現象：開啟本機 API 後無法連線。**
成因：HTTP 監聽殼預設不啟動（見 17.7、20.2）。此為刻意的設計決定，其理由為「開啟監聽等同於新增本機攻擊面，屬使用者決定」。headless 的替代出口是命令列介面的 `--json evidence`。

### 50.3 診斷紀錄的閱讀

診斷紀錄（`diag.log`）的每一行包含四個欄位：時間、發生位置的短標籤、例外型別與訊息、以及對使用者的後果（見 2.1）。

閱讀的順序為：先看**後果**欄位（它說明此次降級的影響範圍），再看**位置**欄位（它說明失敗的來源），最後看例外本身的訊息（它說明失敗的技術原因）。

末接住的例外記錄於 `CrashLog`（見 4.5）。兩份紀錄同置一資料夾，回報問題時應一併附上。

### 50.4 回報問題時應提供的資訊

由本專案的診斷設計可推得有效回報所需的資訊：

- **診斷紀錄與當機紀錄**（見 50.3）。
- **工具版本與作業系統版本**（決定有哪些事實被蒐集、有哪些機制可用）。
- **執行環境**（權限層級、是否在虛擬機中）。
- **具體的現象**（哪個欄位、其可用性值、以及預期的行為）。
- **時間膠囊或匯出檔**（若現象可從事實集合觀察）。

第四項的重要性在於：由於工具區分四種不可用狀態，因此「某欄位沒有值」不是一個完整的描述——其可用性值才是關鍵資訊。

### 50.5 排解的限制

**無法從使用端診斷的缺陷。** 部分缺陷只能由開發者診斷（例如解碼邏輯的錯誤）。此時診斷紀錄與匯出檔是唯一的線索。

**環境相依的現象。** 部分現象僅在特定硬體或驅動版本上出現，其重現需要對應的環境（此即 25.2 所述限制的實務表現）。

**刻意的不作為所產生的現象。** 部分「無法使用」是刻意的設計決定（例如本機 API 的監聽殼不啟動、部分功能不做）。這類情形應在文件中明示而非留給使用者排解，本專案的處理方式是將這類決定登記於判斷的登記表（見 17.7）與豁免清單（見 10.3）。
