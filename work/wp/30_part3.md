# 第三部　交叉對帳

## 第八章　對帳引擎

### 8.1 引擎的職責與非職責

對帳引擎的職責是：在事實齊備的前提下，依既定規則比較多個來源對同一件事的陳述，並輸出相符、矛盾或無法判定。其非職責是明確的：

- 不輸出分數、等級或綜合評價。
- 不預測、不外推。
- 不在事實不齊備時猜測。
- 不把「不適用」判定為「符合」。

最後一項尤其重要。一台沒有電池的桌上型機器，其電池相關規則的輸入事實可用性為 `NotApplicable`；引擎回報的應是「無法判定」並說明原因，而非「符合」。在批量稽核中，把「不適用」計入「無異常」會系統性地高估設備的健康程度。

### 8.2 規則型別

一條規則以 `VerifyRule` 記錄表示，其欄位為：

| 欄位 | 語意 |
|---|---|
| `Id` | 規則識別碼，如 `R-MEM-01`；`R-` 後為分區縮寫，其後為序號 |
| `Part` | 分區名稱，現有記憶體、儲存裝置、電池、處理器、PCIe 鏈路五個分區 |
| `Title` | 規則標題，即該規則所檢查的命題 |
| `RequiredFacts` | 所需事實清單；不足時引擎自行判定為無法判定 |
| `Evaluate` | 判定函式，輸入為齊備的事實集合，輸出為判定結果 |
| `Scope` | 作用域：整機或逐碟 |

`RequiredFacts` 的設計意義值得說明。若引擎不負責前置檢查，每條規則的判定函式都必須自行處理「值為空」的情形，這會產生兩類缺陷：一是各規則對缺值的處理不一致，二是部分規則在缺值時意外走入某個分支而輸出錯誤判定。把前置檢查集中在引擎後，規則實作只需處理資料齊備的情形，缺值路徑在全域被一致地處理。

引擎的實作在 `VerifyFacts` 上操作，該型別提供型別化的取用（`Get`、`Num`、`Text`）與存在性檢查（`Has`）。缺少的事實以 `FactCatalog` 的顯示名與權限需求補足，因此輸出的「無法判定」能夠具體說明缺少的是什麼、以及如何才能讀到（例如需以系統管理員權限執行）。

### 8.3 作用域

規則分為兩種作用域：

**整機作用域**的規則對整個系統執行一次，例如處理器相關規則與記憶體相關規則。

**逐碟作用域**的規則對每一顆儲存裝置各執行一次。這是因為儲存裝置的健康狀態本質上是逐裝置的：一台機器上可能同時存在一顆全新的固態硬碟與一顆經過翻新的舊碟。逐碟作用域使問題碟能夠被個別指出，而非在整機層級被平均掉。

### 8.4 判定的三方語意

| 判定 | 觸發條件 | 輸出內容 |
|---|---|---|
| 相符 | 所需事實齊備且各來源一致 | 判定與簡要理由 |
| 矛盾 | 所需事實齊備且各來源不一致 | 判定、說明、以及具名的證據清單 |
| 無法判定 | 所需事實不齊備 | 判定、缺少的事實名稱、取得該事實所需的條件 |

矛盾的輸出必須包含證據清單（`VerifyFinding` 的證據欄位）。證據的形式是參與判定的原始事實值，因此使用者可以在不信任工具判定的情況下，直接檢視造成矛盾的值本身。這是 1.1 所述「可複核的陳述」原則在對帳層的落實。

## 第九章　規則逐條說明

本章逐條說明本版 18 條規則的命題、輸入、判定邏輯與實務意涵。規則的完整索引見附錄 C。

### 9.1 記憶體分區（五條）

**`R-MEM-01`　各條記憶體模組並非同批。**
輸入：模組數、各條模組製造商、各條模組料號。判定：若模組數少於 2，判為相符，理由為「只有一條模組，無從混批」；否則比較製造商與料號的清單，若存在不一致即判為矛盾，說明為「製造商或料號不一致，這幾條不是同一批出廠的模組」。實務意涵：混批不必然是問題，但它是擴充、更換或拼裝的跡象。此規則刻意不下價值判斷，只陳述不一致。

**`R-MEM-02`　記憶體模組序號異常。**
輸入：模組數、各條模組序號。判定：檢查序號欄位是否存在空值、或是否出現多條模組共用同一序號的情形。實務意涵：SPD 中的序號由模組廠在生產時燒錄，正常情形下每條模組的序號唯一。序號為空或重複，是模組非原廠料件或 SPD 內容被改寫的跡象。

**`R-MEM-03`　記憶體未跑在標稱速度。**
輸入：模組標稱速度（SPD 宣告）、模組實際運行速度（記憶體控制器組態）。判定：比較兩者，實際低於標稱即判為矛盾。實務意涵：此落差在實務上有多種成因，包括 BIOS 設定、平台限制、混插不同速度的模組、以及記憶體控制器降頻。工具陳述落差，不推定成因——這是刻意的，因為成因的判斷需要機器以外的資訊（例如使用者是否更動過設定）。

**`R-MEM-04`　記憶體陣列宣稱與實際安裝對不上。**
輸入：已安裝記憶體總量、記憶體陣列宣稱上限、記憶體插槽數、模組數。判定：檢查已安裝總量是否超過陣列宣稱上限（邏輯不可能，指向來源錯誤或改寫），以及模組數與插槽數的關係是否合理。實務意涵：陣列宣稱上限來自 SMBIOS Type 16，由韌體填寫。若實際安裝量超過該上限，最可能的情形是韌體的描述未更新，其次是 SMBIOS 內容被改寫。兩種情形都值得指出。

**`R-MEM-05`　宣稱 ECC 與模組實際位元寬度對不上。**
輸入：記憶體陣列宣稱的錯誤更正型別（SMBIOS Type 16）、模組是否帶 ECC 位元（由模組的總寬度大於資料寬度判定，屬硬體層量測）。判定：宣稱具備 ECC 而模組實體不具備 ECC 位元，即判為矛盾。實務意涵：此規則的價值在於它是**韌體宣告與硬體事實的直接對比**。ECC 相關的錯誤宣告在伺服器採購中具有實質影響（ECC 記憶體與非 ECC 記憶體的成本差異顯著），因此這一條是伺服器驗機中價值最高的對帳之一。

### 9.2 儲存裝置分區（六條，逐碟）

以下六條規則對每一顆儲存裝置各執行一次。翻新碟幾乎都會在這幾條對帳上留下痕跡，這是本分區在驗機場景中的主要價值。

**`R-SSD-01`　通電小時與累計寫入量對不上。**
輸入：NVMe 累計寫入資料量、NVMe 通電小時。判定：計算每小時的平均寫入量，若超出合理區間即判為矛盾。實務意涵：此規則偵測的是**計數器被重設**。若一顆碟的通電小時被歸零而累計寫入量保留（或反之），兩者的比值會明顯偏離正常範圍。控制器韌體在重設其中一個計數器時，未必會同步處理另一個，因此這個比值是有效的偵測手段。

**`R-SSD-02`　已用壽命與累計寫入量對不上。**
輸入：NVMe 已用壽命百分比、累計寫入資料量。判定：已用壽命為零或極低、而累計寫入量已相當可觀時判為矛盾。實務意涵：「已用壽命 0%」是翻新碟最常見的宣稱。此規則把該宣稱與累計寫入量對照，因為後者的歸零在部分控制器上會留下其他痕跡（例如通電小時、通電次數的不一致）。

**`R-SSD-03`　不安全關機次數多於通電次數。**
輸入：NVMe 不安全關機次數、通電次數。判定：前者大於後者即判為矛盾。實務意涵：兩個計數器在邏輯上有包含關係（每次不安全關機必伴隨一次通電），因此前者大於後者是**邏輯不可能**的情形，指向計數器被修改或其語意被誤解。這類「邏輯不可能」的判定比「數值異常」的判定更為可靠，因為它不依賴對正常範圍的估計。

**`R-SSD-04`　NVMe 回報關鍵警告。**
輸入：NVMe 關鍵警告欄位。判定：該欄位非零即判為矛盾。實務意涵：關鍵警告位元涵蓋備用空間耗盡、溫度超過門檻、可靠度下降、唯讀模式等情形，由裝置自行判定。此規則不多做解讀，直接把裝置的自陳述呈現出來。

**`R-SSD-05`　宣稱容量與可定址容量對不上。**
輸入：磁碟宣稱容量、ATA 可定址 LBA 總數。判定：由 LBA 總數與磁區大小算出的實際可定址容量與宣稱容量不符即判為矛盾。實務意涵：此規則偵測 HPA（Host Protected Area）與 DCO（Device Configuration Overlay）造成的容量隱藏，以及容量標示的不實。容量落差在部分情境下有合法用途（例如廠商保留區），因此規則的輸出包含具體的落差數值，供使用者判斷。

**`R-SSD-06`　宣稱轉速與屬性集矛盾。**
輸入：標稱旋轉速率、是否存在機械專屬的 SMART 屬性。判定：宣稱具備旋轉速率（機械碟）但屬性集中缺乏機械碟專屬屬性（如主軸起轉相關屬性），或反之，即判為矛盾。實務意涵：此規則偵測**裝置種類的偽裝**——以固態硬碟冒充機械硬碟或反之。屬性集是硬體層量測，難以倖免。

### 9.3 電池分區（一條）

**`R-BAT-01`　電池滿充容量明顯低於設計容量。**
輸入：電池設計容量、電池滿充容量。判定：兩者的比值低於門檻時判為矛盾。實務意涵：兩者的比值即電池的健康度。設計容量由電池的控制器宣告且通常固定，滿充容量隨使用而下降。若比值異常低，代表電池已明顯損耗。此規則的價值在於它是**單一子系統內部的交叉**，不需要第二個來源。

### 9.4 處理器分區（五條）

**`R-CPU-06`　各核心微碼版本不一致。**
輸入：逐核微碼版本（由 Ring-0 逐核心讀取 MSR 取得）。判定：各核心的微碼修訂版本不一致時判為矛盾。實務意涵：微碼在開機時統一載入，正常情形下所有核心的版本相同。不一致的情形指向：混合了不同步進的晶片（多處理器或拼裝）、微碼載入過程異常、或讀取路徑本身有問題。這是本專案中少數以逐核心粒度進行的檢查，也是驗機時最有價值的證據之一，因為微碼版本是硬體層事實。

**`R-CPU-02`　品牌字串帶工程樣品標記。**
輸入：處理器品牌字串。判定：字串含工程樣品（Engineering Sample）標記時判為矛盾。實務意涵：工程樣品晶片在市場上偶爾以正常品名義流通，其特性（穩定性、保固、可超頻性）與量產品不同。此規則的輸入來自 CPUID 的直接回報，不易偽造。

**`R-CPU-03`　快取層級異常。**
輸入：L3 快取容量、L2 快取總量、實體核心數、是否為混合架構。判定：快取容量與核心數的關係是否符合該微架構的預期，並考慮混合架構（效能核與效率核的快取配置不同）的情形。實務意涵：此規則偵測快取相關的偽造與拼裝，例如以較低階型號冒充較高階型號。因涉及微架構知識，此規則的判定邏輯較為複雜，也因此更需要避免在缺乏該微架構資料時輸出錯誤判定。

**`R-CPU-04`　偵測到虛擬層，讀值可信度下降。**
輸入：是否偵測到虛擬層（CPUID 的 hypervisor 位元）。判定：偵測到虛擬層時判為矛盾。此規則的語意與其他規則不同：它輸出的是**方法論警告而非硬體異常**。在虛擬機器中，硬體層的許多讀值（MSR、PCI 設定空間、感測器）由虛擬層提供，不一定對應實體硬體。因此此規則的作用是提醒使用者：同一份報告中的其他「量測」值可能並非實體硬體的直接量測。這是本專案把「工具自身的可信度條件」也納入對帳的實例。

**`R-CPU-05`　矽晶基礎頻率與宣稱值對不上。**
輸入：由矽晶參數推算的基礎頻率、CPUID 0x16 回報的宣稱基礎頻率。判定：兩者不符時判為矛盾。實務意涵：前者由最大非睿頻倍頻與 BCLK 推算，屬 `Derived`；後者由處理器直接回報，屬 `Measured`。這一條是驗機中偵測改標的關鍵規則，因為型號的偽造通常需要同時修改品牌字串與頻率相關欄位，而矽晶實際的倍頻表不易修改。

### 9.5 PCIe 鏈路分區（一條）

**`R-LNK-01`　PCIe 鏈路寬度低於裝置能力。**
輸入：當前鏈路寬度、裝置最大鏈路寬度、當前鏈路速度、裝置最大速度。判定：整機取最劣的一條；當前值低於裝置能力即判為矛盾。實務意涵：鏈路降速或降寬在功能上仍可運作，因此作業系統層往往回報「正常」。其成因包括插槽的實體限制（例如 x16 插槽實際只有 x4 的佈線）、電源管理設定、訊號完整性問題、以及轉接卡或延長線的品質。此規則的價值在於它是**設定空間層的直接量測**，不依賴效能測試，因而判定迅速且不產生系統負載。

## 第十章　覆蓋申報、鍵目錄與動態家族

### 10.1 全鍵目錄的由來

事實鍵的完整清單在編譯期固定於 `FactKeyCatalog`，本版共 844 個鍵。這個設計的直接成因是一個已修正的缺陷。

原先的實作在執行期掃描 `Services/` 目錄的原始碼以列舉事實鍵。這在開發環境可行，但在發佈版**必然失敗**：發佈版是單一執行檔，目錄中只有 `Assets/` 與執行檔本身，沒有 `Services/`。掃描失敗時程式回報「0 個鍵」，而覆蓋申報將 0 讀為「沒有任何未覆蓋的鍵」——也就是**掃不到被解讀為沒有問題**。這是本專案所定義的最嚴重錯誤類型（把「量不到」冒充為「沒問題」）的一個實例，其修正在於把鍵的全集移到編譯期，並以測試確保目錄與原始碼一致。

此後的一致性由 `FactKeyCatalogTests` 守住：測試重新掃描 `Services/` 原始碼並與目錄逐鍵比對。新增事實而忘記更新目錄會導致測試失敗。

### 10.2 動態鍵家族

全鍵目錄無法窮盡所有事實鍵，因為有一類鍵的**成員由機器決定**。匯流排上有幾張卡、Super I/O 探到哪個埠、PMU 有幾個固定功能計數器——這些在編譯期列不完，也不應假裝列得完。本版有 23 個這樣的家族，逐筆登記於 `FactKeyDynamicCatalog`，每一筆必須說明兩件事：為什麼成員是編譯期數不出來的，以及成員由什麼決定。

家族清單與理由見附錄 B。以下列舉數例說明其性質：

| 家族前綴 | 成員由什麼決定 |
|---|---|
| `pci.dev.` | 匯流排 0 上實際存在的每一張裝置一筆（成員為裝置號） |
| `sio.0x` | Super I/O 探測到的指標埠（0x2E／0x4E，或平台上實際存在的埠號） |
| `pmu.fixed.` | 固定功能計數器逐個一筆，數量由 CPUID 0x0A 的報告決定（2、3、4 個的架構皆存在） |
| `net.listen.` | 監聽埠逐埠一筆，埠集由連線表決定 |
| `tpm.replay.pcr.` | 逐 PCR 的重放結果，PCR 集由 TPM 規格與平台組態決定 |
| `reconcile.` | 對帳的結論鍵，每條規則一筆 |

`reconcile.` 家族有一項刻意的設計：對帳的**結論**不是被對帳的事實，因此它不進入覆蓋申報的分母（否則覆蓋率的分母會包含工具自身的輸出，形成自我指涉）。但它確實是執行期的真實輸出，因此在此如實登記。

動態家族的機制有兩道守門：**執行期對帳**要求任何執行期出現的鍵，要嘛在目錄全鍵中、要嘛命中某個已登記的前綴，否則紅燈；**殭屍前綴檢查**要求已登記的前綴必須在原始碼中確實有生產者，登記了卻沒人生產的前綴同樣紅燈。這兩道檢查的合稱使「鍵空間」成為一個被完整覆蓋、且可驗證的集合。

### 10.3 覆蓋申報

覆蓋申報把 844 個靜態鍵歸入三種狀態：

- **已覆蓋**：至少一條對帳規則將其列為輸入。
- **明文豁免**：刻意不對帳，且附理由。本版共 562 條。
- **未覆蓋**：既無規則考慮亦無豁免。

第三種狀態不是錯誤。本版明確**不設定覆蓋率門檻**，理由已在 2.5 說明：強制全覆蓋會產生湊數的規則，其輸出的相符判定是假訊號。

豁免的分類與代表性理由如下（完整清單見附錄 D）：

**單一來源類。** 這類事實本來就沒有第二條路徑可以交叉。例如資產識別欄位（序號、SKU、資產標籤）只有韌體一個來源；音訊端點的緩衝區配置是 `IAudioClient` 的配置結果，其與取樣率的關係是算術而非對帳；已安裝角色與功能來自選用功能與服務清單，服務狀態是同一份資料的延伸。

**刻意分開陳述類。** 例如虛擬化的三個觀測值（CPUID、選用功能、服務）是刻意分開陳述的三件事，若硬綁成一條規則，會把「已安裝但未載入」這種正常狀態判成矛盾。同理，網卡的落差已在判讀層把 PCIe 側與線路側並列，兩者本來就該不同，不構成矛盾。

**規格決策類。** 這類豁免記錄的是「明文不做」的決定，並附理由。例如規格編號 XT-003 的 REST 範例集被明文決定不做，理由是「出一份可用的範例等於提供連未承諾端點的程式碼」，其替代路徑為 CLI 的 `--json` 輸出與檔案交換。

**平台限制類。** 例如 AMD 專屬事實（SMU、PSP 的存在性）的豁免條目明記「本機為 Intel 平台，無法驗證；有真機時應補對帳規則，屆時本條豁免要移除」。這類豁免是暫時性的技術債登記，而非永久豁免。

### 10.4 申報而不強制的理由

覆蓋申報的設計原則是**只申報，不強制**。這個選擇需要說明。

在一個有 844 個鍵而只有 18 條規則的系統中，要求「每個鍵都被規則考慮」是不現實的。若把「未覆蓋」設為失敗條件，開發者的理性反應是產生一批為了降低該數字而存在的規則。這些規則的特徵是：輸入的事實組合有些牽強，判定的邏輯有些勉強，但確實能讓數字下降。它們的輸出——「相符」——是假訊號，且會在使用者心中建立「已檢查」的印象。

因此本專案的選擇是：讓未覆蓋的數量**可見且誠實**。使用者可以在報告中看到「本版有 N 個事實鍵未被任何規則考慮」，並據此判斷某個具體欄位是否經過交叉檢查。這比一個經過最佳化的覆蓋率數字有用。
