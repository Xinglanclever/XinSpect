# Part VIII — Specification library and governance

Parts I–VII describe a system that exists. Part VIII covers a different class of material: the adjudication documents the project accumulated while building it — the feature catalogue, the domain verdicts, the pipeline decision, the wiring guard and the counting ledger. These are not design descriptions but **the evidence and shape of decisions**, and they serve the same function in the project as tests do in the code: they make "how we decided" re-checkable, cross-referenceable and open to challenge.

The reason they deserve their own part is an observed failure mode: **an adjudication document that no machine reconciles will drift away from the code, and once it has drifted it does not raise an error — it quietly becomes wrong.** This part records the mechanisms that prevent that, and what they have actually caught.

## 59. The specification library's engineering contract

The project condensed its candidate capabilities, on 2026-10-10 and 10-11, into two catalogues of 300 items each — 600 in total, all written to industrial-specification depth, in `docs/INDUSTRIAL-CATALOG-2026-10-10.md` and `docs/INDUSTRIAL-CATALOG-VOL2-2026-10-11.md`. The first rule in both files is a statement of what the document is: **this is a specification library, not a work order; work starts only on circled IDs, and uncircled entries are candidates only.** This separates two things that a sufficiently detailed candidate list otherwise blurs. Candidates can be revised without implying a promise; circled items must reach implementable precision before work begins. VOL1 groups its 300 items by domain code (FW firmware and boot chain 25, CM CPU and memory 20, ST storage 20, NW network and peripherals 22, SA security audit 20, RC reliability archaeology 16, EV evidence and workflow 20, UX 18, EG strategy and engineering 30, and so on, plus GP game presentation 4). VOL2 adds 27 new domains with a further 300: AC ACPI/AML 18, SB SMBIOS/PCIe tables 15, GX GPU 14, SV server roles 14, FS file forensics 16 and others.

One design difference in VOL2 is worth noting: FS (file forensics) and DL (developer diagnostics) are marked **L2 forensic domains, opt-in by default**. That is not an ordinary priority note but a statement, inside the catalogue itself, of which line a domain's features would cross if enabled by default (see 24.2). The catalogue is thus not only a feature list but also a register of sensitivity.

**The nine fields.** Every P0 and P1 item must carry nine fields, and an item missing any of them is not at implementation precision: goal (the question answered, in one sentence); seam (the specific API, file or table); method (what is read, how, and the retry and abandon conditions); output keys (fact-key naming and value shape, to be reconciled against the catalogue); three-state behaviour (the trigger for each of the six availability states); honesty boundary (what is not done, and why — statements of the "this is a fact, not a verdict" kind written out individually); guard (test-level regression protection, at least one of the five modes in §59.7); dependencies (shared skeletons, knowledge packs, other items); acceptance (green fixture golden values plus a machine record, or an explicit not-measured declaration).

The spirit matches the fact model in Part I: **before implementation, a feature must already answer what shape its output takes, what it says when it cannot read, and who prevents it from degrading.** Deferring those three to implementation time is exactly where this project's defects have come from.

**The seam must reach API level.** The seam field carries a hard condition: work does not start until the seam is specified at API level. If a specification can only say "reads some registry value" without knowing whether it is `RegQueryValueEx` or a WMI class, or knows a metric should exist but not its offset and width, the item stays a candidate and its evidence level is marked as search-level or conjecture-level. There is a precedent: the PCH-generation decision was deliberately left undone because the register to read was not determinable, rather than guessing an offset and shipping half a feature. The concrete meaning of "rather nothing than wrong" here is that **a feature emitting a wrong value is worse than one explicitly marked unimplemented, because the former enters the user's reading process.**

**Cost, sensitivity, priority.** Cost is measured in rounds (S ≤ 0.5, M = 1, L = 2–3, XL ≥ 4), one round being one release iteration at the current pace — work anchored to a delivery unit rather than to a person-day estimate. Sensitivity has four levels and feeds directly into the anonymisation layer: **L0** hardware and version, exported by default; **L1** local metadata (paths, process names, ports), masked on export; **L2** security-relevant (accounts, credential presence, audit, listening surface), masked by default and optionally released; **L3** prohibited (passwords, keys, recovery-key **values**), which **no feature may output**, pinned by a test machine. L3 is the specification form of the data-sovereignty policy in Part V: it does not merely say "do not output" but "have a machine confirm that nothing outputs", making the prohibition a scan guard rather than an author's discipline.

**Trace model and machine reconciliation.** The catalogue uses a four-level aviation-style trace: `REQ-{ID}` (the catalogue entry) → `DESIGN` (service or decoder file) → `TEST` (test name) → `VERIFIED` (machine record or not-measured declaration). The most important property is the permissibility of an empty fourth level: **having no machine record is allowed; failing to say that there is none is not.** Beyond that, one rule pins the catalogue to the code: **every output key a specification claims must be accounted for in the key catalogue** — an extension of the existing documentation-integrity pattern whose purpose the catalogue states directly: *a specification lying is a red light, same as code lying.* Chapter 10 explains why the static key set must be fixed at compile time (a release build cannot scan sources, and a failed scan reads as full coverage); this rule supplies the other half — the code may not hold unregistered keys, and the specification may not promise keys that do not exist.

**Seven cross-cutting pieces.** All new domains must apply seven components:

| # | Component | Mandatory content |
|---|---|---|
| F1 | Read-only scan skeleton `IReadOnlyScanner` | Fixed internal order (discover → read → decode → tri-state → keys); `finally` restores any transient state; a timeout bound per step; facts obtained before an interruption are preserved |
| F2 | Tri-state/six-state contract | Reuses the availability states and the state lattice; sampled moments (processes, ports, windows) marked `Unknown` rather than passed off as `Present`; imported data starts `Unknown` |
| F3 | Specification-reference chain | Every decoder method must cite its source; **no citation, no value** |
| F4 | Knowledge-pack framework | Versioned offline snapshots (OUI, PCI, microcode CVEs, dbx, PSU models, known issues, bugcheck codes); declared SHA-256; if there is no update channel, say so |
| F5 | Anonymisation and egress permission | Every field marked L0–L3; any new egress or write path must be opt-in, user-triggered, documented as a new entry, and described honestly |
| F6 | Five guard modes | A new guard must declare its mode and the real risk it prevents; guards that cannot state one are not added |
| F7 | Audit chain and write gate | All writes accounted through the write gate; state changes recorded; evidence manifests cross-verified against the audit chain |

F1's "reads are free, writes go through the gate" and F3's "no citation, no value" restate two existing positions (2.6, 42.3). They are repeated here because they are what a new domain is most likely to lose: unlike output keys, their absence does not immediately show up in a test.

**The global dataflow.** The catalogue draws one dataflow that locates every domain: sources (WMI, MSR/MMIO, SMBus, ECAM, registry, event logs, ETW, filesystem, firmware variables, user-supplied files) all enter through the F1 skeleton; decoders are pure functions carrying citations and tested by golden values, round-trips and fuzzing; the fact layer applies the state contract, then knowledge-pack cross-checks, the rule engine and a capability matrix; then the audit chain, write gate and anonymisation; then the presentation layer; then outputs (JSON/HTML/PDF, CLI, local API, monitoring endpoint, signed bundle). This matches the architecture overview of Part II with one addition: **offline mode is listed as another shape of the source layer.** After mounting existing images, event logs, dumps or raw disks, the same decoders, the same states and the same guards apply. Offline forensics is therefore not a second subsystem but another input to one pipeline — which is why the OF domain (8 items) can exist without new architecture.

The value of the catalogue is not that it lists 600 items but that it decomposes "is this finished?" into nine answerable questions, a four-level trace and seven mandatory components. **That makes "how much have we done" and "did we do it correctly" separately askable** — the first handled by the counting discipline in chapter 65, the second by guards and reconciliation.

## 60. Domain-by-domain adjudication

`docs/CAPABILITY-DOMAINS-2026-10-09.md` records an item-by-item verdict on an external capability list. Two methodological constraints should be noted before any of its conclusions are cited. First, **the document endorses no vendor**: the existence, function and licence of each tool it mentions was not verified individually (it states plainly that its only licence lookup returned nothing usable), so the verdicts address **capability**, not products. Second, **any claim of "already integrated" cites the project's own files** — each verdict names a type, a file, or a reference count. Together these make the document re-checkable: a reader need not trust the author's knowledge of external tools, only inspect whether the project's own code does the thing in question.

**Four verdicts, with the fourth constrained.** *Already integrated* (the capability exists here and does the same thing); *integrated this round* (code moved, with new files and tests); *integrable, not done* (public specification, read-only, machine-verifiable — a gap); *not integrable* (with a reason, and the reason must be one of: hardware, licensing, conflict with a settled principle, or a different product category). That last restriction is the document's core design: **"not integrable" is not a field you may fill in freely; its reason is confined to four kinds.** Without the restriction the verdict becomes an exit available for any difficulty, and the document's value depends precisely on how narrow that exit is.

**The shape of "already integrated."** The first domain shows the sharpest disagreement with the external list. Its integrated portion is a whitelist read-only driver (12 referencing files) plus reflective loading of WinRing0 (47 files); PCI/PCIe configuration space, SMBIOS and SPD are already read. The corresponding tools in the external list are "full-access read-and-write hardware windows". Hence a key sentence: this domain **is not "not integrated" but deliberately integrated into a narrower shape.** The distinction is the document in miniature — "having the capability" and "providing it with the same permission shape" are different claims. The same structure recurs: for performance/ETW/latency, the verdict notes that the external tools' core data source is ETW and that `.etl` is an offline-parseable file format, so this is *read it yourself*, not *dispatch a tool*; for GPU, the verdict is that **this domain holds no gap worth acting on**, because the project already reads MSRs directly for throttling and power-wall attribution — more low-level than reading a third-party utility's displayed values.

**The shape of "not integrable."** The four reason kinds correspond to four irreducible limits, distributed as follows: *needs hardware* (PCIe protocol analysers, CAN bus tools, vendor RF test hardware); *needs a kernel driver or injection* (DMA memory access tools, graphics API interceptors, ARK families requiring a self-written kernel driver); *needs the network* (symbol attribution requiring a symbol server); *a different product category* (memory forensics frameworks, DFIR collection and orchestration, third-party scan engines). The second group includes **offensive memory access** and **fault injection** — judged not integrable not because it is technically impossible but because it conflicts with the read-only stance. The document thus demonstrates how a position is actually used: **settle the principles first, then use them to cut the list — rather than reading the list and then deciding what the principles are.**

**One-line conclusion.** The document compresses the whole list into one sentence: of twelve domains, **two have no gaps, five are largely integrated, three have cores belonging to a different product category or a developer toolchain, and the gaps genuinely worth acting on number four — all of them pure decoders or read-only reads, requiring no hardware, no new privilege and no third-party engine.**

**The four gaps.** *UEFI image decomposition* (FV/FFS/section tree): the specification is public, it is a pure decoder, and it needs no hardware, no new privilege and no writes. Its acceptance notes include a lesson from experience — **use a real dump as the fixture**, because the project has been burned by synthetic data on an NVMe offset; synthetic data only proves a decoder is self-consistent with its own assumptions. *Driver IOCTL and symbolic-link static analysis*: no driver loading and no IOCTL calls, hence compatible with whitelist minimalism, and cross-referenceable against the existing BYOVD blocklist; acceptance requires listing the IOCTL dispatch and device names with their `METHOD_*`/`FILE_*` flags. *`setupapi.dev.log` peripheral connection timeline*: plain text, offline, read-only; the acceptance note says **do not parse localised fields**, only the structured passages — field labels change with the system language, so parsing by label yields different results on Chinese and English systems, silently. *Reading `.etl` content back*: writing, header validation and list management already exist; what is missing is reading the content back, and undecodable events must be classified as undecoded rather than padded with zero.

**Assumptions that were overturned.** Three entries are especially useful. The plan to read Windows' built-in memory diagnostics result channel turned out to be impossible — the channel does not exist on this machine, and the document records this so that the next round does not try again: it is not "we have not done it", it is that the channel is absent. A second entry corrects the document's own earlier claim that `powercfg /energy` had been integrated; what is actually used is `/batteryreport`, and the entry adds a fact the list had missed: `/sleepstudy`, `/systempowerreport`, `/batteryreport` and `/energy` all *write report files*, unlike the project's five read-only queries, and so do not belong in the read-only section. A third records that the project already produces standard `.etl`, validates `.etl` headers and manages the list, while no part of the codebase reads the content back (a source scan returns zero hits) — "can write it, can recognise it, cannot read it back".

The common structure of these three is that **adjudication is not planning but the removal of uncertainty.** Its output includes not only a gap list but an updated list of what is *not* a problem, and the latter is often worth more.

## 61. Whitelist minimalism and dispatch admission

Placed side by side, the clearest difference between this project and an external low-level tool list is not feature count but **the shape of access**. The representative external tools offer a full read-and-write hardware window; this project offers a **whitelist read-only** path — only those read paths that have been explicitly enumerated. Many things that are "possible" in the external list are therefore deliberately not done here. The adjudication handles that gap not by arguing case by case but by raising it to a criterion and then queueing every item behind it.

**Four-tier triage.** Data is obtained in one of four ways, and the tier is settled before priority is discussed. **A: read it yourself** — the specification is public or the format is offline-parseable, so it becomes a pure decoder with no external program dispatched. **B: native seam** — the system itself offers a queryable interface, wrapped as a read-only source following the project's existing conventions. **C: dispatch needed** — considered only when A and B are both infeasible. **D: not done** — conflicts with a settled principle, or belongs to another product category. The key inference is that **an external tool having the same data is not a reason to dispatch it.** If the data source is tier A, the correct action is to read it, and at most the external tool supplies a known answer for comparison. The handling of ETW is the instance: its core source is ETW, `.etl` is offline-parseable, so the whole path is self-read.

**Three admission conditions, all required.** To stop "infeasible" from being freely defined, the document sets three conditions that must hold simultaneously: the capability has **no** stable API or public specification to read itself; the external component it needs (driver or hardware) is **already on the machine**, requiring no additional installation; and its output is **structured**, or at least does not require parsing localised text. If any condition fails, integration is the answer. The third condition extends chapter 44 directly: if the only way to obtain something is to parse text that changes with system language, the source's reliability is outside the project's control and it fails silently — field names change, output comes back empty, or results differ by locale. **Wrapping unreliable parsing as fact keys imports that uncertainty into the fact layer**, which is exactly what the six states and the citation chain exist to prevent.

**Seven cases that stay on the list as "run it elsewhere".** After the three conditions are applied strictly, the dispatch needs that remain number seven, and they share one property: the *premise* is absent rather than the criterion permitting them. Pre-boot memory testing (needs an independent boot environment, impossible in-process — the project's rowhammer and PMU probes cover the measurable part at runtime); PCIe protocol-level analysis and eye diagrams (analyser hardware); USB protocol capture (a kernel-level capture driver); CAN and fieldbus (hardware and vendor drivers); memory forensics (a different product category, and it needs a dump); per-frame graphics API capture (requires injecting the target process); BSOD symbol attribution (requires the network, which conflicts with zero upload). The last case shows the typical treatment: the project does not perform symbol attribution, but **the half that needs no symbols** — dump header, bugcheck code, module list — is made into facts and handed to gaps 1 and 2. A verdict of "not integrable" therefore does not make the path disappear; it splits it into the part this project can complete honestly and the part the user completes elsewhere.

**The honest conclusion is zero automatic dispatch.** Checking all seven against the three conditions, none passes: they remain listed because the premise is absent, not because the criterion admits them. The result is stated as *zero dispatches, seven "run it yourself in the right environment".* The shape matters: it translates "we cannot do this" into "this needs a premise this tool does not have". The former is a gap in capability; the latter is a **mismatch of premise**, and the two mean very different things to a user — the latter tells them where to go, instead of leaving them searching for a button that does not exist.

The document also states its own boundaries: it did **not** verify each tool's existence, function or licence, and it did **not** estimate cost or schedule. Declaring those limits in the file — rather than leaving them for the reader to guess — follows the same rule as the known-limitations chapter: **an unrecorded limitation becomes a disappointment; a recorded one becomes a foreseeable trade-off.**

## 62. Unified pipeline: integrate first, dispatch last

The project's master plan once said that the fact layer, reconciliation, policy and fleet were four systems. Reading the code produced a more precise description: the problem is not four subsystems but **four namespaces for the same thing.** Facts are identified by string keys (56 producers); machine verification uses an `enum` with **no correspondence** to those keys; policy scoring uses a third string syntax, with **zero references** to the fact type; the fleet layer does not exist. Three more measured divergences: fact assembly had **three paths with two key-naming schemes**; reconciliation had **two implementations** — the built-in rule set and a shipped-out JSON form, guaranteed equivalent by tests, meaning the same rule must be edited twice while one copy is unavailable to users; and policy was scattered across three services, none of them joined to the fact layer by a common interface.

This explains a specific phenomenon: coverage reporting answers "which facts did the rules touch?", but "fact" is a string key in the first namespace, an enum in the second and another string in the third — so the report can only guess by scanning sources, and **when it cannot guess, it lies.** Hence the conclusion: **this is not a single defect but the symptom of having no unified pipeline,** and the defect surfaced in the release build for a reason chapter 10 explains (a release build cannot scan sources, and a failed scan reads as full coverage).

**Dispatch institutionalises drift.** Dispatch means keeping the four subsystems separate and adding a coordinator between them that routes work (registries, adapters and middleware all count). Integration means they stop being four — one fact type, one production entry point, one pipeline. Integration was chosen not out of tidiness but because of the *shape of the risk*. Dispatch makes drift structural: keep two implementations aligned through a layer, and that layer must know what both sides look like, making it a third truth to maintain. The project has already paid this cost — the coverage report had to infer the fact layer's contents from outside. **Dispatch also fails silently:** when two implementations drift, nothing raises an error, whereas integration fails at compile time. This project's tolerance for silent failure is zero (six states, honesty boundaries, fuzz testing all exist for that). Finally, **integration makes each new feature automatically stronger**, whereas dispatch only makes it automatically more complicated — the difference is how each pays off over time as features accumulate.

**Three conditions for "integration is genuinely infeasible".** All three must hold simultaneously: the truth **does not belong to this project** (external tool output, a third-party format); it has **no public specification** to rewrite against (with a specification it should become a pure decoder, which is not infeasible); and it **must be obtained at runtime** (it cannot be turned into facts offline). If any fails, integrate. The document asks for this criterion to be written into the help and documentation, otherwise "infeasible" becomes something anyone can define for themselves — the same mechanism as the dispatch admission conditions of chapter 61, applied on the inside rather than to an external list.

**The rewritten design**, in one sentence: facts have a single type and a single production entry point, and reconciliation, verification, policy and fleet are consumers on that pipeline rather than parallel systems. Concretely: three key namespaces become one, with enumerations derived from keys rather than written separately; three assembly paths become one declaration; two rule implementations become one source, with any external form a generated product rather than a hand copy; verification rules **declare which keys they need** and treat a missing key as a state rather than introducing another identifier; policy consumes facts and emits verdicts; and the fleet becomes an offline diff of the same facts, needing serialisation rather than a new model.

**The registry is a by-product, not a substitute.** A prior debate framed registry and unification as alternatives. The conclusion is that **as long as registration happens inside the single fact-producing function, it is part of integration rather than dispatch.** The difference is who owns the list. A dispatch-style registry has facts produced by many services and a separate table saying who produces what, aligned in the middle — so the table drifts, being a second truth. An integration-style registration allows facts only through the single entry point, where the key is recorded by the type system — so there is no second truth to drift. The direction can therefore be kept, but **it must be a by-product of integration, never a replacement for it.** This generalises: when you find yourself maintaining a description *about* other components, ask first why that description cannot be a product of those components themselves.

**Four machine-checkable acceptance criteria.** Adding a fact producer changes exactly one place and it appears in reconciliation, verification, query and export; no second identifier exists (guarded by a source scan); rules have one source of truth, any external form generated and asserted equal rule by rule; and the pipeline has one entry point, with any service bypassing it going red. All four check for the presence of a *duplication*, not for code quality — the project's usual guard shape, a decidable question rather than a judgement call (22.6).

**Five slices**, ordered by risk and verifiability rather than effort: S1 move the verification enum to reference fact keys (most independent, smallest surface, and removes one identifier namespace outright); S2 collapse fact assembly into one declaration; S3 make reconciliation rules a single truth; S4 make policy consume facts and emit verdicts; S5 fleet as an offline diff, last because it needs stable keys. S1 is chosen as the starting point because it is the one slice after which **an entire identifier namespace no longer exists** — measurable, and it does not require touching all 56 producers first. The document also states its boundaries: it is a design, no code was moved; the fleet layer does not exist, so the fourth "system" is not something to integrate but something that will grow from the new model, a wording difference from the master plan; and no effort estimate is given.

## 63. The wiring guard

`docs/ROUND-WIRING-GUARD-2026-10-10.md` records a round that added no features and did one thing: turn "finished but not wired" from something people remember into something tests catch. The evidence was a re-runnable command counting production-code references to three fact services: **all three were zero.** Their unit tests were green — because **unit tests can test a service; they cannot test whether anyone calls it.**

Worse was the second layer of evidence: the fact keys belonging to those services were **already registered in the key catalogue** (three were there early, one was not). Since coverage reporting uses the catalogue as its denominator, it counted facts that were **never produced** as "already considered by a rule or explicitly exempted" — the screen gave a positive conclusion, and the conclusion was empty. This is the same disease as the documented released defect in the catalogue tests: **the report's input comes from registration, and nothing guards the gap between registration and reality.** The round therefore did not fix a service; it supplied a missing link.

The reverse gap surfaced too: the catalogue scanner recognised only four source forms, while the common "unavailable helper" pattern in services passes the key as an **argument** — a shape it could not see at all. Extending the patterns produced four keys that had producers but no catalogue entry. The fix added a constraint: only literal values containing at least one dot count, so ordinary strings are not mistaken for keys. This is the general tension of scan guards — **scan too wide and false positives train people to ignore the guard; too narrow and blind spots remain.** The balance is struck using a structural language feature (here, the key naming convention) rather than keywords.

**The guard rule** is one sentence: a public class declared in a file whose name ends in the service suffix must be referenced by production code, or the test goes red and names which one. It is a source-level guard rather than a runtime check, and the institutional reason matters: a runtime check covers only paths that execute, and "nobody calls it" leaves no trace at runtime — **a service that is never called will never fail a runtime check.**

**Three traps**, all written into the test's comments because they are endemic to this kind of guard. Comparing filenames to class names fails immediately on a file declaring two services (both already wired), so the guard now parses declared class names. **The guard can be fooled by prose:** its first version counted the navigation/documentation directory as production code, so **writing a service's name in the manual made it look referenced** — measured, it did. That directory is now excluded, with the reason recorded in the test. In general: **a guard whose criterion is "does this text appear" can be satisfied by any prose.** And **the whitelist must itself be guarded**: exceptions require reasons and have a cap (five, currently empty), because **a whitelist without a cap becomes a second source of truth in three years.**

Whether the guard has teeth cannot be settled by reading it, so a positive control was run: a temporary service file with no references was added, the guard went red and named it, and deleting the file restored green. The document is equally clear about what this proves: it was a one-off manual experiment, **not kept in the suite** (keeping it would leave a deliberately failing test forever), and it demonstrates that the guard goes red in that situation — not that it catches every missing wire.

The guard's grade is stated plainly: it checks **whether anyone references it**, not reachability. It catches "nobody calls it", not "called but never reaches the user". The latter needs three-way reconciliation between the catalogue, runtime registration and the report, and this round only achieved catalogue ≡ source scan. Marking the grade matters because **an overestimated guard reduces vigilance** — readers assume guarded areas are safe.

**Three red lights, attributed rather than fixed.** The full suite ended at 3631 total / 3 failed, and the timeline is itself evidence: at 01:32 the suite was 3629 green with exit code 0 in 57 seconds; at 01:49 the machine logged a reboot/login-phase event; afterwards the suite read 3631 / 3 failed at 1 m 51 s–2 m 1 s. Two GPU tests failed because **there is no hardware D3D11 adapter** — the machine's display adapters are all virtual. Those tests are real-hardware deep-bench tests and must fail in this environment; the round touched no D3D11 or DXGI line, so the fix is not in the code. One performance-budget test failed because **the power scheme is "power saver"**: twenty scan rounds took 74 s against a 60 s budget, while the whole suite went from 57 s to 111–121 s (about double). The handling includes three things: showing the test's path does not touch the round's changes (it calls the driver-backed reload path, which never reaches the new user-mode loaders); giving the one-line command that restores green; and **explaining why it was not run** — "that is a machine-wide setting which changes how the whole machine behaves, and I should not change it unilaterally". Together these are a pattern worth recording: **attribute, offer the fix, explain why you did not apply it.** In a project where all-green is the floor, admitting three red lights and locating each to the environment is more consistent with its culture than returning a green number nobody can explain.

The final section of the document is reserved for the author's own three mistakes, all back-filled into the original files: a **factual error in documentation** (a claim that certain keys were absent from the catalogue, when they had long been present — corrected in place, with the lesson that **an assertion without command evidence does not belong in a document**); the guard's **first version comparing filenames to class names** (a false positive on a two-in-one file); and the guard's **first version being fooled by prose**. Their common structure is that **none is a feature defect but a defect in the verification mechanism** — and that class is more dangerous than the former, because it biases every verification result that follows.

## 64. Four defects where the tests were green and the feature was dead

The four defects in this chapter come from one adjudication document, and their common property is stated outright: **none is a mistyped new feature; all are existing implementations that do nothing in a real environment.** Each was found during post-completion reconciliation. The signature of this class is that every layer looks correct on its own, because the defect lives **in the seam between layers** — and seams are usually where testing is absent.

**Defect one: integrated but not wired.** A storage-reliability fact service had the service, seven unit tests (injecting a fake source, all green), catalogue entries, and fact-set and export serialisation — **but no call to its loader anywhere in the project.** In the real application and CLI it was therefore always an empty list: nothing on screen, nothing in the export, nothing in a query, and tests green throughout. The fix's shape is worth recording: **make the wiring itself a named entry point** shared by UI startup and the CLI, connect both, and add a source-level guard test checking that both call sites still exist. The fix also answers "why not put it in the more natural place" — that place is the driver-backed composition point, gated on the startup path (whole batch skipped when a load is already running). Attaching a source that **needs no driver** there would make its presence depend on a gate unrelated to it. Wiring-site choice is thus not a matter of style but of ensuring one source's availability is not decided by another source's state.

**Defect two: the six states were applied in the wrong order.** The collection logic **checked availability before reading.** A real source cannot know before querying whether it will fail (the flag defaults to true), so a failed query fell into the "available but zero rows" branch and emitted: *"the source was read but reported no counters — **this is not an error**, this machine has no usable provider."* The document's comment on that output is one sentence: **it is a lie** — it was a failure, and the cause was in hand. The old fake-source tests could not catch it because their availability flag was fixed and reading never changed it. The fix has two parts: **read first, then judge availability**, and write the seam contract to say that availability means "the result of the most recent read", not a prior promise; and a source throwing its own exception must become a read-error fact carrying the exception message, **never silently an empty collection.** Three regression tests were added, with the measurement that restoring the old order turns four tests red. The value of this defect is that it shows how three-state honesty actually fails: **not by misusing a state, but by getting the order of state determination wrong.** Even with every state defined precisely, the timing of obtaining them can classify a failure as not-applicable — and on screen both look like "no data".

**Defect three: the CLI mode could not run at all on main.** Running the real binary in CLI mode crashed at entry with a null-argument exception: the window framework's application class rejects a null startup URI, and the project's startup code set it to null precisely to stop the main window being created automatically. **The CLI branch therefore died on the first line**, so no `--json` output could ever run. The detail that matters: the CLI tests **call the service class directly**, so they never pass through the application startup path and never meet the exception. **The test targets the function; the crash was in the function's entry.**

**Defect four: two binding paths could never resolve.** Found while adding a UI render check, this one is in the firmware-security page's virtualisation card. It survived because the existing smoke tests **build every page empty** — an empty page does not expose a broken binding path, since both render as nothing. The fix adds a test that checks template rendering when the page **has data**. Structurally identical to defect one at a different level: unit tests reach a service but not its wiring; smoke tests reach a page but not a page **with data**. Both blind spots are about **the combination in a real state.**

Read together, all four are the same shape: the service, the states, the tests and the bindings were each individually correct, and the defect sat between them. The general detection method is therefore not more unit tests but **guards on the seams** — check that the call exists, check the combination in a real state, check rendering with data. The wiring guard of chapter 63 supplies the first of these, and its stated grade reminds us of the method's limit.

These four all occurred after a judgement of "complete", and none can be found by raising test coverage, because **coverage measures which code runs, while these defects live where there is no code.** The project's answer is to institutionalise the reconciliation step itself: after declaring a feature complete, check item by item whether it is reachable in a real environment — the same governance logic as coverage reporting, where **a declaration is not an announcement but a claim that must be verified.**

## 65. Counting discipline

`docs/ITERATIONS.md` has existed since 2026-10-03. Its institution, stated at the top of the file: **one thing per round → pure decoders test-first (red → green) → unreadable means a state → the full suite must be green to count → commit → record in the ledger.** Each entry carries a round number, a work package, its content, the test count and the commit. The ledger opens with a **test baseline** — the full-suite number measured before a given batch — so every later entry is comparable to its predecessor. The baseline is not just a statistic: **a test count stuck at the same number is a signal**, because a round that did work without moving the count usually means the change is not covered.

`docs/PROGRESS-PLAN-2026-10-11.md` handles the 600-item catalogue. Its 2026-10-11 audit sorted every item into three states: not started, partially covered (a neighbouring capability exists but the specified output keys or scope have not landed), and complete — **VOL1 (300): 14 complete, 47 partial, 239 not started; VOL2 (300): 26 / 76 / 198; total 600: 40 / 123 / 437.** The partial class is treated as the plan's chief prey, because those are mostly "attach fact keys to a capability that already exists" — closing what is nearly done at low cost.

**Five working rules.** Fifty items make a version: version number, changelog, README badges, links and history, and the test baseline all move **only when the cumulative count reaches fifty**. Run the suite every ten items (in the foreground), fixing red immediately rather than carrying it into the next group. Publish one release per version — push, tag, three assets, the release verification script, and the byte-size documentation commit — **in that order.** Easy first: prefer items that are read-only, have an existing seam, can be unit-tested with synthetic fixtures and carry no hardware risk; defer items needing hardware, AML interpretation, UI rendering or large engineering. And the honesty red lines stand: unreadable is always a state, no citation means no value, and no fabricated values. The ordering constraint in the third rule is worth noting: the five steps depend on each other (the verification script runs against uploaded assets, the byte sizes match the published files), so a different order makes verification meaningless — a pitfall that, once stepped in, became part of the process.

**Counting discipline: what counts as an item.** This section was added on 2026-10-12, and the document states its trigger directly: the user's feedback that **some features had already been done.** The rule: an item counts only as (1) **a new capability** — something previously unreadable is now readable — or (2) **closing** — the capability existed but the specified output keys or statement had not landed, and this round lands them with tests. Three things never count: **redoing an existing service** (same thing under a different key name), **doing half** (keys present, the specified substantive action absent), and **claiming only** (stating that this version will not do it). The deduplication method is stated too: search the catalogue ID and source keywords, then inspect the service directory for the same job; **if it exists, the item is closing or does not count — only otherwise is it new.**

The section's value is that it preserves individual adjudications rather than only the rule. A device-wake record was **not counted**, because the existing power service already ran the same queries (last wake, wake timers, wake requests) and the new key merely moved it into the key space. An execution-environment self-declaration was **not counted** for the same reason — virtualisation platform and vendor facts were already stated. A device error-code item was **downgraded to partial**: only current grouping was done, while the specification's history of changes over time was not, so the keys stay but **the item is not complete** — the concrete use of the half-done rule, separating the existence of keys from the completion of an item. Several items **did count, as closing** (for example a single-table existence statement where the catalogue previously had only generic per-table enumeration). One item was **struck** because the existing update-history service already provided the same fact keys, so no second implementation was written. And three items were recorded as **half-done with keys retained** — a unit-conversion layer not implemented, a query performance index not built, and one item declaring only a consent gate without the functionality behind it. Those three keep their keys, do not count as complete, and are listed as outstanding in the plan — **the ledger doubles as a debt list.**

**Effective versus nominal totals.** Counting discipline forces those two apart. The document records one actual correction: a version had recorded 56 items, deduplication removed two duplicates, leaving **54 effective**; that version was therefore released a round early, but its version code and tests were real, so nothing was withdrawn. This round added seven, giving **61 / 600 effective**. The next release point is defined as twenty-five items after a given version — making "when do we release" a reconcilable number rather than a feeling.

An outward-facing progress number is only worth anything if it survives being questioned. If the count includes duplicates and half-done work, then "61 items complete" collapses at the first spot check — and the cost is not those few items but **the credibility of the whole ledger.** Counting discipline therefore belongs with the measurement self-validation of chapter 12 and the key-catalogue reconciliation of chapter 10: **none of them exists to make a number look good, but to make it checkable.** A checkable number that looks bad beats a good-looking one that is not — the same principle this project applies in the code and in its documentation.
