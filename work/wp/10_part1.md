# 第一部　定位與哲學

## 第一章　專案定位與適用場景

### 1.1 名稱與立場

曦覽的英文名稱 XinSpect 由兩部分構成：`Xin` 為專案代號，`Spect` 取自拉丁語 *spectator*（檢視者、觀察者）。此一命名不是修辭，而是對工具功能的技術描述：本程式的職責是把「硬體自己說的」、「韌體說的」與「作業系統說的」三組陳述並列呈現，並在兩者不一致時具名指出矛盾所在。程式本身不對硬體是否為正品、是否經過改裝、是否值得購買作出結論。

這個立場有三個現實理由。

**第一，單一來源的結論在取證上沒有價值。** 一台機器上「CPU 型號」這個值至少有四個可能的來源：CPUID 指令的直接回報、SMBIOS 結構中的處理器條目、登錄檔中的處理器描述，以及系統 API 的摘要。四個來源可能互相抄襲，也可能各自獨立。若工具只輸出一個數字，使用者無法判斷這個數字來自何處，也就無法在爭議中主張任何事。曦覽的做法是把來源欄位與數值一起輸出：CPUID 0x16 回報的基礎頻率與由矽晶倍頻推算的基礎頻率是兩個獨立的事實，兩者不一致本身就是一條可查證的線索（對應規則 `R-CPU-05`）。

**第二，判定需要脈絡，而脈絡在使用者手上。** 記憶體模組的製造商與料號不一致（規則 `R-MEM-01`）在多數二手交易情境下是混批的跡象，但在企業採購中可能是分批進貨的正常結果。工具能確定的是「不一致」這個事實；這個事實的意義取決於使用者所知的情境。因此曦覽的對帳引擎只輸出三種判定——相符、矛盾、無法判定——而不輸出分數、等級或真偽結論。

**第三，工具本身不具備驗證自身結論的能力。** 任何軟體都可能誤判。若曦覽輸出「此機器疑似改裝」這樣的結論，使用者能做的只有相信或不信；但若曦覽輸出「記憶體模組序號欄位為空，且通電小時與累計寫入量的比值不在合理區間，來源分別為 SMBus SPD 與 NVMe SMART 記錄」，使用者可以自行複核這兩條線索，也可以拿這份陳述去質問賣家。可複核的陳述比一個結論有用得多。

### 1.2 三個來源層

曦覽的事實收集依來源性質分為三層，這個分層貫穿整個程式：資料模型的 `source` 欄位、對帳規則的輸入選擇、以及報告的呈現順序都遵循同一分類。

**硬體層**指的是繞過作業系統、直接與硬體通訊所得的讀值。這包括型號特定暫存器（MSR）、PCI／PCIe 設定空間、SMBus 上的 SPD（記憶體模組的序列存在偵測）與 TSOD（溫度感測器）、ATA SMART 屬性、NVMe 健康紀錄、Super I/O 暫存器與 CMOS。此層的取得需要 Ring-0 權限，曦覽透過自寫的 WinRing0 事實讀取層與白名單唯讀驅動 XsRegProbe 完成，細節見第六章。

**韌體層**指的是由平台韌體在建置期產生、於開機時提供給作業系統的靜態描述。這包括 ACPI 表（MCFG、HEST、BERT、SLIT、CEDT、HPET、FPDT、FADT 等）、SMBIOS 結構、UEFI 變數。此層的取得不需 Ring-0，但需具備讀取權限；其內容反映的是「韌體聲稱的機器組態」，可能落後於實際硬體（例如更換過元件而未更新 SMBIOS）。

**作業系統層**指的是作業系統與其驅動程式對硬體的理解。這包括 WMI 的 CIM 類別與 MSFT 進階類別、登錄檔、事件記錄、效能計數器、ETW 追蹤與 X509 憑證存放區。此層最容易取得，但也最容易被改寫（登錄檔可編輯、WMI 提供者可替換、驅動程式可回報自訂值），因此曦覽對這一層的事實一律標記為 `Reported` 而非 `Measured`。

三層之間的落差是本工具最主要的情報來源。例如顯示卡的鏈路寬度：PCIe 設定空間可讀出當前協商的鏈路寬度與速度，裝置能力暫存器可讀出該裝置支援的最大寬度，兩者不對等即為一條可陳述的事實（規則 `R-LNK-01`）；而作業系統層往往只回報「正常運作」，因為降速的鏈路在功能上仍可運作。

### 1.3 適用場景

曦覽的設計圍繞四類專業場景，各場景對工具的要求不同，理解這些差異有助於正確解讀輸出。

**二手設備驗機。** 買方在付款前需要判斷設備是否經過不當改裝、是否為翻新件、其消耗性元件是否已接近壽命終點。此場景的特徵是：時間有限、無法拆機、賣方可能在場。曦覽對此場景的支援集中在無需拆卸即可取得的證據：快閃記憶體（SPI）內容的雜湊與前後比對、微碼版本的一致性、SMART 與 NVMe 的累計寫入量與通電小時比率、固態硬碟的已用壽命百分比、HPA／DCO 造成的容量落差、以及控制器與裝置標示之間的一致性。此類證據的特點是**難以在不被發現的情況下偽造**，因為它們位於裝置的持久性記錄中。

**伺服器與工作站上架前的基線建立。** 機房設備在交付前需要一份可保存、可日後比對的組態快照，用於變更管理與保固爭議。曦覽為此提供時間膠囊（快照的序列化容器）、硬體變更時間軸（兩份快照的比對結果）與審計日誌（可脫離應用程式驗證的簽章鏈）。此場景的特徵是文件需要長期保存且需可驗證，因此報告格式與簽章機制比即時性更重要。

**效能調校與故障排除。** 在調校超頻、記憶體時序、PCIe 鏈路或電源策略時，使用者需要區分「設定的值」、「量測到的值」與「硬體宣稱的值」。曦覽在此場景的價值在於把三者分開陳述：設定的值來自登錄檔或 API，量測到的值來自感測器或基準測試，硬體宣稱的值來自 SMBIOS 或 SPD。三者一致的機器很少，而不一致處往往就是調校空間所在。

**安全稽核。** 在需要向第三方說明一台機器的信任狀態時（例如受監管環境的端點盤點），需要的是可引用的結構化證據而非介面截圖。曦覽為此提供事實的機器可讀匯出（`--json evidence`）、查詢語言（可對快照提出結構化問題）、以及防護機制的逐項狀態（TPM、Secure Boot、BitLocker、記憶體加密、驅動程式封鎖清單比對）。此場景的特徵是**「讀不到」本身就必須被記錄**：一台無法讀取 TPM 狀態的機器與一台 TPM 未啟用的機器是不同的結論，混淆兩者會產生誤導性的稽核報告。

### 1.4 明確的不作為

界定一個工具的邊界，與界定其能力同等重要。曦覽刻意不做以下五件事。

**不主動變更硬體狀態。** 讀取一律唯讀。少數確實需要寫入的功能（例如特定的感測器校正或風扇策略套用）一律置於同意閘門之後，且在介面上明確標示其風險與影響範圍。寫入路徑集中於 `WriteGate` 與 `CeremonyService` 兩個模組，任何新增的寫入行為都必須經由這兩個模組，以維持可稽核性。

**不在未經請求時產生網路流量。** 程式不收集、不上傳任何使用者資料。唯一會產生對外連線的功能是使用者主動呼叫的 AI 評價（第二十一章）與更新檢查；兩者都需使用者明確啟動，且其端點可設定。本機 API 預設為 loopback 唯讀，且 HTTP 監聽殼預設不啟動——開啟監聽等同於新增本機攻擊面，本專案將其視為使用者的決定，而非工具的預設。

**不代替使用者診斷故障。** 曦覽可以指出「BMCE 記錄中存在一個與此次開機相關的硬體錯誤」或「某顆磁碟的已用壽命與累計寫入量比值異常」，但不會輸出「主機板故障」這樣的結論。故障診斷需要對硬體設計與使用歷史的完整理解，工具不具備這些資訊。

**不對外提供繞過防護的功能。** 記憶體攻擊面盤點、Rowhammer 探測、易受攻擊驅動（BYOVD）比對等功能的存在目的，是**讓使用者知道自己的機器暴露於什麼風險**，而不是提供攻擊手段。因此這類功能的輸出集中於「是否存在可利用條件」與「現行防護是否啟用」，不包含利用程式碼。同理，REST 範例集（規格編號 XT-003）在評估後被明文決定不做，理由記於豁免清單：發佈一份可用的範例等於提供連向未承諾端點的程式碼，其替代路徑為 CLI 的 `--json` 輸出與檔案交換。

**不承諾特定硬體平台的完整性。** 專案主要在 Intel 平台上開發與驗證。AMD 專屬事實（SMU、PSP 相關）已實作，但開發機為 Intel 平台，因此其對帳豁免條目明文記載「有真機時應補對帳規則，屆時本條豁免要移除」。把「無法驗證」偽裝成「已驗證」在本專案被視為最嚴重的錯誤類型。

## 第二章　設計原則

曦覽的設計原則不是文件中的宣示，而是由測試與機器檢查強制執行的約束。本章逐條說明每一項原則的內容、其背後的失效模式，以及它在程式碼中的落實位置。

### 2.1 原則一：三態誠實——讀不到必須說得出為什麼

**失效模式。** 一個硬體診斷工具最常見、也最難察覺的缺陷，是讓「量不到」與「值為零」在介面上長得一樣。使用者看到記憶體插槽數為 0，會理解為「這台機器沒有記憶體插槽」，而非「WMI 查詢失敗」。這個混淆在單機使用時只是不便，在批量稽核時會直接產生錯誤結論：一批機器的某個欄位全為 0，可能代表這批機器的驅動程式版本一致地不支援該查詢，而不是這批機器全都缺少該硬體。

**約束。** 每個事實都攜帶 `FactAvailability` 欄位，其值域為：

| 值 | 語意 | 典型成因 |
|---|---|---|
| `Present` | 已讀到值 | 正常情形 |
| `NotSupported` | 平台不具備此能力 | CPUID 未宣告該功能、ACPI 表不存在 |
| `InsufficientPrivilege` | 有此能力但權限不足 | 未以系統管理員身分執行而需讀 MSR |
| `ReadError` | 有能力、有權限，但讀取失敗 | WMI 提供者異常、IOCTL 逾時、暫存器讀回不一致 |
| `NotApplicable` | 此機器上此項目無意義 | 桌上型機器的電池事實、無 CXL 硬體時的 CXL 事實 |

**落實。** 可用性欄位與值同時進入資料模型，因此無法在輸出階段被遺漏。介面上，讀不到的事實顯示原因文字而非空白或「—」；輸出時，`--json evidence` 保留相同的欄位。WMI 查詢失敗、MSR 被拒、感測器不存在等情形在程式中以 `Diag.Swallow(site, ex, consequence)` 記錄，其中 `site` 為發生位置的短標籤、`consequence` 為對使用者的實際後果。此紀錄同時進入記憶體環形緩衝與 `diag.log`，使用者回報問題時一併附上即可。

值得注意的是 `Diag` 的自我約束：此類別自身絕不拋例外(FILEPATH diag.log 的寫入失敗只會使該筆紀錄留在記憶體中)。一個診斷機制若成為新的失敗來源，就違背了它存在的理由。同理，`Diag` 與 `CrashLog` 分工明確：前者記錄「已接住、功能降級、程式繼續」的例外，後者記錄「已經炸了」的未處理例外。

### 2.2 原則二：可稽核來源

**失效模式。** 若一個事實不記錄來源，它就無法被複核。使用者看到「處理器基礎頻率 3.20 GHz」時，無法判斷這個值來自 CPUID 指令的直接回報、SMBIOS 的字串欄位、或是登錄檔中可被任意編輯的描述。當這三者的值不同時，缺少來源資訊的輸出等於沒有資訊。

**約束。** 每個事實必須攜帶 `source` 欄位，內容為可辨識的來源標識，例如 `MSR 0x1A0`、`WMI Win32_Processor`、`CPUID 0x16`、`SMBIOS Type 17`、`ACPI MCFG`。暫存器解碼器額外必須攜帶規格引用註記（`SpecRef`），指向該欄位在規格書中的章節。

**落實。** `SpecRef` 的存在由反映式機器檢查強制：測試掃描解碼器組件中的型別，任何缺少註記的解碼器會導致測試失敗。這使得「隨手加一個解碼器」的成本提高，而這個成本是刻意設計的。

### 2.3 原則三：自驗量測

**失效模式。** 效能量測最容易產生的錯誤不是數值不準，而是**量測本身失準而無人察覺**。一個沒有正確設定工作集大小的頻寬測試、一個因為 CPU 頻率未鎖定而產生變動的計時、一個因為執行緒數與實體核心數不符而失真的並行量測，都會穩定地輸出一個錯誤但看起來合理的數字。

**約束。** 凡涉及量測的功能，必須在回報數值之前自行驗證量測機制。具體落實於三處：

- **西洋棋基準以 perft 作檢核。** 走子產生器在計時之前先執行已知節點的 perft 計算，若節點數與公認值不符，代表走子產生邏輯有缺陷，此時量測結果不予回報。perft 在此扮演的是數學檢核碼的角色，而非熱身。
- **頻寬換算先自驗。** 記憶體頻寬量測在回報前先以已知大小的負載執行一次，驗證傳輸量與耗時的關係符合預期，避免因快取命中或記憶體對齊導致的虛高讀數。
- **PMU 程式化逐輪驗證寫回。** 效能監控單元（PMU）的計數器設定在每一輪量測中都驗證「寫入的值與讀回的值一致」，因為計數器被硬體其他使用者（例如 BIOS 或另一個監控程式）重設，是實務上會發生且難以察覺的情形。

**落實。** 這些自驗並非可選的除錯輔助，而是回報路徑上的必要環節。未通過自驗的量測結果，其可用性欄位會被標記，而非以數值形式輸出。

### 2.4 原則四：對帳而非評分

**失效模式。** 給出分數是最容易實作、也最容易誤導的輸出形式。一個 87 分的機器與一個 92 分的機器之間的差異，可能完全落在量測噪音之內；但分數一旦輸出，使用者就會據此行動，且不會追問分數的構成。

**約束。** 對帳引擎只輸出三種判定：

| 判定 | 語意 |
|---|---|
| 相符（Match） | 所需事實齊備，且各來源彼此一致 |
| 矛盾（Conflict） | 所需事實齊備，且各來源彼此不一致 |
| 無法判定（Unread） | 所需事實不齊備——**缺值時引擎自行判定，規則實作中不必再寫缺值分支** |

**落實。** `VerifyRule` 記錄的 `RequiredFacts` 是引擎的前置檢查：若所需事實有任何一項缺少，引擎直接回傳「無法判定」並說明缺少的是什麼、以及如何才能讀到（此資訊來自 `FactCatalog` 的顯示名與權限需求表）。這個設計使規則實作只需處理「資料齊備時該如何判定」這一種情形，同時保證缺值不會被誤判為相符。矛盾的輸出必須具名列出雙方來源，並附上證據清單。

### 2.5 原則五：豁免必須附理由

**失效模式。** 在有數百個事實鍵、卻只有十數條規則的系統中，「這個鍵沒有被任何規則考慮」是常態而非例外。危險之處在於這個狀態**在畫面上看起來一切正常**：事實進了快照、顯示於介面、匯出於報告，但永遠不會被交叉檢查。新增事實時最常見的疏漏正是如此。

**約束。** 覆蓋申報把每個事實鍵歸入三種狀態之一：已覆蓋（至少一條規則將其列為輸入）、明文豁免（刻意不對帳，且附理由）、未覆蓋（既無規則亦無豁免）。第三種不是錯誤，但必須是一個**已知的數字**。

**落實。** 本版有 562 條豁免，每一條都附有理由字串，理由的形式是「這類事實為什麼沒有第二個來源可以交叉」。豁免的門檻是「無法交叉」，不是「懶得寫規則」——這個區別由審查維持，而 `ExemptionsWithoutReasons` 檢查確保不存在空理由的豁免。此外，豁免清單中包含**明文不做**的條目（例如規格編號 XT-003 的 REST 範例集），使「決定不做」與「尚未做」在文件中可區分。

值得強調的是本專案**不設定覆蓋率門檻**。強制全覆蓋會逼出一批為了達標而存在的規則，這些規則輸出的「相符」判定是假訊號，其危害大於誠實申報一個未覆蓋數字。

### 2.6 原則六：唯讀優先與同意閘門

**失效模式。** 硬體工具需要 Ring-0 權限才能完成其核心功能，而 Ring-0 權限的程式碼一旦有缺陷，後果是系統層級的。同時，使用者對一個「什麼都能做」的工具無法建立信任，因此也不會在重要的機器上使用它。

**約束。** 讀取一律唯讀。需要寫入的功能必須：(1) 經由集中的寫入閘門模組；(2) 在使用者介面上明確標示風險與影響範圍；(3) 需要使用者逐次同意。

**落實。** 寫入路徑集中於 `WriteGate` 與 `CeremonyService`。驅動層的 XsRegProbe 採白名單設計：驅動僅接受清單中登記的暫存器存取請求，請求的暫存器與操作類型在編譯期固定。此設計的代價是擴充成本（新增暫存器需修改驅動與清單），而這個代價換取的是攻擊面的可列舉性。

### 2.7 原則七：突變測試作為量尺

**失效模式。** 單元測試覆蓋率衡量的是「哪些程式碼被執行過」，而非「哪些缺陷會被發現」。一個 100% 覆蓋的測試套件可能對某個分支的錯誤結果毫無反應。

**約束。** 純函式解碼器（不依賴作業系統、不進行 I/O 的部分）獨立為 `XinSpect.Decoders` 類別庫，並以 Stryker 進行突變測試，目標分數 82%。

**落實。** 突變測試要求測試對「程式碼的微小改動」敏感。此機制已在實際開發中發現真實缺陷：擴展家族（extended family）的進位處理在文件中記載但未實作，而該缺陷在功能測試中不顯現——因為受影響的輸入組合在真實硬體上罕見——但突變測試將其暴露。

### 2.8 原則八：單一執行檔與離線可用

**約束。** 程式以單一可攜執行檔發佈，不需安裝、不需登錄檔寫入、不需背景服務。核心功能（事實收集、對帳、報告產生）完全離線可用。

**理由。** 驗機場景經常發生在無法安裝軟體的環境（賣方機器、受管制的工作站、臨時的工作場所）。同時，一個不需安裝的工具其移除成本為零，這降低了使用者在陌生機器上使用它的心理門檻。

**代價。** 單一執行檔意味著無法在執行期掃描原始碼，這一限制直接產生了第三章所述的事實鍵目錄設計，以及附錄 A 的全鍵清單。這是一個由部署形態反向決定的架構決策，也是本專案中數個關鍵設計的直接成因。

## 第三章　事實模型與可信層級

### 3.1 統一事實模型

曦覽的全部觀測值收斂為單一型別 `HardwareFact`，其欄位如下：

| 欄位 | 型別 | 語意 |
|---|---|---|
| `key` | 字串 | 事實的唯一識別碼，點分命名，如 `role.surface` |
| `category` | 字串 | 分類，用於介面分組與報告目錄 |
| `name` | 字串 | 人類可讀的名稱 |
| `value` | 字串 | 呈現用的值 |
| `numericValue` | 可空數值 | 可比較、可運算的值的部分；純文字事實為空 |
| `unit` | 字串 | 單位，如 `MHz`、`MiB`、`°C` |
| `source` | 字串 | 來源標識（見 2.2） |
| `trust` | 列舉 | 可信層級（見 3.3） |
| `availability` | 列舉 | 可用性（見 2.1） |
| `measuredAtUtc` | 時間 | 量測時間，用於時間軸與歷史比對 |

這個設計有兩個直接後果。其一是**消費端的一致性**：時間膠囊（快照序列化）、查詢語言、本機 API 與 HTML 報告四種輸出全部消費同一個模型，因此不存在「介面上看到的」與「匯出的」不一致的情形——這是實務上最常見、也最難察覺的文件缺陷來源。其二是**新增事實的成本固定**：新增一個事實只需產生一筆 `HardwareFact`，四種輸出與查詢語言、對帳引擎皆自動可見，不需為個別輸出補寫程式碼。

`numericValue` 與 `value` 的分離值得說明。以記憶體速度為例：`value` 為 `3200 MT/s`，`numericValue` 為 3200，`unit` 為 `MT/s`。查詢語言的比較運算子需要前者，報告的呈現需要後者。若只有字串，比較將退化為字典序；若只有數值，單位與格式化資訊將遺失。純文字事實（例如處理器品牌字串）的 `numericValue` 為空，此時以其為輸入的比較運算子會判定為無法比較，而非以零代替。

### 3.2 鍵的命名與穩定性

事實鍵是程式的性質，而非機器的性質。有哪些鍵取決於有哪些服務，不取決於執行機器具備什麼硬體。這個區別是本專案數個設計的基礎。

鍵採點分階層命名，第一段為領域前綴（共 107 個，見附錄 A），其後為子領域與具體項目。例如 `ac.hpet.full.base` 屬於 ACPI 領域的 HPET 完整解碼、基礎計數器欄位。穩定性要求為：鍵一旦發佈即不更名，語意變更需以新鍵表達；鍵的移除需同步更新目錄，否則測試紅燈。

### 3.3 可信層級

`FactTrustLevel` 區分四種可信層級，其劃分依據是「這個值經過多少轉手」：

| 層級 | 語意 | 例 |
|---|---|---|
| `Measured` | 本工具直接量測所得 | MSR 直讀的微碼版本、PCIe 設定空間讀出的鏈路寬度、感測器讀值 |
| `Reported` | 系統或韌體自述 | SMBIOS 的記憶體模組製造商、WMI 的處理器描述、ACPI 表的宣告值 |
| `Derived` | 由其他事實推導 | 由最大非睿頻倍頻與 BCLK 推算的矽晶基礎頻率、由 SPD 的時序表推算的等效延遲 |
| `Unknown` | 不可用或無法歸類 | 讀取失敗且無其他線索時 |

層級不是品質評分，而是**推論鏈長度的陳述**。一個 `Reported` 的值不比一個 `Measured` 的值「差」——SMBIOS 中的序號欄位沒有其他來源可以量測，它只能是 `Reported`。層級的用途在於決定對帳規則的行為，以及在輸出時讓使用者知道該值需要多少額外的驗證。當一個 `Derived` 事實與一個 `Measured` 事實矛盾時，優先懷疑推導過程；當兩個 `Reported` 事實矛盾時，優先懷疑其中一個來源被改寫。

### 3.4 可用性與可信層級的正交性

`availability` 與 `trust` 是兩個正交的維度，其組合的語意如下：

| | `Present` | 讀不到 |
|---|---|---|
| `Measured` | 直接量到的值 | 有此能力但本次讀取失敗／權限不足 |
| `Reported` | 來源自述的值 | 來源不存在於此平台 |

正交性使「這台機器沒有此硬體」與「這台機器有但讀不到」在資料模型層級即可區分，不需依賴輸出層的慣例。這也是 2.1 所述失效模式的結構性解法：混淆之所以不可能發生，是因為產生混淆所需的資訊在資料模型中無處遺失。
