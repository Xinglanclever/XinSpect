## 第十七章　伺服器、工作站與合規

### 17.1 為什麼需要獨立的模式

伺服器與工作站的事實需求與消費級機器不同，差異不在量而在性質：

**事實的來源不同。** 伺服器平台提供消費級平台沒有的來源，包括帶外管理控制器（BMC／iDRAC／iLO）的相關結構（SMBIOS Type 38）、機箱的實體安全狀態（SMBIOS Type 3 的入侵偵測與鎖定狀態）、電源供應單元的 PMBus 資料、以及企業儲存路徑（iSCSI、MPIO、光纖通道）。

**事實的意義不同。** 消費級機器的「虛擬化已安裝」通常意味著使用者裝了虛擬機軟體；伺服器上則可能意味著這是一台執行 Hyper-V 角色的主機。同一組事實的判讀需要不同的脈絡。

**事實的完整性要求不同。** 消費級機器的部分欄位缺失只是不便；伺服器的組態快照若缺少關鍵欄位，則可能無法通過變更管理審查。

曦覽對此的處理不是複製一套功能，而是以 `ServerModeFactsService` 判定機器是否處於伺服器工作模式，並由條件式的事實收集（`ServerRoleConditionalFactsService`、`ServerRoleDeepFactsService`）與合規檢查（`ServerComplianceFactsService`）在該模式下展開。

### 17.2 角色與功能的盤點

`RoleSurfaceFactsService` 處理已安裝角色與功能的盤點。其事實來源是 WMI 的 `Win32_OptionalFeature`（選用功能的安裝狀態）與 `Win32_Service`（服務的執行狀態），兩者結合成「已安裝、服務執行中 N 項、已安裝未執行 M 項」的陳述。

此處的設計決策值得說明。首先，服務狀態**只查詢一次**。實作中先取得完整的服務清單並建立索引，再對每個功能計算其對應服務的執行數量，避免為每個功能各查一次服務清單——後者在角色數量多時會顯著拖慢載入。其次，「已安裝但服務未執行」被陳述為一種狀態而非異常，因為它有合法成因（服務設為手動啟動、角色已停用但功能未移除）。

角色的**合規性**檢查是獨立的一層。此處存在第二部所述的已知順序缺陷：`LoadServerCompliance()` 需要角色事實作為輸入，而角色的載入排在較後段，因此在現行的循序載入下，合規性所看到的是上一輪的角色事實。

### 17.3 企業儲存與網路

企業儲存的事實包括 iSCSI 工作階段（`IscsiSessionFactsService`）、MPIO 與光纖通道的存在性（`EnterpriseStorageFactsService`）、以及 CIM 與 WMI 中相關的服務存在性。其對帳豁免理由為：「企業儲存偵測（iSCSI／MPIO／FC）來自 SCM 與 WMI 的服務存在性，屬環境事實。」

網路系統的盤點由 `NetworkSystemInventoryFactsService` 與 `NetworkSecurityInventoryFactsService` 處理，涵蓋網卡、其進階屬性、卸載能力（`NetOffloadFactsService`）、連結狀態（`NicLinkFactsService`）與鏈路健康（`NicHealthFactsService`）。

### 17.4 帶外管理

`OobFactsService` 探測帶外管理的存在性，來源為 SMBIOS Type 38。其豁免理由為：「帶外管理存在性探測（SMBIOS Type 38）；本機無硬體時本來就不適用。」此條同時說明了一項重要的邊界：當本機不具備該硬體時，事實的可用性為 `NotApplicable`，而此狀態與「讀取失敗」必須區分。

### 17.5 服務就緒時間線

服務就緒時間線（規格編號 PO-005）量測各服務相對於開機時點的開始時間。其設計約束記錄於豁免清單，值得全文引用：「相對開機的秒數；**時間是事實、原因不是**，不評級不裁決慢，不列服務名稱。」

此約束體現本專案對「量測」與「判讀」邊界的堅持。工具能確定某個時間點上發生了什麼，但不能確定某個時間點**應該**發生什麼——後者依賴部署環境的知識（一台資料庫伺服器與一台檔案伺服器對服務啟動順序的要求不同）。此外，「不列服務名稱」是一項隱私考量：服務清單可反映組織的軟體部署，屬於環境資訊。

### 17.6 背景服務模式的能力盤點

背景服務模式（規格編號 AG-005）盤點「若要以服務形式執行，目前缺少什麼」。其實作約束記錄於豁免清單：「能力盤點與成本量級；**不建立服務、不註冊排程**——回答『如果要，缺什麼』，『可以做』與『正在做』是兩件事。」

此條的設計立場值得注意：工具盤點可行性，但不執行變更。這與 2.6 的同意閘門原則一致，也與 1.4 的不作為清單一致。一個「順手幫你裝好服務」的功能看似方便，但會在未經明確同意的情況下變更系統狀態，且其變更的移除需要額外知識。

### 17.7 營運清單與其治理

`OperationsInventoryFactsService` 與 `InventoryGovernanceFactsService` 處理營運層級的盤點與其治理規則。此處涉及的是一個較高層次的設計模式：**判斷的登記表**（`WiringDecisions`）。

此模式的內容是：當程式中存在一個需要人為決定的分岔（例如「HTTP 監聽殼是否要啟動」），該決定本身被登記為一筆資料，包含決定內容、理由、以及決定的條件。執行環境檢查時參照此登記表，而非隱含於程式碼中。其價值在於：決定的理由不會隨時間與人員變動而遺失，且使用者可以查閱「工具不做某事」的具體理由。

本機 API 的 HTTP 監聽殼即為此模式的實例：其決定為不啟動，理由為「開啟監聽等同於新增本機攻擊面，屬使用者決定」，並提供 headless 的替代出口（CLI 的 `--json evidence`）與審計日誌的外部驗證路徑（`--verify-audit`）。

## 第十八章　虛擬化與機密運算

### 18.1 三個刻意分開的觀測值

`VirtualizationFactsService` 對虛擬化提出三個獨立的觀測值：CPUID 的 hypervisor 位元、Windows 選用功能中的虛擬化元件、以及虛擬化相關服務的存在性。

三者的分離是刻意的，其理由記錄於豁免清單：「虛擬化的三個觀測值（CPUID／選用功能／服務）本來就是刻意分開陳述的三件事。硬綁成一條對帳規則，會把『裝了但未載入』這種正常狀態判成矛盾。」

此設計的判讀價值在於三者的組合有六種可能，每種對應不同的實際狀態。例如「選用功能已安裝、服務存在但未執行、CPUID 未報告 hypervisor」意味著虛擬化平台已安裝但未啟用；而「CPUID 報告 hypervisor」則意味著**本文具機器正執行於虛擬層之上**，此時所有依賴硬體直讀的事實（MSR、PCI 設定空間、感測器）必須被理解為由虛擬層提供，其可信度下降——這正是規則 `R-CPU-04` 所陳述的方法論警告。

### 18.2 Hyper-V 與嵌套虛擬化

`HyperVInventoryFactsService` 盤點 Hyper-V 的組態，包括虛擬交換器、虛擬機器的存在與狀態。此項的用途是在伺服器場景中提供宿主機層級的組態視圖。

### 18.3 NUMA、大頁與資源配置

`NumaTopologyService` 取得 NUMA 拓撲，其來源為 kernel32 與 ACPI 的 SLIT 表。此項的豁免理由為：「NUMA 拓撲來自 kernel32 與 ACPI SLIT，兩者已在解碼層並列；單節點機器的跨節點項目本來就無從量測。」此條說明兩件事：來源的並列已在解碼層完成（因此不需另立對帳規則），以及**單節點機器上部分項目本質上無法量測**（不可量測與量測失敗必須區分）。

`LargePageService` 與 `LargePageDecoder` 處理大頁的支援與組態；`RdtService` 處理 Intel 資源導向技術（快取與記憶體頻寬的配置）。

### 18.4 機密運算

機密運算相關的事實分為 Intel 與 AMD 兩條路徑：

- **Intel 路徑**：`PlatformSecurityMsrFacts`、`MemoryEncryptionFactsService`、`TmeFactsService`（記憶體加密系列）、`TdxFactsService`（信任域擴充）。
- **AMD 路徑**：`AmdSecurityFactsService` 處理 SEV、SEV-ES、SEV-SNP、SME 的支援與啟用狀態，以及 PSP 的存在性。

這一組事實的設計要點是**支援與啟用的分離**：`sev.supported` 與 `sev.enabled` 是兩個獨立的事實，因為硬體支援而韌體未啟用是常見且重要的狀態。

其驗證限制同樣必須明示：本版開發機為 Intel 平台，AMD 相關事實無法驗證，豁免條目已明文記載此限制與其解除條件。

### 18.5 CXL

`CxlFactsService` 處理 CXL 的事實，來源為 ACPI 的 CEDT 與 CHBS 表。其豁免理由為：「CXL 事實來自 ACPI 表（CEDT／CHBS），單一來源；本機無 CXL 硬體。」這是一個典型的「實作完成但無法真機驗證」的情形，本專案的處理方式是在豁免清單中登記此限制，而非以測試通過宣稱功能可用。

## 第十九章　證據實驗室與查詢

### 19.1 證據實驗室

證據實驗室（`EvidenceLabService`）是事實的深度蒐集與分析介面。其與啟動序列的關係是補充而非替代：啟動序列蒐集通用事實，證據實驗室則提供更深入、更耗時的蒐集項目，並將其組織為可查詢、可比對、可匯出的形式。

實驗室的組織單位是**快照**（Snapshot）：一次完整的事實蒐集結果，附帶量測時間。快照是後續所有分析操作的輸入單位。

### 19.2 時間膠囊

時間膠囊是快照的序列化容器，其格式為 `docs/spec/snapshot.schema.v1.json` 所定義的規範版本。膠囊的用途是長期保存與跨機器比較。

其設計要點有三：

**自足性。** 膠囊包含完整的可讀事實集合與其脈絡（量測時間、來源、可信層級、可用性），不依賴讀取端的環境。因此一個膠囊可以在另一台機器上被分析，也可以在數月後被重新解讀。

**規範化。** 膠囊的序列化格式是規範化的（canonical），因此同一組事實產生位元組相同的輸出。這使雜湊比對成為可行的變更偵測手段。

**與覆蓋申報的連結。** 膠囊中的鍵集合可與全鍵目錄比對，因此可以計算「此次蒐集涵蓋了全鍵中的哪些部分、哪些未涵蓋」，並區分「未涵蓋」與「涵蓋但讀取失敗」。

### 19.3 硬體變更時間軸

`EvidenceTimelineService` 與硬體變更時間軸（規格編號 HM-007）提供兩份快照的比對。其豁免理由為：「輸入是兩份快照的比較結果，已是第三者對照，不再疊規則。」此條的邏輯值得注意：變更時間軸本身就是一種對帳（時間上的對帳），因此不需再對其輸出疊加跨來源的對帳規則。

變更時間軸的輸出是差異清單，每一筆包含鍵、舊值、新值與變更時間。其用途涵蓋保固爭議（「我交機時這顆碟是新的」）、變更管理（「上週有沒有人動過這台機器」）與故障排除（「問題是什麼時候開始的」）。

### 19.4 查詢語言

曦覽提供一個小型的查詢語言，規格為 `docs/spec/query-language.v1.md`。其設計目標是讓使用者能對快照提出結構化問題，而不需匯出資料後以其他工具處理。

語法的基本單位是子句：一行一子句，`#` 開頭為註解，值含空格時吃到行尾。可用欄位七種：

| 欄位 | 比對對象 |
|---|---|
| `key` | 事實鍵 |
| `category` | 分類 |
| `source` | 來源標識 |
| `value` | 值 |
| `availability` | 可用性（支援別名 `ok`／`error`／`no-permission`） |
| `since` | 時間下界 |
| `until` | 時間上界 |

運算子三種：`=` 為精確比對、`~=` 為子字串包含（不分大小寫）、`^=` 為前綴比對。子句之間為 AND。語法錯誤時拋出 `ParseException`，附帶修正指引。

此語言的兩項設計原則值得強調。

**第一，查得到與讀得到是不同的事。** 查詢語言對「存在但讀不到」的條目照樣返回匹配，並附上原因。因此一個查詢可以刻意用來列舉「所有因權限不足而讀不到的事實」——這在稽核中是必要的操作。

**第二，把查錯偽裝成空結果屬於誠實違反。** 語法錯誤返回明確的錯誤與修正指引，而非空結果集。此原則與 2.1 的三態誠實一致：在一個以誠實為核心設計原則的工具中，「查不到」與「查錯」不可混為一談。

### 19.5 知識包與語意覆蓋

`KnowledgePackService` 與 `KnowledgeCoverage` 處理外部知識的載入。知識包的形式為資料表，內容例如裝置合規基線清單、已知的 CVE 對照表、或組織自訂的檢查清單。

`QueryInsightFactsService` 與 `QueryGovernanceFactsService` 處理查詢的治理，包括說明覆蓋率（規格編號 QS-005，比對 HelpCatalog 與 PageRegistry 兩個專案自有資產的一致性）。

## 第二十章　命令列介面、本機 API 與報告輸出

### 20.1 命令列介面

命令列介面的主要用途是自動化與 headless 環境。其核心出口是 `--json evidence`：以規範化的 JSON 輸出完整的事實集合，形狀與時間膠囊一致。此出口的存在使曦覽可以嵌入既有的資產管理或稽核流程，而不需依賴其介面。

`--verify-audit` 提供審計日誌的外部驗證：不啟動應用程式，直接驗證日誌的完整簽章鏈。此設計的目的是使審計日誌的驗證不依賴產生該日誌的程式——否則驗證者必須信任被驗證的對象。

### 20.2 本機 API

本機 API 由 `LocalApiHandler` 實作，提供兩個端點：

| 端點 | 方法 | 內容 |
|---|---|---|
| `/api/facts` | GET | 返回全部事實（規範化 JSON，與時間膠囊同一形狀） |
| `/api/query` | POST | 接受查詢語言全文，返回匹配結果 |

API 的設計約束為：**loopback 唯讀、匿名機器識別**。所謂匿名機器識別是指 API 不將機器識別資訊作為請求的必要條件，也不在回應中洩漏超出事實集合的識別資訊。

同時，HTTP 監聽殼**刻意不啟動**（見 17.7）。這是一個重要的架構決策：API 的實作存在，但其接聽行為預設關閉，因為開啟接聽會新增本機攻擊面。headless 的出口由命令列介面承擔。此決定的登記內容包含決定、理由與條件，使用者可查閱。

### 20.3 報告輸出

報告輸出分為三種形式：

**HTML 報告。** 由 `HtmlReportService` 產生，包含事實的組織化呈現、對帳結果、以及判讀說明。其設計要求是**方法論的可見性**：報告中對每個數值標示其來源與可信層級，使讀者無需回溯介面即可判斷證據的性質。量測方法論的完整說明另見 `docs/MEASUREMENT-METHODOLOGY.md`。

**外部報告。** `ExternalReportService` 處理與外部系統交換的格式。

**報告簽章。** 報告簽章（規格編號 RS-010）以審計鏈的頭部與驗證結果作為簽章內容。其豁免理由為：「審計鏈頭與驗證結果，鏈的完整性由 AuditVerifier 的專門測試守，不再用規則對帳。」

### 20.4 審計日誌

`AuditLogService` 記錄程式的操作性事件（事實蒐集、報告產生、以及任何寫入操作）。日誌的設計要點是**可獨立驗證**：日誌條目以雜湊鏈方式串接，鏈的完整性可脫離應用程式驗證。此設計使日誌能作為爭議情境中的證據，而非只是除錯資訊。

### 20.5 輸出的一致性保證

前述四種輸出（介面、HTML 報告、CLI 的 JSON、本機 API）全部消費同一個 `HardwareFact` 模型（見 3.1）。此一致性由架構保證而非由慣例保證：新增事實不需為個別輸出補寫程式碼，因此不存在「某個輸出忘了更新」的情形。這是 3.1 所述設計的直接效益，也是本專案在輸出層最少缺陷的原因。

## 第二十一章　AI 評價與資料邊界

### 21.1 功能內容

AI 評價功能將本機的硬體摘要交給語言模型，產生對該機器的評述。實作支援 Ollama（本機模型）或任意 OpenAI 相容端點；提示詞可自訂；API 位址與金鑰由使用者設定（`SharedAiEndpoint` 處理端點共用，`AiChatStore` 處理對話狀態，`AiTools` 提供工具呼叫的介面）。

### 21.2 資料邊界

此功能是本程式中少數會產生網路流量的功能之一，因此其資料邊界必須明確：

**僅在使用者主動呼叫時發生。** 無背景呼叫、無自動摘要上傳。

**端點由使用者指定。** 使用本機模型（Ollama）時資料不出機器；使用外部端點時，使用者已明確選擇該端點並自行設定憑證。

**送入的內容為事實摘要。** 送入模型的內容是事實集合的摘要，而非原始資料或檔案內容。

### 21.3 為何保留此功能

此功能曾有爭議：一個以「不下結論」為核心原則的工具，為何要提供一個會下結論的功能？

保留的理由是**判讀與量測的分離**。曦覽的職責是不在量測與對帳層下結論；但使用者在取得事實之後，仍需要對事實的解釋。AI 評價在此扮演的是「第二意見」的角色，其輸出被明確標示為生成內容，與事實陳列在報告中分屬不同區塊，且其輸出不被任何對帳規則或判定所引用。

換言之，此功能的設計使其無法影響工具的事實層——它是一個消費者，不是一個生產者。這是本專案對「生成式功能」的處理原則：可以存在，但必須在資料流的方向上處於末端，且其輸出必須可識別。
