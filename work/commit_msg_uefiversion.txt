ULTIMATE-1000 階段二 P2-050：映像與韌體版本一致性

═══ 兩把鍵 ═══

  uefi.version.cross     映像內嵌版本 vs 韌體宣告版本（一致／不一致／無從對照）
  uefi.version.embedded  映像內嵌的版本字串（BuildNumber ＋ UTF-16LE 文字）

後者不是規格宣告的——一把只說「一致不一致」的鍵，
回答不了「**你到底在比什麼**」。

═══ 三態，而第三種永遠不可以被算成第二種 ═══

「**「無從對照」不是「不一致」。**版本比對需要兩邊都有：
**缺一邊就沒有對照可言**。」

═══ 而「不給一致率」出現在每一個分支裡 ═══

「**本服務不給一致率**——它只對觀察到的條目陳述，
而『有幾成一致』需要先界定分母，那會把『無從對照』偷渡成『不一致』。」

**而第一版我漏了這件事**：那句話只在「有一致性判定」的 return 裡，
而兩條「無從對照」的分支沒有。**測試抓到了**——
而抓到的正是我為了防這件事而寫的那條測試
（`不給一致率那句話要在每一個分支裡`）。

**失敗的原因是一個結構問題**：我用一個 bool 去切換措辭，
而**那兩種措辭一個含通則、一個不含**。
修法是把通則抽出來、bool 只決定「補充哪一句」。

═══ 而第五次的緩衝區錯誤 ═══

`new byte[2 + 8]` 放 `"1.2.3\0"`（12 bytes）——**同一個「起點 vs 起點＋寬度」
的錯誤，這是第五次**（Type0、Boot、Type19、Type4 各一次）。

而這次的修法與前四次不同：
    var str = Encoding.Unicode.GetBytes(text + "\0");
    var payload = new byte[2 + str.Length];   // ← 沒有算，就沒有算錯的可能
前四次我都直接改數字。

═══ 附帶：TestArrayBoundsTests 的擴充，而它繞了九輪 ═══

那個守門原本只認 `new byte[單一常數]`——而第五次的 `new byte[2 + 8]`
就是因為它是運算式而整條宣告被跳過。

**而擴充的過程有大量繞路**：寫壞兩個腳本、弄壞編譯、
用過濾器遮住編譯錯誤、拿被截斷的數字（30）當基準推論。

**而它們的共同點是：我在用複雜度處理一個「我其實不確定該怎麼做」的問題。**

第一版擴充的規則是「非字面大小 ＋ 有寫入 → 紅燈」，結果全測試套 **56 條**。
而我原本要加 **56 個 bounds-checked-by 標記**讓它變綠。

**我停下來的理由：**
> **要 56 個標記才能變綠，那就不是守門，是儀式。**
> 而「加標記讓紅燈消失」正是這整個專案一直在防的事。

**改成的規則：能檢查多少就檢查多少**

    new byte[40]                       → 檢查
    new byte[36 + 40]                  → **算出來檢查**（新增常數運算式求值）
    new byte[36 + payload.Length] + 位移 0x10   → 放行（位移合理）
    new byte[36 + payload.Length] + 位移 0x8000 → **紅燈**（驗不了又可疑）

**關鍵是第四列**：**新規則不是放寬，而是把報紅燈的條件
從「驗不了」改成「驗不了又可疑」。**

**而標記機制保留著**——它的用途是「如果有人寫了真的驗不了的東西，
他有一條明說的路」；沒有的話，那個人的選擇會是「放寬守門」或「繞過它」。
**目前沒有任何測試檔用它。**
