ULTIMATE-1000 階段二 P2-037：映像截斷與突變耐受

═══ 兩把鍵 ═══

  uefi.parse.gaps      走訪缺口（截斷與損壞的處數，逐 FV 列出）
  uefi.parse.tolerant  走訪的突變耐受（截斷、完整、空輸入都不丟例外）

═══ 這一項不新增解碼器——它把既有的停損行為接出來 ═══

UefiFvInfo 早就有 SkippedCount，而**沒有任何地方用它**——
既有的 CountFact 只報「FV 數」與「校驗和不符」。

而那個欄位的設計是對的：
  if ((state & StateHeaderInvalid) != 0) break;   // 走到自由空間：**不計**
  if (p + 0x20 > fvEnd) { skipped++; break; }     // 截斷
  if (size < headerSize || p + size > fvEnd) { skipped++; break; }  // 損壞

**「走到自由空間」不是缺口，是 FV 的正常結尾**——
所以 SkippedCount 只記後兩種，而 SkippedCount > 0 是一個有意義的訊號。

═══ 「不崩潰」不能只是宣稱 ═══

所以測試裡有**真正的突變組**（這是本專案第一次做性質測試，
與其他測試驗「欄位讀對了沒」是不同的類型）：
  空陣列／1 byte／只有 _FVH 前綴／全零／全 FF／亂數 1 KiB／亂數 64 KiB
  ／合法前綴後截斷／長度欄位極大

要求「不丟例外」，並要求截斷輸入**停在合理的地方而不是漫遊**。

而事實層的措辭也很小心：
「**這一項只證明「這幾種輸入不丟例外」**，不證明「所有異常輸入都安全」
——完整的突變組在測試裡，而**測試通過的範圍就是它證明的範圍**。」

═══ 沒有走訪時缺口數必須是 null 而不是 0 ═══

「**「沒有 FV」與「FV 裡沒有缺口」是不同的斷言**」——
0 會讓前者看起來像後者。

═══ 而本輪我把同一個錯犯了兩次，兩次都被自己的守門攔住 ═══

① 在 UefiParseGapsTests 自己猜 FV 格式 → 漏 4 個欄位
   （FileSystemGuid／Attributes／block map／表頭校驗和）
   → 被 Assert.True(fvs.Count > 0) 擋下
② 讀既有的 BuildFv 並抽成共用 → 一次過

那個擋下我的斷言是紅燈之後才加的：
「**合成輸入應該要能解出至少一個 FV——否則這一條驗不到東西**」。
它的作用是讓猜錯的輸入**當場現形**，而不是等後面的斷言給出模糊的錯誤。
