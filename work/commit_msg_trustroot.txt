ULTIMATE-1000 階段二 P2-058：信任根來源陳述

═══ 兩把鍵 ═══

  bt.root        觀察到幾種信任根的證據
  bt.root.types  每一種的名字→錨點（本機看得到的證據）

═══ 核心：三種根不互斥 ═══

「硬體信任根」是一個分類問題，而三種根是三條獨立的信任來源，可以並存：

  Boot Guard     錨在 CPU 熔絲裡的 OEM 金鑰雜湊
                 本機證據：FIT 目錄裡有 ACM／啟動模組條目
  TPM 度量開機   錨在 TPM 的背書金鑰（EK）
                 本機證據：關鍵 PCR 已被延伸
  Secure Boot    錨在韌體裡的平台金鑰（PK）
                 本機證據：Secure Boot 已啟用

═══ 界線：看得到證據 ≠ 根已生效 ═══

尤其 Boot Guard：**FIT 目錄裡有 ACM 條目不代表 Boot Guard 已啟用**
（既有的 fw.bg.profile 就是這樣說的，而它讀不到設定檔）。

所以本服務只陳述「哪幾種根的證據存在」，**不宣告「這台機器的根是 X」**
——後者需要查看熔絲與設定檔，而兩者都不在使用者模式的範圍內。

而「錨點本身看不到」也寫進去了：
「CPU 熔絲與 TPM 的 EK 都不在使用者模式的範圍內。」

═══ 沒有證據 vs 讀不到 ═══

三個狀態分開列，而**三者都讀得到但都沒看到根是一個有意義的結果**：
「它排除了『讀不到所以看不到』這個解釋」。

═══ 而這一輪我犯了一個關於「猜」的錯誤，兩次 ═══

我看到 `Expected: null / Actual: False` 就開始推理
「可能是三元運算子的優先序」，然後改了 SecureBootEnabled 那段
——**而失敗的是 MeasuredBoot。**

**我沒有讀測試告訴我的行號，而是猜了一個「看起來合理」的原因。**

而這正是我在同一輪剛寫下的註解的內容：
「**一個運算式裡塞三個判斷，就會有一個判斷沒被驗到。**」
——我接著犯了它的另一個版本：
「**一個測試裡塞三個斷言，就會有一個斷言沒被看清楚。**」

修正後有一個統一的形狀（在 FromFacts 裡出現兩次）：

    availability switch
    {
        Present        => true,
        NotApplicable  => false,
        _              => null,   // **讀不到不是「沒有」**
    }

**`_ => null` 那一行是關鍵——因為 default 分支最容易被寫成 false。**
