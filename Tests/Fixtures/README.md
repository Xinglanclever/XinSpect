# 測試基準檔（golden fixtures）

這裡的 `.bin` 是**從真實硬體傾印出來的原始位元組**，用途是驗證解碼器的位移與長度。

## 為什麼不用合成資料驗正確性

1.9.1-B1 修掉的 NVMe 健康記錄位移錯誤，帶了三個發佈版沒被抓到——原因是當年的測試資料
是「照著錯誤的實作位移」合成出來的，於是測試把 bug 一起鎖死了。合成資料只證明程式跟
自己一致，不證明它跟規格一致。所以：

- **正確位移**：一律用真實位元組驗證。
- **邊界情況**（全 0、全 F、溢位、欄位缺失、緩衝區過短）：才用合成資料。

## 檔案

| 檔案 | 來源 | 傾印日期 |
|---|---|---|
| `smbios-real.bin` | `MSSmBios_RawSMBiosTables`（等同 `GetSystemFirmwareTable('RSMB')` 的表身）。主機板 ROG RAMPAGE VI EXTREME OMEGA（X299），8 個 Type 17 結構、1 個 Type 16。 | 2026-09-04 |
| `spd-ddr4-real-dimm1.bin` | DDR4 UDIMM 8 GB，料號 `ZhuQue_8G_Y`，模組廠與顆粒廠皆 SK Hynix（0x80AD），製造 2024 年第 51 週。 | 2026-09-05 |
| `spd-ddr4-real-dimm2.bin` | DDR4 UDIMM 8 GB，料號 `ZJ-4000-C18-8G-RWMC`，**製造日期與序號在 SPD 裡都是空的**。 | 2026-09-05 |
| `spd-ddr4-real-dimm3.bin` | 與 dimm1 同批（同料號、同週次、同 CRC），序號不同。 | 2026-09-05 |

### 這三份 SPD 的來源要特別說明

它們是從 **CPU-Z 報告的 `SPD registers` 十六進位傾印區轉錄**的，不是曦覽自己讀的。原因是本機
（i9-7980XE／X299）的 DIMM SPD **不在 PCH 的 SMBus 上**——HEDT 平台走 CPU 記憶體控制器自己的
SMBus 區段，而曦覽目前只實作 PCH 那條路徑（見 `Services/SmbusController.cs`）。

這個來源仍然滿足基準檔的目的，而且在一件事上更強：**同一份報告裡還有 CPU-Z 對同一串位元組的
獨立解讀**（廠商、料號、序號、製造週年、XMP 版本與各組時序）。位移寫錯會立刻和它對不上，
而自己傾印再自己驗做不到這件事。`SpdDecoderTests` 的每一條真實位元組斷言旁邊都註明了對應的
CPU-Z 讀值。

換到 PCH SMBus 讀得到 SPD 的機器（主流桌上平台）之後，應該補一份自讀的傾印進來。

### 這三份的實機原始序號

遮蔽前的位元組 325–328（入庫時已覆寫成同長度的 `XXXX`）：

| 檔案 | 原始序號 |
|---|---|
| `spd-ddr4-real-dimm1.bin` | `00000042` |
| `spd-ddr4-real-dimm2.bin` | `00000000`（SPD 裡真的沒燒） |
| `spd-ddr4-real-dimm3.bin` | `00000051` |

`dimm2` 那一列是驗機功能的示範案例：SMBIOS 對它回報的序號是全 0，而「模組沒燒序號」與
「BIOS 沒抄過來」是兩件完全不同的事。直讀 SPD 給出了定論——**SPD 自己的序號與製造日期都是空的**。

## 入庫前的遮蔽規則

這個倉庫是公開的，所以識別資訊要遮掉，但**位移與長度必須保持原樣**，否則就失去了驗證位移的意義：

- 序號與資產標籤字串（Type 1／2／3／4／17）就地覆寫成同長度的 `X`。
- SPD 的序號欄（DDR4 位元組 325–328，二進位而非字串）覆寫成同長度的 `58 58 58 58`（＝`XXXX`）。
- Type 1 的 UUID（+0x08 起 16 位元組）整段歸零。
- 其餘欄位一律原樣保留——包含製造商、料號、插槽名稱、速度、製造週年、CRC，那些正是要驗的東西。

DDR4 SPD 的兩段 CRC（位元組 126–127 涵蓋 0–125，位元組 254–255 涵蓋 128–253）都不涵蓋序號欄，
所以遮蔽序號不會讓 CRC 失效——`SpdDecoderTests` 仍然驗得到三條模組的六個 CRC 全部相符。

重新產生的方式：以管理員身分讀 `MSSmBios_RawSMBiosTables`，套上上面的遮蔽規則後寫檔。
